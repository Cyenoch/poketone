# Design

## Context

动机和范围见 proposal.md。下面只列决定做法的源码现状（2026-11-16 读码，没有运行测试）。

- **生存模式**
  - `src/run/sim/` 是纯数据的确定性模拟。
  - `src/run/createRun.ts` 负责固定步长循环和「本机输入 → `Command`」，并作为世界客户端注册到 `AppRenderer`。
  - 视图只读模拟（`src/run/view/`）。
  - 应用路由是 `AppScreen = "lobby" | "lab" | "run"`（`src/app/session.ts:34`），页面通过 `app-host.ts` 的 `registerScreen` 挂到单一画布上。
- **按路径工作的检查**。它们只认生存模拟的路径，代码一搬走，保护就会悄悄失效：
  - `scripts/game-build.ts` 的联机指纹只扫描 `src/run/sim/`。
  - `scripts/ci-scope.mjs` 用正则 `src/run/(sim/|balance/|lab.ts|createRun.ts)` 决定是否跑 sim 和 golden。
  - `.oxlintrc.json` 中禁止非确定性 `Math.*` 的 override 只覆盖 `src/run/sim/**` 和 `src/run/lab.ts`。
  - 测试中的 `mock.module` 用写死的源码路径，例如 `scripts/ui-run-session.test.mjs`。
- **存储**：`AppStorage`（`src/platform/app-storage.ts`）是同步接口，网页用 localStorage，原生用文件。
- **渲染**：
  - 已有单一画布、`AppRenderer`。
  - 静态实例按区块打包（`src/run/view/environment/chunkedInstances.ts`）。
  - 敌人按种类批量绘制。
  - 宝可梦模型映射在 `src/run/view/assets.ts`。
- **联机**：消息是 JSON（`src/network/codec.ts`）；Harbor 拒绝已开始的房间。本 change 不碰联机。
- **内容**：森林花名册（`src/run/sim/content/stages/forest.ts`）里有绿毛虫、小拉达、波波、走路草、六尾等已有模型的种类。

## Goals / Non-Goals

**Goals:**

- 交付 proposal 中的第一个可玩版本，并让它能在真实浏览器里玩完一天。
- 数据形状一开始就按最终设计来。区块键、身份分层、按楼层预留的部件数据、按时间戳推算的再生，在第一个版本里都用真实结构表示，只是规模很小。这样后续阶段只加功能，不改存档结构。
- 生存模式的行为、golden 摘要和联机协议完全不变。

**Non-Goals:**

- 不做后台线程、二进制编码、联机和多个存档位。
- 不做承重、自由放置和守城高处。
- 不为后续阶段预留开关或空接口。数据形状要对，但不写还用不到的代码路径。

## 整体方向（后续 change 的约束）

以下是整个模式的方向，本 change 不实现。没有标注的条目是用户 2026-11-16 确认的，后续 change 必须遵守。标「（建议）」的是 Claude 提出、用户还没确认的默认方案，后续 change 要先拿到用户确认才能实现。实施时把本节搬进新手册 `docs/BASE-MODE.md`，保留这些标注，本节改为引用该手册（见 tasks 1.4）。

- **世界**
  - 6×6 个 32 单位区块，以后约 8×8，难度由内向外分圈，发狂的源头在最外圈。
  - 外圈有巢穴，清掉巢穴得古代科技点、开启下一个时代。
  - 探索结果全队共享。
  - 没有玩家的区域时间冻结；据点和进行中的围攻例外，始终运行。全员下线时世界暂停，不补算。
- **存档**
  - 多个世界存档位，存在房主设备上；房主必须在线。
  - 成员身份记在世界存档里，房间凭据只用来连接。
  - 网页和原生之间不互传存档。
- **联机**：历史成员不限，同时在线 4 人。中途加入时发一次新手物资、给完整权限，在核心旁出生。房主可以把丢失的成员身份重新指派。建造、资源和围攻结算以房主为准。
- **训练师**：
  - 倒地后由队友救起。
  - 重生顺序：床边，其次核心旁，沦陷时地图边缘的营火。
  - 训练师等级产生科技点。
  - 出战伙伴靠科技从 1 只增加到 3 只。
  - 名册容量随据点等级增长。
  - 抢同一只宝可梦时，第一下有效命中的得手，另一方的球不退。
- **经营**
  - （建议）工作按属性区分，例如草系种植和伐木、水系浇灌、火系冶炼、电系给附近设备供电、岩石和地面系采矿，全部属性都能搬运、建造和修理。
  - （建议）有工作优先级、区域划分和生产单（「做 N 个」和「库存保持 N 个」）。
  - 工人有体力，累了回床。树果既是口粮，也是诱饵和回复品；缺水只会让作物长得慢。
  - （建议）工人上限约 20，随据点等级提高。
  - （建议）据点等级在核心处投入材料升级。
- **建造**
  - 地基和家具可以自由转向，墙、楼板、屋顶跟随吸附点。
  - 用支撑距离判断承重，允许有限的悬挑；坍塌时箱子里的东西变成掉落堆。
  - （建议）坍塌的部件留下虚影；虚影不记录容器里的物品。
  - 多楼层只保留守城需要的高处，例如走道、塔楼、高台。敌人只在地面寻路，会飞的敌人才攻击上层。
  - 不做私人箱子。
- **围攻**
  - （建议）预告写明属性、方向和规模，并带随机词条。
  - （建议）围攻中击败敌人攒能量，满了三选一抽临时卡，围攻结束后失效。
  - 炮塔的伤害记在建造者名下。
  - 沦陷时只抢共享仓库箱子里的 20%，不抢正在制作的材料。
- **科技**
  - 首版科技树缩小到 3 个时代，约 30 项。
  - （建议）具体节点、时代开启条件和古代科技，见计划页的科技树初稿。
  - 科技树本身是确定的，随机性来自词条、卡、捕获和蓝图碎片。「蓝图」一词留给科技碎片，不用来称呼虚影。
- **砍掉**：饥饿、口渴、体温、耐久、负重、电线和传送带、繁殖、骑乘、心情、跨世界进度、钓鱼和料理小游戏、NPC 村庄、天气、首版的融合和战术总览镜头。
- **阶段**（建议）
  - 2：联机。
  - 3：经营，加上营地时代科技、自由放置和守城高处。
  - 4：完整世界、多个存档位、第一个巢穴和据点时代。
  - 5：承重、坍塌、要塞时代、源头头目。

## Decisions

### D1 目录：`src/base/` 和 `src/shared/`

- `src/base/` 是模式根目录，下面有 `sim/`、`view/`、`ui/` 和 `session.ts`。
- 两种模式都要用的确定性基础代码放进 `src/shared/sim/`：`math.ts`、`rng.ts`、`noise.ts`。
- 搬移只改导入路径，不留转发文件。
- 共享代码 MUST NOT 依赖任何一种模式。之后要共享更多代码，只在第一个版本确实要用时才搬，例如寻路的堆和网格。
- **为什么不选其他方案**：
  - bun workspaces：用户不要。
  - 复制一份：会形成两套实现。
  - 把模式放进 `src/run/` 下：会让 `run` 同时指两种模式，边界模糊。
- 「能搬」不等于「该共享」。World、Player、Command、存档结构、刷怪节奏、伙伴系统、伤害入口、`viewFootprint` 和固定步长循环都按模式各自一份。

### D2 先扩大检查，再搬代码

搬任何模拟代码之前，先把四类按路径工作的检查改成认识 `src/shared/` 和 `src/base/sim/`：

1. **指纹**：`game-build.ts` 一起扫描 `src/run/sim/`、`src/shared/` 和 `src/base/sim/`。两种模式共用一个构建指纹，这是已经确认的默认方案。
2. **CI 选测试**：
   - 改 `src/shared/` 要跑生存 sim 和 golden；只改 `src/base/` 跑据点测试，不跑 golden。
   - 新增 `test:base` 脚本，只列据点测试文件；同样的文件也列进 `test:sim`，所以完整 sim 运行时会一起跑。
   - `ci-scope.mjs` 多输出一个 `base`。`ci.yml` 新增一步：`base` 为真且 `sim` 为假时运行 `bun run test:base`，避免同一批测试跑两遍。
3. **lint**：确定性数学的 override 加上 `src/shared/**` 和 `src/base/sim/**`。
4. **测试路径**：测试里写死的路径随搬移一起改。

验证方法：

- 搬移前后 `bun run golden` 不变。
- `bun run test:sim` 通过。
- 在 `src/base/sim/` 里写一处 `Math.sin`，确认 lint 能拦住。
- 用四种示例 diff 运行 ci-scope：只改据点、只改共享、两者都改、完整运行。逐一核对 workflow 会执行的命令，确认没有漏跑或重复。

### D3 据点模拟

- **接口**：`stepBaseWorld(world, commands)`，固定 30 Hz。状态是纯数据，可以直接序列化。随机数只来自世界种子。
- **自己的类型**：World、Command、Event。
- **视图只读**：视图只读取模拟状态。摆放预览要调用的校验函数必须是纯函数，没有副作用。
- **寻路**：不复用生存模式的流场。生存模式的流场里墙不能打。
- **墙在格子之间**：墙和门是格子之间的「边」上的部件，不占格子。所以通行规则按跨边判断：
  - 跨过一条有墙或门的边，对敌人来说要付出代价，代价随这面墙或门的剩余耐久增加。
  - 训练师和己方宝可梦跨过门边不需要代价，跨过墙边则不行。
  - 斜向移动不能穿过墙角：两条相邻边只要有一条有墙，就不能从中间斜着穿过。
  - 单位移动时的碰撞判断和寻路用同一套跨边规则，两者不会互相矛盾。
- **围攻流场**：按上面的跨边代价，算出一张通往核心的流场。敌人沿流场走，下一步要跨过墙边时，就攻击那条边上的墙或门。部件变化只标记流场「需要重算」，每一步最多重算一次。第一个版本的地图很小，约 96×96 格，所以重算很便宜。
- **其他方案**：
  - 每个敌人各跑一次 A*：敌人多时开销太高，而且同一方向的敌人没法共用结果。
  - 把墙所在的格子整格标为高代价：同一格四面可能有不同的墙，进入方向不同撞到的墙也不同，整格代价表达不了这一点。

### D4 世界数据从一开始就分区块

- **区块**：按 32 单位区块组织，第一个版本是 3×3 个区块，面积和现有森林相当。区块里只记相对种子的改动，例如被砍的树和它的再生时刻、部件和虚影、掉落堆。
- **再生**：只记下「何时再生」。到那个时刻再生效，不在每一步扫描所有采集点。
- **身份三层**：
  - 成员：跨会话，记在存档里。
  - 席位：本次连接。
  - 实体：训练师、宝可梦、部件。
    第一个版本只有一个成员和一个席位，但伤害来源、捕获归属都已记到这三层上。
- **时间**：区域时间和世界时间分开记。第一个版本只有一个始终运行的区域，所以两者相等，但字段已经分开。

### D5 部件和虚影用同一种记录

- **三层数据**：
  - 部件定义：内容表。
  - 摆出来的实例：id、定义、网格格位或边、朝向、楼层（第一个版本恒为 0）、耐久、设置、状态。
  - 占用、墙边、寻路代价等索引：读档后从实例重建，不进存档。
- **虚影**：虚影就是状态为「虚影」的同一种实例，另记来源：规划或损坏。所以覆盖、作废、建成都走同一套占用逻辑。损坏的虚影保留原来的设置。主动拆除直接删掉实例。
- **为什么不单独建一张虚影表**：重叠判断、存档和寻路都要多写一份。

### D6 摆放校验一份代码、两处调用

- **一个纯函数**：`canPlace` 依次检查领地、网格或吸附位置、重叠、支撑和地形，返回结果和拒绝原因。
- **两处调用**：预览时在视图里只读调用；执行指令时模拟再查一次。只有通过的指令才生成虚影。
- **扣材料的时机**：材料在建成时扣，摆放虚影不花材料，所以「拒绝不扣材料」自然成立。

### D7 工人接活

- **工作板**：工人从一块确定性的工作板上取活。
- **排序**：按 base-building 规格中的修建顺序，先看类别，再看到核心的距离，最后按 id。
- **错峰**：每个工人每隔固定步数才重新规划一次，起点按 id 错开，避免所有工人在同一步思考。
- **认领**：被认领的活带着认领者，其他工人不会重复去做。
- **避险**：围攻开始后，所有非驻守的工人停下全部工作，包括远离敌人的修建，直到围攻结束。这比「只避开敌人附近的活」简单，也更好预期。
- **安全处**：第一个版本先用「核心周围的可达格」。按「敌人到不了的格子」计算更准确，但成本高，等实测证明需要再改。
- **被打倒**：工人或驻守的宝可梦被打倒后回球恢复，保留原来的分配。它认领的活随即释放，其他工人可以接手。

### D8 捕获

- **球是投射物**：命中时结算。成功率由目标的剩余生命比例和种类的捕获难度决定，后者是领域数据。随机数用世界种子。
- **不可捕获的目标**：瞄准阶段就拒绝投掷，不生成投射物，所以不耗球。
- **捕获围攻敌人**：被捕获的围攻敌人移出本场围攻的成员名单，不触发击败掉落。名单空了，围攻就结束。
- **野生宝可梦**：按区块在领地外生成，用世界种子决定。每个生成点只记下「何时重新生成」，和采集点再生一样到点才生效。
- **捕获后**：宝可梦以「个体」的形式进入名册或收容箱。个体记录种类、个体 id 和来源。等级、进化等字段等后续阶段需要时再加，不提前占位。

### D9 存档：异步的世界存储

- **接口**：新增 `WorldStore` 异步接口，网页实现用 IndexedDB。现有同步的 `AppStorage` 和生存存档不改。
- **记录**：每个存档位存一条头记录，外加每个区块一条记录。
  - **头记录**：格式版本、种子、校验和，以及不属于任何区块的全局动态状态：随机数状态、下一个实体 id、世界时间和区域时间、围攻的阶段和日程、名册和收容箱（含各自的分配和恢复进度）、共享仓库、本次沦陷是否已结算损失。
  - **区块记录**：位于该区块的全部模拟实体及其状态，包括训练师、宝可梦、敌人、飞行中的精灵球、部件和虚影、掉落堆、工人当前的认领和手上搬运的物品、采集点的再生时刻。
  - **不进存档**：占用、墙边、流场、工作板索引等都是缓存，读档后由已保存的状态确定地重建。
- **任意时刻都能保存**：退出可能发生在投球途中、搬运途中或破墙途中，所以读档一致性要求的是保存时刻的完整状态，而不只是黎明那一刻。各系统的任务都要加上「做到一半时保存、读档后继续」的续跑验证，同时比较状态和事件（见 tasks 3.4、6.2、6.4、7.2）。
- **原子写入**：同一次保存在一个 IndexedDB 事务里完成，要么全部写入，要么一条都不写。
- **只认当前格式**：格式版本不符或校验失败时，不读，也不改。
- **编码**：第一个版本整世界都很小，用 JSON 编码，每次保存都写全部区块。以后改成只写有改动的区块、在后台线程压缩，记录结构不用变。
- **原生端**：第一个版本不做，大厅入口也隐藏。

### D10 会话和镜头

- **会话**：`src/base/session.ts` 负责：读档、资源准备、固定步长循环、黎明和退出时自动保存，以及退出前等待保存结果。
- **路由**：`AppScreen` 新增 `"base"`。
- **一次提交**：进入世界和生存出发一样，只提交一次。
- **世界视图**：
  - `src/base/view/` 作为世界客户端，通过 `AppRenderer.setWorld`（`src/rendering/app-renderer.ts:184`）注册，在两个模拟步之间做只读插值。
  - 地形和植被优先复用 `src/run/view/environment/` 里只依赖地形数据的模块；需要共用时搬进 `src/shared/`，规则和 D1 一样。
  - 单位使用现有的模型加载，按种类批量绘制。建筑部件按「区块 × 部件种类」批量绘制。
  - 新的 `AppScreen` 不会自动获得生存模式对图形上下文丢失和恢复的处理，据点视图要自己接上：丢失时释放 GPU 资源，恢复时重新准备，退出时全部释放。验证顺序：丢失 → 恢复 → 继续 → 返回大厅 → 再进入。
- **主线程**：第一个版本的模拟在主线程运行。模拟是纯数据，以后搬进后台线程只需要改宿主。后台线程等手机实测证明需要时再做（见 Risks）。
- **镜头只活在视图里**：
  - 跟随镜头默认高角度，拉近时俯角变低。
  - 建造模式下切到俯视，可以在领地内平移。
  - 挡住训练师的墙按实例属性在着色器里淡化。
  - 镜头参数从不进入指令。
- **调试**：开发版暴露 `window.__poketoneBase`。

### D11 界面

- **页面**：以下页面都挂在 `app-host` 上，用 DESIGN.md 的 token：
  - 大厅入口和存档位面板
  - 据点 HUD：时钟、围攻预告、快捷栏
  - 行囊
  - 建造菜单
  - 名册和工作分配
  - 核心仓库存取
  - 工作台
- **输入**：每个页面都能用键鼠、触控和手柄操作。
- **局内配色**：生存模式的局内界面跟随当前宝可梦的属性。据点模式没有「当前宝可梦」，在 UI 设计阶段再定。
- **分工**：界面设计和实现只由 Claude（Opus）做；模拟、寻路和存档交给 GPT-6 Astra。

### D12 数值

- **集中存放**：所有可调数值放进 `src/base/sim/content/params/`，作为唯一的带类型数据源。包括一天的时长、预告提前量、围攻规模、领地半径、部件耐久、捕获难度、再生时间和沦陷损失比例。沦陷损失比例按用户决定取 20%。
- **初值的来源**：围攻规模、守岗输出和墙的有效耐久，先用一个小的解析估算定初值，写进 `docs/BALANCE.md` 的据点小节。
- **平衡工具**：生存模式的平衡模型不改；据点模式的完整平衡模型等经营和科技落地后再做。

### D13 资源

- **训练师**：原创形象，不参照任何现有动画或游戏角色。流程是：原创立绘 → 多视图设定图 → Tripo 多视图建模（低多边形）→ 侧视渲染确认朝向。动作要有待机、移动、挥击、投球、阵亡。
- **开发期替身**：资源未就绪时，开发版用胶囊体代替训练师，发布版不允许。
- **建筑部件和核心**：用 Blender 脚本生成，和树、灌木的做法一样，走现有游戏模型构建（`assets:game`）。
- **音效**：按 `docs/AUDIO.md` 决定哪些需要独立音效，用 ElevenLabs 生成。每个音效对齐对应动作的关键帧。可能需要的有：
  - 围攻预告
  - 围攻开始
  - 摆放和建成
  - 捕获的投掷、成功和失败
  - 核心被毁
  - 沦陷解除

  预告和危险提示 MUST NOT 用铃声或尖锐的哔声。

## Risks / Trade-offs

- **[范围膨胀]** 第一个版本容易越做越大。→ 判断标准只有「这 20 分钟好不好玩」，不在本 change 的项写进后续 change。
- **[搬移破坏生存模式]** 搬移数学和随机数时可能误改行为。→ 只改导入路径，搬移前后各跑一次 golden，摘要必须完全一致。不允许为了让它通过而重新录制。
- **[检查悄悄失效]** 新目录不在按路径工作的检查范围内。→ 按 D2 先扩大检查，并用 D2 的三项验证方法逐一确认。
- **[围攻寻路开销]** 墙频繁被打坏会让流场反复重算。→ 只标记、每步最多重算一次，地图有边界。用「某个种子的第 1 天围攻」重放测耗时，结果只用于诊断。
- **[手机主线程预算]** 手机上从没实测过。→ 第一个版本完成后在 iPhone 上真机测一次，记下视口、构建和结果。超出预算时，按测出的热点立项改后台线程或降精度。模拟器视口不能当作真机验收。
- **[存档损坏]** 写到一半失败可能留下坏档。→ 一个事务写完整个存档；版本不符的存档不读不改；失败时报错，不假装已保存。
- **[训练师资源进度]** 模型可能拖后腿。→ 资源任务放在最前面并行做，开发版可用替身，发布版要求真实模型。
- **[知识产权]** 训练师形象可能和现有角色相似。→ 只用原创形象；提示词和来源记录在资源旁。
- **[工人避险规则太粗]** 「核心周围」不一定安全。→ 先上线最简规则，实玩后再改；规则变化会写在后续 change 里。

## Migration Plan

- 全部是新数据，不需要存档迁移；生存存档格式不变。
- 只在网页发布，原生端隐藏入口。
- **回滚**：移除大厅入口即可。已经写入 IndexedDB 的世界存档留在原处，不读也不改。
