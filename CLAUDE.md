# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

poketone is a free, non-commercial, low-poly 3D Pokémon survivor-like (React 19 + TypeScript 7 + Three.js, Bun bundler + StyleX). There is no trainer: the player controls the Pokémon directly. `README.md` (Chinese) is the player/contributor overview (gameplay, controls, setup); `docs/DEVELOPMENT.md` covers the toolchain, dependency policy and the model/audio asset pipelines. Read both before larger changes. **Never add a shop, IAP, ads or any monetisation** (`PRODUCT.md`).

## Documentation and OpenSpec

Read `AGENTS.md`, `docs/README.md` and the relevant `openspec/specs/<capability>/spec.md`. Use `bun run spec:list` to find existing changes. New behavior, features and multi-step refactors use the workflow in `docs/OPENSPEC.md`; small corrections without contract changes need no new proposal. Preserve user authorization; do not add approval steps or branches by habit. Main specs hold behavior, docs hold design/runbooks; dated QA evidence is not kept in the repo. Complete actual tasks before archive; artifact status is not implementation verification.

## Commands

**Shared UI:** Web/native use the shared application session and single-canvas GPU host. Read the `gpu-presentation` / `platform-services` specs, `DESIGN.md` and `openspec/changes/complete-shared-ui-acceptance/` before UI/host work. Use the state-machine map for implementation ownership. Keep visual and behavioral contracts; do not add normal visible DOM UI or DOM-to-texture compatibility.

bun 1.4.4 (pinned via `packageManager`) manages dependencies and runs every script: `bunfig.toml` sets `[run] bun = true`, so package bins (oxlint, oxfmt, tsc) run on bun too. Node is not used.

Web development uses `scripts/dev.mjs`: starts Web on 5173 and Harbor on 8787 together; never chooses another port. If either port is occupied, report the existing instance instead of starting another. Startup failure and SIGINT/SIGTERM clean up this invocation's services. `scripts/web.mjs` serves Web; `scripts/web-build.mjs` bundles with Bun, emits StyleX CSS, versions models and injects the shared game fingerprint. Source changes reload the whole page. `bun run preview` uses fixed 4173 and expects a separately running Harbor for multiplayer. StyleX owns DOM platform-control styles; global document reset remains in `src/styles.css`. GPU UI continues to use Three/UIKit.

Native development: `bun run native` starts the SDL app at the lobby; `bun run test:native` checks platform contracts and the actual GPU navigation lifecycle. These are opt-in, not new Web gates. `app/session.ts` owns navigation, progress, audio and screen mounting for both Web and SDL; `run/session.ts` owns their shared run flow. `platform/{web,native}` owns storage, resources, input and window services. Read `docs/NATIVE-RUNTIME.md` for exact scope and dependency fixes.

Run a single test file, or a single test by name:

```sh
bun test --timeout=0 ./scripts/combat.test.mjs
bun test --timeout=0 -t "<name>" ./scripts/combat.test.mjs
```

Tests live in `scripts/*.test.mjs`, are written against `node:test` and run under `bun test` (`--timeout=0`: bun's default 5 s per-test limit would cut the long sim tests). They import `.ts` sources directly; bun resolves extensionless sibling imports, so sim code must stay runnable under plain bun (no bundler-only imports, no DOM/Three.js). A new test file only runs in `bun run test:sim` once it is added to that script's file list.

GitHub Actions runs the validation and deployment workflow in `.github/workflows/ci.yml`. Locally, verify by risk, not by habit: run what covers the behaviour you changed, and reuse evidence already gathered for the same version.

`scripts/ci-scope.mjs` selects the CI suites from the commit diff. Pure UI/network/deploy changes do not trigger full sim or golden. View/renderer/model-loading code and visual assets select the existing `view.test.mjs` and `ultimate-fire-vfx.test.mjs` instead; when full sim runs, it already includes those files, so they are not repeated. Actual sim/balance/lab/createRun changes, golden tooling, dependency/build configuration and manual full runs retain sim/golden checks; other sim test changes select sim only. Type/lint/format, UI, production build and the existing build/network/deployment checks remain. Real EGL tests such as `view-zone-content.test.mjs` stay targeted local checks on a supported GPU host, not a new CI platform requirement.

## Architecture

- **`src/run/sim/`: pure, deterministic simulation.** `stepWorld(world, commands)` (`world.ts`) advances at a fixed 30 Hz (`TICK` in `state/world.ts`). State is plain serialisable data, and all randomness comes from the seeded `rng.ts` (never `Math.random`). Main modules: `content/` holds the content tables (`elements`, `statuses`, `moves`, `abilities`, `lines/<line>` for starters/forms, `enemies`, `items`, `difficulties`, `stations`; key order is iteration order, so keep it); `state/` holds the state types (`entities`, `events`, `commands`, `world`); `director.ts` handles spawning and the stage clock, `beats.ts` the timeline beat kinds, `enemies.ts` enemy AI and contact, `movement.ts` chase-heading styles (`EnemyDef.move`), `skills/` one module per enemy attack (`EnemyDef.skill`: telegraphed wind-ups via `skills/telegraph.ts`, Oddish's spores) and the rules of the hazards it leaves, `hazards.ts` the hazard loop, `hurt.ts` damage to players, `bosses/` the guardian brains; `attacks.ts` + `archetypes/` cover player move behaviour; `combat.ts` and `stats.ts` handle damage and derived stats; `upgrades.ts` handles level-up cards; `evolution.ts`, `fusion.ts`, `stations.ts`, `partners.ts` and `ultimates/` cover their own systems; `terrain.ts`, `mapgen/` and `nav/` cover terrain, map spec and pathing (see `docs/MAPGEN.md`, `docs/NAVIGATION.md`). Output to the view goes through `world.events`.
- **`src/run/view/`: Three.js rendering.** Each frame it reads sim state and interpolates from the previous tick. **It never writes back, and must not call sim APIs that have side effects** (for example flow-field requests), because that would desync multiplayer. `assets.ts` (`formModels`, `facingYaw`) maps forms to GLBs and fixes their orientation. Move VFX are in `vfx/`. Colour grading uses three's `CustomToneMapping` (`grade.ts`), not a post-process pass (`docs/RENDERING.md`, `docs/LESSONS.md`).
- **`src/run/createRun.ts`** owns run resources, fixed-step simulation and local input → `Command` (`send`), registered as a world client on the application renderer. `AppRenderer` / `RenderSurface` own the canvas/context and application frame scheduling. Two-to-four-player co-op is implemented: each endpoint owns its player actions while the host settles shared results (`docs/MULTIPLAYER.md`). Keep local input as one source of commands.
- **`src/run/balance/`** holds the analytical balance model (pressure index, TTK, EHP, budgets) that `scripts/balance-*.ts` use.
- **Meta progress:** `run/progress.ts` (progress schema v4; localStorage key `poketone.progress.v3`), `run/save.ts` (export/import envelope v3 + checksum) and `run/lab.ts` (research lab upgrades). These versions are separate from world snapshot v4, which also preserves smoothed spawn pressure. Bad or mismatched saves are kept untouched. `run/session.ts` retains unsaved results for retry and waits for the backpack write before `createRun.ts` activates the prepared world; lifecycle details are in the state-machine map.
- **UI:** `app/session.ts` owns the common application flow; `ui/gpu/app-host.ts` draws screens, windows, HUD, notifications and transitions on the app renderer. `run/session.ts` updates the GPU HUD from run snapshots. `App.tsx` only mounts the Web session and its platform error surface; `platform/native/main.ts` boots SDL and file storage. Platform input reaches the same host through `UiSurface`; semantic navigation and physical shortcuts remain distinct. Shared save UI uses `TextServices`; shared networking receives a `DirectPeerFactory`, with no RTC globals on native. No duplicate React screen controllers or NativeRunHost.
- **Dev hook:** dev builds expose the live world as `window.__poketoneWorld` so you can fast-forward and inspect it in the browser.

## Conventions

- **Behaviour-preserving refactors must keep `bun run golden` unchanged.** Use active OpenSpec changes for tasks and `docs/ROADMAP.md` only for uncommitted product directions.
- Active development: change structures directly. Don't add save migrations, compat shims or legacy fields. Settings are sound, developer mode and UI scale only; no gamepad rumble feedback/settings or reduced-motion listener, control or branch. Native default-path lookup rejects legacy `save.txt` without modifying it.
- Balance changes start from the analytical model (`bun run balance:model`). The bot is only for calibration.
- UI work: read `PRODUCT.md`, `DESIGN.md` (tokens in its frontmatter) and the matching `.impeccable/surfaces/` brief first. In-run HUD/dialogs take the current Pokémon type's look through shared tokens in the GPU presentation layer; do not restore the deleted `ui/type-colors.css`. `.impeccable/` is excluded from oxfmt on purpose. Project skills live in `.agents/skills/` (for example `impeccable`, `game-ui-ux`, `game-feel`, and the project's own `skill-vfx` for move effects and telegraphs, and `skill-audio` for sound effects and music).
- Mobile is landscape-only. WebGL 2 is required, with no silent fallback.
- New 3D models: low-poly Tripo only (`smart_low_poly=true`, `face_limit` 500–1500, `--dry-run` first, `TRIPO_CLIENT_APP=claude`), through the multiview workflow in `.agents/skills/skill-model/` (official artwork → nano banana 2.1 sheet → split → multiview-to-model, 40 credits). Record provenance next to each asset. Render a side view to check facing before adding `facingYaw`. Trees, bushes and the Bulbasaur line's rig are built in Blender scripts instead (see `docs/DEVELOPMENT.md`).
- **New sound effects and music come from the ElevenLabs MCP, following `docs/AUDIO.md`** (sound identity, what deserves its own asset and how many variants, workflow, mastering). Don't hand-synthesise new sounds or pull audio from elsewhere. Generated audio goes to `assets/audio/elevenlabs/` with a `manifest.json` entry and is mastered with `bun run audio:master`; only assets marked `ship` in the manifest reach `public/audio/` (`bun run audio:master --publish`). When wiring, land each sound's hit on its effect's key frame using `master/timing.json` (docs/AUDIO.md, "声画同步"); never play a sound before its effect starts or after it has finished. The game plays them through the shared engine in `src/audio/` (menu, UI and runs use one AudioContext).
- **Public assets are fetched by their plain path only through `fetchAsset` / `assetUrl` (`src/prepare/asset-url.ts`).** Release builds serve content-hashed copies (`scripts/web-build.mjs` `assetUrls`, `HASHED_DIRS`), cached `immutable`; plain names are `no-cache` (`deploy/nginx.conf`). Never `fetch` those directories directly, never give a fixed-name file that can change a long cache, never version with query strings. A manifest missing one entry fails only that entry. See `docs/LESSONS.md` (线上缓存).
- Add newly found pitfalls to `docs/LESSONS.md` in its symptom / cause / fix format.
- Other docs: `src/run/sim/content/README.md` (content registry), `docs/AUDIO.md`, `docs/GAME-FEEL.md`, `docs/ART-PROMPTS.md`. A maintainer-local, gitignored `references/` may hold a reference game's snapshot; use it as a content yardstick only, never as something to recreate, and never commit it.
