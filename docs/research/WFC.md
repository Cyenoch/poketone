# 波函数坍缩（WFC）在 poketone 里用不用

**后续方案更正（本次清理归位）：** 当前选择布局加图章及塔楼模板，是为了直接控制战场构图并复用既有地形，不是因为WFC无法表达连通。基础邻接模型可通过预固定路径或全局约束扩展；沙漠角点0/200与overlapping189/200是不同实验，不能混为一种算法结论。原实验数字保留在下文，性能只对应当时实现、样图和设备。用户已明确质量与正确性优先，不设固定毫秒生成门槛；以下20–50ms、2/5ms等仅为早期假设，不是当前约束。真实模块需求出现时可以重新评估，不因生成较慢直接排除。

调研日期 2026-11-05。原型代码与图片在本次会话的临时目录（见 §4），未进仓库。

## 1. WFC 是什么

- **两种模型**（[mxgmn/WaveFunctionCollapse](https://github.com/mxgmn/WaveFunctionCollapse)）
  - **Overlapping**：从一张样图里切出全部 N×N 小块（可加旋转 / 镜像），输出的每个 N×N 窗口都必须是样图里出现过的小块。相当于高阶马尔可夫链。它「学风格」，不需要人写规则，但模式数随 N 爆炸。
  - **Simple tiled**：人给出一组瓦片和「哪些边能挨着」（插槽 / 邻接表），只约束直接相邻的两格。它是一阶马尔可夫链，可控、便宜，但规则要有人来写。
- **算法**：每格保存「还可能是哪些瓦片」，然后循环三步：
  1. 观察：挑候选最少的格，按权重随机定一块。
  2. 传播：把邻居里不再相容的候选删掉，直到不动（AC-3 / AC-4 弧相容）。
  3. 出现空格就是**矛盾**。原版直接重开；也可以回溯，或者像 Merrell 的 Model Synthesis 那样分块逐片修改来降低失败率（README 原话）。
  - 「合理的瓦片集 + 合理的随机」很少需要回溯（[Boris the Brave, WFC Explained](https://www.boristhebrave.com/2020/04/13/wave-function-collapse-explained/)）。
- **权重**：决定每种瓦片出现的频率，比如调房间大小（[Tips and tricks](https://www.boristhebrave.com/2020/02/08/wave-function-collapse-tips-and-tricks/)）。
- **它本质上是约束求解**：Karth & Smith 用 ASP 重新表述 WFC，分析它和传统约束求解的关系（FDG 2017，DOI 10.1145/3102071.3110566，[条目](https://bibtex.github.io/FDG-2017-KarthS.html)）。
- **已知短板**：
  - 「WFC 只约束邻近瓦片，很少生成大尺度结构，大地图会显得均质、没有规划」（WFC Explained）。
  - 「不加路径约束经常生成一堆互不连通的房间」（Tips and tricks）。
  - 补法有三种：预先固定部分格子（会被无缝融入）、全局路径约束（DeBroglie）、把地图先分区再用不同设置各跑一次。

### 相关方法

| 方法                                     | 要点                                                                                                                                                                                                                                 |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Model Synthesis（Merrell 2007）          | WFC 的前身，「两者几乎相同、结果非常相似」，更偏 3D 模型（[paulmerrell.org](https://paulmerrell.org/model-synthesis/)）。它分块逐片修改，以降低大图失败率                                                                            |
| 约束式瓦片放置（DeBroglie 等）           | WFC 加非局部约束（路径、计数、边界），本质是通用 CSP                                                                                                                                                                                 |
| 不规则网格（Townscaper）                 | 「网格是不规则的……任何拓扑、任何 3D 网格都能变成四边形」，前作 Brick Block 用类似 Marching Cubes 的角点模块（[Game Developer](https://www.gamedeveloper.com/game-platforms/how-townscaper-works-a-story-four-games-in-the-making)）  |
| 自动铺砖（marching squares / dual grid） | 先有一张粗粒度的「哪里是高地」，再按 4 个角查表选边缘瓦片。确定、O(n)、不会矛盾。很多「看起来像 WFC」的需求其实只要这个                                                                                                              |
| 噪声 / SDF 图章                          | 我们现在的做法（地形梯田、水洼的 lobes − bites + wobble），对大形状和构图最可控                                                                                                                                                      |
| 规则放置 / 房间生长（Brogue）            | 房间逐个「长」上去，天然连通；湖泊、岩浆等用元胞自动机，只在不切断地面时放下（第三方解读：[anderoonies](https://anderoonies.github.io/2020/03/17/brogue-generation.html)、[brogue.wiki](https://brogue.wiki/wiki/Level_generation)） |
| 图重写 / 循环生成（Unexplored）          | **不是 WFC**：约 5000 条图改写规则、24 种「环」，形状用小元胞自动机（[Boris, Unexplored](https://www.boristhebrave.com/2021/04/10/dungeon-generation-in-unexplored/)）                                                               |

### 真实游戏怎么用

- **Bad North**：用 Maya 做了 300 多块 3D 地形瓦片（岩壁、楼梯、海滩、崖边…），在 Unity 里扫描边缘求出能相接的组合。每块瓦片自带可通行信息，不可通行处种树而不放房子。满足不了约束就恢复存档状态重开。偶尔仍会生成「看起来坏掉、加载不出来」的岛，地图越大越慢（Game Developer 同文）。Stålberg 的 EPC 2018 讲座由 README 链接：[YouTube](https://www.youtube.com/watch?v=0bcZb-SsnrA)，未观看。
- **Townscaper**：WFC 跑在不规则四边形网格上，选的是角点模块。它是玩具，不需要保证可玩性。
- **Caves of Qud**：多遍生成。粗遍定建筑结构，**中间遍用 WFC 填细节**，末遍处理连通和投放（GDC 2019，[Vault](https://gdcvault.com/play/1025913)）。模板是 PNG，N 通常为 3，生成「通常要几秒，期间游戏卡住」（[Qud wiki](https://wiki.cavesofqud.com/wiki/Modding:Waveform_Collapse_Map_Generator)）。
- **Dead Static Drive**、**Matrix Awakens**：只见于 README 的列表，没有找到用法细节。
- **Unexplored、Brogue**：都不是 WFC，这里作为反例。

### 什么时候选 WFC

| 选 WFC                                                          | 选别的                                                      |
| --------------------------------------------------------------- | ----------------------------------------------------------- |
| 有一套**手工模块**，相接处必须严丝合缝（Bad North、Townscaper） | 要大尺度构图、成片空地、特定数量的地标：噪声 + 图章 / 规则  |
| 想从样图「学」局部纹理，并能接受均质（Qud 废墟细节）            | 要强保证（连通、平台、出生点）：生成即保证的构造法 + 校验   |
| 局部相邻规则多到手写 if 难以维护                                | 只是边缘过渡：自动铺砖查表                                  |
| 离线或加载时生成，对几十到几百毫秒不敏感                        | 早期假设20–50ms；已由质量优先决定替代，联机一致性按当前规范 |

## 2. 对照 poketone 的需求逐项判断

**2026-11-05调研时的实现**（以下数字和路径仅对应当时原型；当前流水线见 [MAPGEN](../MAPGEN.md)）：

- 生成流程是 `createTerrain` 值噪声 → 三层梯田（缓坡 / 陡崖由慢噪声决定）→ `placePads` 随机试点、压平 → `placePuddles` 轮廓 SDF 挖碗 → `placeProps` 带间隔的随机撒点 → `validateMap` 在最终导航上复查，放不下就抛 `MapGenError`，换种子重来（约 0.3%）。
- 生成在 Node 上中位数 13.4 ms。
- 渲染层把同一张高度场画成网格，崖面、崖沿、墨线都由着色器按坡度和 `groundBlockedMask` 画出（`view/terrain.ts`、`environment/ground.ts`）。**没有拼接式地形模块**，边缘过渡天然连续。

**共同风险**：

- **矛盾**：样图或规则越复杂越常见（塔 N=4 有 56%）。必须有阶段内重试和兜底的 `MapGenError`。
- **跨引擎确定性**：
  - ECMAScript 规定 `Math.log` / `sin` / `cos` / `hypot` 只是「实现近似」。原版 WFC 用香农熵（`Math.log`）选格，不同 JS 引擎可能选到不同的格，所以要换成**整数**的「剩余候选数」，并用种子流打破平局。
  - **现有 mapgen 已经在用 `Math.hypot` / `sin` / `cos`**（`puddles.ts`、`pads.ts`、`props.ts`、`validate.ts`），V8 与 JavaScriptCore 之间是否逐位一致没验证过，见 §5。
- **性能**：64×64 的 overlapping 在 M5 Pro 上中位数约 25 ms，已经是现有整条流水线的两倍。手机更慢是当时未实测的预估，不作选型门槛。
- **可读性**：WFC 的输出偏碎，俯视镜头下轮廓不清。导航的 `MIN_REGION` 会把碎块抹掉，结果是「画面上有、走起来没有」。

## 3. 当时建议（非当前任务）

以下保留2026-11-05研究稿的方案与成本估计。旧2B阶段已结束，不能据本节重新执行迁移；当前实现查MAPGEN与主规范，未排期方向查ROADMAP。

当时建议在2B阶段暂不引入WFC，改做两件事：

1. **`TerrainSpec`（2B 本来就要做）**：把 `terrain.ts` 的常量变成每张图的参数，加入少量「形状图章」。
   - 参数：`levels`、`step`、`cliffRamp` / `gentleRamp`、`undulation`、噪声频率、`rim`。
   - 形状图章：岩丘 / 台地（复用 `PuddleShape` 的 lobes − bites + wobble，改成向上抬）、线状挖槽（岩浆河、冰缝、海岸），线状挖槽要求固定留桥。
   - 保证：仍由 `validateMap` 在最终导航上复查。新增一条「出生点到每块平台、到地图四个象限都可达」，放不下就抛 `MapGenError`，沿用换种子重来。
   - 6 张图大约就是 6 份参数，外加 2 种新图章（隆起、线状挖槽）。
2. **紫苑塔用 `FloorTemplate` 数据**：手写 3–7 层（参照游戏就是这么做的），加种子变化，不需要求解器。

### 以后真要用 WFC 时（触发条件：有了一套可拼接的 3D 模块套件）

最小落地：**「废墟 / 塔墙」小块 simple-tiled WFC**。例如岩石沙漠里 2–3 处遗迹，或紫苑塔房间内部的矮墙、墓碑排布。

- **接入点**：在 mapgen 里放在 `placePads` 之后、`placeProps` 之前，作为一个 `placeKits` 阶段。规格写成 `MapSpec.kits?: { tileset: KitId; size: 12 | 16; count: number; tag: string }[]`。每块遗迹先像平台一样找一块平地（复用 `placePads` 的选址），再在 ≤16×16 的格子上解。
- **确定性**：
  - 从地图随机流派生一条**子流**：`createRng(seed ^ KIT_STREAM ^ index)`。这样加不加遗迹，都不挪动后面道具的随机数（2B 要求「mapgen 种子流不变」）。
  - 选格用整数候选数加子流打破平局，固定扫描顺序，权重用整数，不用 `Math.log`、`Math.random`。
- **连通与可放置**：
  - 边界一圈**预先固定**为「空地」瓦片，入口格固定为「门 / 缺口」。这是最便宜也最可靠的手段（Tips and tricks：固定格会被无缝融入）。
  - 解完把实体瓦片转成 `Obstacle` 或格阻挡，在最终导航上照常走 `validateMap`。区域内重试 ≤ 8 次，仍失败就抛 `MapGenError`，沿用换种子。
  - 内部连通要么事后泛洪检查，要么换成 Brogue 式的「先连通再填充」。
- **早期性能假设（非当前门槛）**：原稿曾建议每块 ≤ 2 ms（桌面）、全部遗迹 ≤ 5 ms。原型同算法 32×32、71 个模式只要 5.3 ms，16×16 加 20 来块瓦片会远低于这个数（未单测）。
- **数据格式**（`content/kits/<id>.ts`，纯数据）：

  ```ts
  { id: "desert-ruin", cell: 2, tiles: [
      { id: "wall-straight", sockets: ["w", "o", "w", "o"], weight: 4, rotate: 4, solid: true, model: "ruin-wall" },
      { id: "wall-corner",   sockets: ["w", "w", "o", "o"], weight: 2, rotate: 4, solid: true, model: "ruin-corner" },
      { id: "floor",         sockets: ["o", "o", "o", "o"], weight: 20, solid: false },
  ] }
  ```

  相同插槽字母互相可接，邻接表在加载时算出，不要人写 N² 的表。

- **视图映射**：每块瓦片对应一个 GLB（Tripo 低模或 Blender 脚本），按 `model` 实例化，和现在 `Obstacle` 的实例化走同一套。旋转取瓦片的 `rotate` 序号乘 90°。地面仍由高度场着色器画，瓦片只放墙体，不放地面。
- **工作量**：
  - 求解器约 150 行，加单测（确定性、固定格、矛盾转 `MapGenError`），约 1 天。
  - 一套瓦片数据、接入和浏览器验收，约 1 天。
  - 模块套件的建模另算，是瓶颈。
  - 排在 **2B（StageDef / StageTheme）和沙漠地图本身落地之后**，不早于 4L。
- **不值得做的情况**：如果遗迹只有 3–5 种固定造型，手写 prefab 加随机旋转就够了。

## 4. 原型（临时目录，未进仓库）

- **代码**：`wfc-fast.mjs` 是求解器：AC-4 计数传播，整数「最少候选」启发，每次尝试开始时抽一次各格的平局随机数，mulberry32。`run-fast.mjs` 和 `extra.mjs` 是实验脚本。
- **环境**：Apple M5 Pro，Node 26.13.0。每种设置 200 个种子（N=4 塔为 100 个），先预热 5 次。中心固定为空地（WFC 预置格）。
- **怎么看连通**：单元格不是导航格，「连通」指输出的地面格 4 连通，没有经过真实导航。
- **同种子两次输出逐格相同**（已验证）。

**读法**：

- 简单样图（「空地」能接任何东西）几乎不会矛盾，但输出只是样图的局部纹理重复。
- 规则一复杂（塔 N=4），矛盾率和耗时一起暴涨。
- 这两头都没给出「比噪声 + 图章 + 校验更好」的结果。
- 选格还是 O(格数²) 的线性扫描，换堆能再快一些，但量级不变。

- **V8 / JavaScriptCore 之间 mapgen 是否逐位一致**：现有代码已经依赖 `Math.hypot` / `sin` / `cos`，规范不保证跨引擎一致。联机主机建议随种子下发一个地图摘要（地形高度、障碍的哈希），对不上就直接报错，而不是悄悄分叉。这条和 WFC 无关，但 2B / 3F 前值得测一次。
- 资料覆盖：
  - Bad North 的细节来自 Game Developer 的二手报道。Stålberg 的讲座没看。

## 一并保留的算法取舍更正

现有道具撒点已带最小间距，不能将其描述为无约束随机撒点；Bridson只应在实际高密度采样需要时评估。高度网格与shader已有崖边信息，只有采用边缘模块时再评估Marching Squares；有限河沟以折线/曲线加宽度更可控，不默认改用空间殖民。主机权威不等于全模拟锁步，当前一致性与实际地图传输边界见 [simulation](../../openspec/specs/simulation/spec.md) 和 [multiplayer](../../openspec/specs/multiplayer/spec.md)。这些是原地图方案对早期调研的更正，本次没有新算法实验。
