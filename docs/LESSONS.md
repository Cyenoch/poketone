# 踩过的坑

每条写清现象、原因和以后的做法。新坑按同样格式追加。

## 渲染与 DOM

### 伤害数字从左边飞进来（越靠右越明显）

- **现象**：飘字先出现在偏左的位置，再滑到命中点；屏幕越靠右、手机上越明显。
- **原因**：数字用内联 `transform: translate(x, y)` 定位，弹出动画却用了 CSS 独立属性 `scale`。`translate` / `rotate` / `scale` 这些独立属性按规范在 `transform` **之外**、绕元素未变换时的 `transform-origin` 生效，于是缩放把定位的平移量一起放大了：`scale: 1.9` 时实际位置约是 1.9 倍的 x，回到 1 时才落到正确位置。
- **做法**：定位和动画放在两个节点上：外层只接收每帧的 `transform`，内层（`.run-number__pop`，`display: inline-block`）只做缩放 / 旋转动画。任何由 JS 逐帧写 `transform` 的元素，都不要再给它加变换类的 CSS 动画、过渡或独立属性。

### StrictMode 下第二次挂载拿到「已丢失」的 WebGL 上下文

- **现象**：开局报 `Cannot read properties of null (reading 'precision')`。
- **原因**：开发模式下 React 会挂载 → 清理 → 再挂载；清理时 `forceContextLoss()` 让这块 canvas 的上下文永久失效，第二次挂载复用了同一个 `<canvas>`。
- **做法**：每次挂载在 effect 里新建 canvas，清理时移除（`RunScreen.tsx`）。

### 后加载的全局样式覆盖了屏幕样式

- **现象**：冒险画面 canvas 高度为 0，只看到天空色。
- **原因**：`.inner-screen--run` 与 `.inner-screen` 同优先级，`styles.css` 在后面加载，`grid-template-rows: auto …` 胜出，所有子元素都是绝对定位，第一行高度为 0。
- **做法**：需要覆盖共享布局时提高选择器优先级（`.inner-screen.inner-screen--run`），不要依赖 CSS 文件的加载顺序。

### 网格行里用百分比高度的图片溢出

- **现象**：手机上伙伴立绘撑出选项框，名字被挤掉。
- **原因**：`height: 100%` 相对的是 `auto` 高度的网格行，解析不出确定值，最终按 `max-height` 渲染。
- **做法**：图片用确定的尺寸（`clamp(…vh…)` 或 token），不在自动高度的容器里用百分比高度。

### 调试视图改变了模拟结果

- **现象（设计阶段发现）**：开发者模式要画流场箭头，若调用 `flowDirection()`，会通过 `requestFlowField()` 标记「有人在读」，改变流场刷新调度。
- **原因**：查询函数带副作用。
- **做法**：调试与画面层只读模拟数据，直接读 `layer.field.cost`；凡是会改调度或状态的 API，都不能从画面层调用，否则打开调试会让联机各端结果不一致。

### 远处的草和花变小

- **现象**：离玩家越远的花、草越小，画面上半部分明显缩水。
- **原因**：为了省性能，植物在离相机 22–30 m 之间缩小到 0，但玩家本身就离相机约 17 m，屏幕上沿离相机 28 m、远角 33–36 m，缩小区间整个落在画面里。
- **做法**：距离淡出（LOD）的起点必须在画面外：先按相机高度、俯角、视场角和最宽的屏幕比例算出屏幕远角的距离，再把淡出放在它之后（现在 38–44 m）。改相机或视场角时同步检查。

### 地上的焦痕跟着玩家转

- **现象**：大字爆炎落地后留下的「大」字焦痕，玩家一走动它就跟着旋转。
- **原因**：为了让「大」字正对镜头，贴花的顶点着色器每帧按 `cameraPosition` 重算朝向；镜头跟着玩家平移，焦痕和镜头的相对方向一变，它就转。
- **做法**：落在地上的东西（焦痕、残留、命中印记）朝向只在落地那一刻定一次：`decals.stamp(..., yaw)` 存进贴花，需要正对镜头的取那一刻的 `fx.viewYaw + π`。不要在着色器或每帧逻辑里读相机或玩家朝向来摆地面形状；本来就跟着玩家的（喷射火焰的扇形、高速旋转）用模拟给的方向。

### 全屏后处理会把招式特效洗白

- **现象（设计阶段发现）**：要加调色和暗角，常规做法是先渲染到渲染目标再做一遍全屏处理。
- **原因**：three 往渲染目标画时，内置材质输出线性色、不做色调映射；而招式特效（`vfx/gl.ts`）直接输出显示空间（sRGB）颜色并按显示空间预乘混合。整帧换成线性渲染目标后，特效颜色会被当成线性值再编码一次，发白发灰；所有半透明物（圆形影子、水面）的混合也会从 sRGB 空间变成线性空间，深浅全变。
- **做法**：调色写进 three 的 `CustomToneMapping`（`view/grade.ts`）：仍然直接画到画布，每个内置材质在最后一步自己调色，没有额外的绘制与带宽；特效不经过它，保留原色。暗角用乘法混合的全屏三角形，`dst × v` 与 alpha / 加法混合可交换，结果等于真正的后处理。注意雾在色调映射**之后**混入，雾色要直接给「调过色」的颜色。

### 按半米高度网格画的水线是折线

- **现象**：水洼改成不规则形状后，岸线和深浅色带都是一段段直线拼成的多边形，近看有棱角。
- **原因**：水面着色器按「水面 − 地形高度」判水，高度图半米一格，双线性插值出来的等高线在每个格子里近似直线；水线附近坡越缓，误差越大。地形网格本身在采样点之间是线性三角形，比水面高出的那一点还会被深度测试切出折角。
- **做法**：渲染层画设计轮廓本身：开局把到轮廓的带符号距离（模拟层的 `shoreDistance`）烘焙成 4 纹素 / m 的纹理，着色器只读它；水面抬高 4 cm 盖住线性三角形的误差。开挖让水线落在碗最陡的地方，模拟层按高度网格算的水线和轮廓最多差约 0.23 m，测试守着 0.3 m；贴着水的东西（植物）也要量到这条轮廓，而不是网格。

### 水岸常量凭感觉调，越调越像贴纸

- **现象**：水洼外围一圈奶油白的等宽描边，像贴在草地上的贴花；换成泥岸后又出现一圈比草还亮的浅灰褐带。
- **原因**：一是白沫按屏幕像素计宽、整圈都有。二是太阳强（3.9），线性反照率 0.16 的「暗泥」受光后比草还亮（截图 sRGB 约 150 / 134 / 90，草约 84 / 127 / 54）。三是水边那条「从浅水推进的细线」实际宽度远超设计，在透明水边叠出一圈灰白：把各项分量直接输出成 RGB 才看出来。
- **做法**：先在截图上沿岸线取一排像素，量出哪一段比草亮，再动常量；分不清来源时，把可疑项（白沫、波线、薄水边）临时写进 `diffuseColor` 的三个通道，或者先把那一层丢掉，看岸是不是地形画的。暗色材料的反照率要按受光后的结果定，草的线性反照率才 0.1 左右。

### 网格的平直着色别在导出时拆顶点

- **现象**：把手搭树冠改成平直着色（`use_smooth = False`）后，树的顶点从约 330 个变成 1812 个，GLB 从 16 KB 涨到 68 KB；树要画两遍（阴影），全图 51 棵树和 34 丛灌木每帧多出约 20 万次顶点着色。
- **做法**：几何保持平滑（共享顶点），在材质上开 `flatShading`（片元里用屏幕导数求法线），画面一样、顶点不变。另外 bmesh 的 `create_icosphere(subdivisions=1)` 只有 20 个面，2 才是 80 个面。

### 天上劈下的闪电在屏幕顶部糊成一条黄带

- **现象**：雷丘终极技（和落雷）劈到靠相机一侧的敌人时，屏幕顶部出现一条横贯的纯黄色宽带，压住 HUD。
- **原因**：闪电是朝向相机的条带，从地面竖直拉到 9–13 m 高；相机在玩家身后 11.5 m、高 12.5 m。目标在相机一侧时，闪电顶端几乎擦过相机，透视下那一段被放大、压扁成一条横带。
- **做法**：「从天而降」的效果顶端要向远离相机的方向倾斜（`skyTop`，`vfx/fx.ts`），这样总是从屏幕上沿出画，不会经过相机附近。新加竖直高耸的特效时用同一个函数。

### Android 模拟器里 3D 画面一片空白

- **现象**：Pixel 模拟器的 Chrome 里能开局、计时、出伤害数字，但 3D 场景只有一片底色，模型预览也看不到模型。
- **原因**：模拟器（不论 SwiftShader 软件渲染还是 `-gpu host` 用 Mac 的 GPU）里 WebGL canvas 都不出现在画面 / 截图里：同一页 2D canvas 正常，`gl.clear` 成纯红的 WebGL canvas 也看不到，与游戏代码无关。软件渲染约 5 fps；`-gpu host` 下生产构建 60 fps、模拟正常推进。
- **做法**：模拟器只用来验证布局、触控和流程；3D 画面和性能要在真机或桌面浏览器上看。先放一块纯色 WebGL canvas 确认能上屏，再判断是不是游戏的问题。

### 给精灵着色器加一个形状，所有粒子都不见了

- **现象**：加了睡眠的「Z」形状后，整局没有任何粒子、弹头和火花，状态色照常；`tsc`、lint、构建全部通过。
- **原因**：GLSL ES 里 `half` 是保留字，`vec2 half` 让整个精灵片元着色器编译失败。所有精灵共用这一个材质（一次绘制），一处错误就让整层消失；报错只出现在浏览器控制台（`THREE.WebGLProgram: Shader Error`，开发服务器日志里也有一份）。
- **做法**：改了 `vfx/**` 的着色器，必须在浏览器里开局看一眼并查控制台里有没有 `Shader Error`。别用 `half`、`fixed`、`input`、`output`、`filter`、`sample` 这类 GLSL 保留字当变量名。

### iPhone Safari 横屏两侧出现天蓝色竖条

- **现象**：iPhone 横屏（iOS 26 Safari，地址栏可见）对局画面左右各空出约 60px 的天蓝条，灵动岛落在左条里；HUD 离场景边只有 12px，说明页面拿到的 safe-area inset 是 0。
- **原因**：`index.html` 已写 `viewport-fit=cover`，但这一版 Safari 横屏仍把页面装进安全区（WebKit bug 301108 / 306465），两侧用页面背景色（`:root` 的 sky）填充。CSS 改不到那两条。
- **做法**：对局中把 `:root` 背景设成 navy-deep（`:root:has(.game-shell--run)`），让两条读作深色画框；HUD 一律用 `max(边距, env(safe-area-inset-*))`，不再额外叠加边距。布局按 Safari 实际给的视口（约 812×358）验证，再用 `Emulation.setSafeAreaInsetsOverride` 模拟 cover 生效时的 844×390 / 932×430。

### 墨迹居中测出 ±1px，先查几何再怀疑组件

- **现象**：同样 16px 字、50px 高的按钮，「继续」墨迹偏 −0.12px，「我来检查」−0.88px，「0 / 3」计数签 +1px；换个位置同一组件又变 0.5px。
- **原因**：两件事叠加，都不是组件的错：① 字形本身——「/」「p」有下伸，个别汉字（耗、尽、我）墨迹上下不对称，墨迹框中心随字符串变；② 盒子落在小数 y 上时，基线吸附到整像素（1× 下最多 0.5px，2× 也没有消失）。字体度量已修好（行框中心 0.362em），`line-height: normal` 下文本 range 的盒子在每个控件里几何偏差都是 0。
- **做法**：先用 `document.createRange().selectNodeContents(el).getBoundingClientRect()` 对比文本盒与控件盒，几何偏差必须是 0；墨迹残差只在同一字符串、同一位置下前后对比（`scripts` 外的临时脚本同时跑改前 / 改后两个服务）。不要为某个字符串补 padding / translate；固定倍数的 `line-height`（1.4、1.5、等于控件高的行高）会引入真实的半行距取整，换成 `line-height: normal` 或 flex 居中。

### 暂停、选卡时什么都不动，CPU 照样被吃掉

- **现象**：暂停菜单 1× 下约 100 ms/s 主线程，选卡约 130 ms/s，4× 降频时 400–500 ms/s；首页静止也有约 20 ms/s。画面上只有一个焦点按钮。
- **原因**：① 世界冻结时渲染循环照常每帧 `renderer.render`（约 1,300 次 draw call/秒），画出来的和上一帧完全一样；② 装饰纹的漂移动画改的是 `mask-position` / 自定义属性喂给的 `background-position`，不能合成，每帧重算样式并重绘，而键盘焦点可以在一个按钮上停几分钟。
- **做法**：冻结且没有事件、镜头没动、画布没被 resize 清空时跳过 `render`（第一帧冻结和恢复的第一帧必须画，见 `createRun.ts` 的 `canvasStale` / `wasFrozen`）。会长时间停留的动画只动 `transform` / `opacity`：图案放进一层比宿主大一格的子层平移；非合成属性的动画只在真实指针悬停时播放。量的时候用 `Performance.getMetrics` 的 TaskDuration 加 WebGL draw 计数，并在 `Emulation.setCPUThrottlingRate` 4× 下再量一遍。

### GPU 上下文恢复后小地图是空的

- **现象**：手机切走应用再回来（或驱动重置）后，3D 场景完好，小地图和全图只剩图标，地形底图没了；暂停中恢复时小地图整块空白。
- **原因**：GPU 丢失时浏览器连 2D canvas 一起清空（Chrome 实测：离屏、`willReadFrequently`、32 px 的都会清空，各自先 `contextrestored`，约 0.5 s 后才是 `webglcontextrestored`）。three 会在下一次 `render` 把自己的缓冲、纹理、着色器全部重传，`WEBGL_lose_context` 测出来逐像素一致；但小地图的底图和热区光斑是开局烘焙一次的 2D canvas，没人重画。`WEBGL_lose_context` 只丢 WebGL，复现不出来，所以之前误以为是 three 丢了树和石头（其实是拿两局不同种子的截图在比）。
- **做法**：`createRun` 只有一个 `webglcontextrestored` 处理：标记冻结画面需要重画，并调用 `minimap.restore()` 重新烘焙、两块画布都重画。新加的「烘焙一次」的 2D 画布或 GPU 端生成、three 无法重建的资源，都要接到这里。验证用 CDP 的 `Browser.crashGpuProcess`（headless Chrome 加 `--disable-domain-blocking-for-3d-apis`，否则第二次崩溃后不再恢复），截图要在同一种子、同一位置、同一时刻对比。

### 窗口退出动画期间吞键、抢焦点

- **现象**：暂停菜单或属性面板关闭后 160 ms 内按的键没反应；从属性按 Esc 回到暂停菜单，焦点丢在 `<body>`；暂停菜单能叠在选卡上，之后 Esc / P 都失效。
- **原因**：`usePresence` 让窗口多挂载一段退出动画，但窗口在这段时间仍然 `stopPropagation` 全部按键，属性面板仍是 `showModal` 的模态，挡住了下面菜单的 `autoFocus`；选卡是非模态 `<dialog open>`，Tab 能走回 HUD 的暂停键。
- **做法**：退出开始就让窗口 `inert`、不再拦键；模态窗口在退出开始时 `close()`（动画照放，`display` 由作者样式保留，遮罩改用自身阴影随之淡出），下面的菜单用 effect 聚焦首项。任何对局窗口打开时 HUD `inert`。程序移动焦点（窗口打开、重抽后重新发牌）不弹提示、触屏不预先聚焦，只有玩家用按键移来的焦点才显示键盘态（`ui/inputModality.ts`）。

### 敌人的毒针在草地上看不见，手机上完全消失

- **现象**：尼多兰的毒针在桌面 1280×800 上只有约 10 px 的暗紫三角，844×390 的手机上几乎找不到；脚下的地面圈根本没画出来。
- **原因**：① 弹头按命中半径（0.14 m）画，而且用的是一半暗紫、一半淡紫的 `shard`。手机上大约 30 CSS px/m，整个弹头只有约 8 px，暗紫和深绿草地明度接近。② `shard` 和 `flame` 的尖都朝 `+y`，可 `stretch` 对齐速度时 `+x` 才是飞行方向，所以尖横着朝外，看不出方向。③ `Decal.ring` 没调 `.args()`，环宽是 0，GLSL 的 `smoothstep(0, 0, x)` 结果未定义，火花和毒针的地面圈一直没显示。
- **做法**：命中体大小的敌方弹体靠明度和轮廓被看见，不靠变大。弹头要有亮芯和墨色描边，宽度等于命中直径，只沿飞行方向加长来表示方向（新的 `Shape.needle`：尖朝 `+x`）；身后拖一道 0.5 m 的拖尾，外加一圈淡光晕；地面圈画在 1.6 倍半径处（和孢子一致）。凡是用 `stretch` 对齐速度的形状，尖都要朝 `+x`，不朝 `+x` 的形状就别对齐（火花改成直立火焰，靠拖尾表示方向）。`Decal.ring` 必须传 `.args(t, width, start)`。验收时在手机分辨率（844×390 @3×、667×375 @2×）的草地上截图，看飞行中的弹体，不能只看桌面。

### 新道具的中文名在界面上缺字，字库装不下

- **现象**：道具第 2 批加了 29 个名字和说明后，`test:ui`（ui-fonts）报几十个字不在 GPU 字库里；按提示重跑 `scripts/fonts/build-ui.py`，`ui-500` 能烘，`ui-700` 在固定的 2048 × 1280 页上失败（`msdf-atlas-gen` 退出 1），留下一半新、一半旧的字库。
- **原因**：GPU 界面没有字体回退，字库是从 `src` 里出现过的全部字符烘出来的；内容表（道具、敌人、招式名）每加一批，字符集就涨一截，三档字重共用一个固定页尺寸。
- **做法**：加内容名的批次要算上字库：先看 `test:ui` 的缺字清单，再请负责界面的人（字库尺寸、分页由界面那边定）重烘；不要自己改页尺寸，也不要在烘失败后留着半套产物不说。

## 资源

### Tripo 模型朝向不统一

- **现象**：角色侧着走、倒着走。
- **原因**：Tripo 导出的模型多数面向 glTF +X，个别面向 −X 或斜向，不是约定的 +Z。
- **做法**：新模型先用 Blender 从 +X 和 +Z 两侧各渲染一张确认朝向，在 `view/assets.ts` 的 `facingYaw` 登记校正角。

### Tripo 纹理偶尔是空的

- **现象**：绿毛虫生成后通体灰白。
- **做法**：生成后看预览图；纹理失败时用 `--then texture`（约 10 积分）重新贴图，不要重新生成整个模型。

### Tripo 低面数的圆形树冠是碎片壳

- **现象**：阔叶树和灌木近看是一团皱巴巴的尖碎片，灌木上还有个红点，玩家认不出是什么。
- **原因**：`smart_low_poly` 生成的蓬松树冠不是封闭体，而是互相穿插的单面碎片（原始导出就这样，预览图里也看得到）；发布管线再按比例减面，碎得更厉害。松树、岩石这类大块形体没有这个问题。
- **做法**：圆形树冠这类简单形体用 `assets/props/build-props.py` 在 Blender 里手搭（封闭的二十面球团 + 顶点色），不花积分；Tripo 生成后先关掉背面渲染看预览，有破洞就别进游戏。手搭时树冠要按包围盒居中在树干上：游戏按包围盒中心放置道具，偏了碰撞圆就不在树干上。

### Tripo 四足绑骨会认错身体部位

- **现象**：妙蛙种子走路时侧面伸出一块绿/黄的面片，身体扭成一团。
- **原因**：Tripo quadruped 绑骨把背上的种子当成了头（「Head」骨链竖直插进种子），把真正的头当成了一条后腿；`preset:quadruped:walk` 重定向到这副骨架上，第一帧就有四肢骨偏离静止姿态 80–120°，网格被撕开。静止姿态本身没问题，模型实际也朝 +X（之前登记的 −X 是在坏动画下看出来的）。
- **做法**：新绑骨先渲染权重图（按主导骨上色）和动画的几帧侧/正视图，再决定用不用；骨架认错时别花积分重做同一个网格，在 Blender 里自己绑（见「四足自己绑」）。朝向一律按静止姿态测。

### Tripo 双足绑骨把尾巴蒙在手臂上

- **现象**：皮卡丘跑动时尾巴大幅甩动。
- **原因**：双足骨架没有尾骨，尾巴的闪电片权重落在左上臂/前臂，跑步摆臂带着尾巴甩（相对胸骨平均偏移 0.26，角色高 1.25）。只去掉肩后顶点的手臂权重会让尾巴片混入头部/骨盆权重，个别帧折叠撕裂。
- **做法**：新角色先看权重图里尾巴、耳朵跟着哪根骨（按主导骨统计顶点，再看这些顶点的包围盒在不在那根骨该在的位置）。蒙错的整块在 `run-bipeds.py` 里按几何条件改给骨盆（`rehome`，区域写成按静止位置判断的函数），尾骨链再接过去。重新生成的皮卡丘尾巴又落在 `L_Forearm`，重新生成的雷丘尾巴后半段和闪电尖落在 `L_ToeBase`（贴地，在左脚外侧），都这样修。不要用压低摆臂来掩盖：旧做法 `damp_arm_swing` 把手臂摆幅压到 30%，尾巴还是跟着动，手臂也死板。

### Tripo 双足的 idle / run 把双手埋进肚子

- **现象**：火恐龙、卡咪龟、水箭龟、皮卡丘、雷丘在图鉴和局内站着时双手插进肚子；喷火龙、杰尼龟轻一些。
- **原因**：网格和绑骨没问题（静止姿态是 T 字，手臂离身体很远）；是 Tripo 重定向的 `preset:idle` / `preset:run` 按细身材的人把手臂放下来，贴着身体侧面垂直下垂，落进这些圆肚子里。管线（`damp_arm_swing`、`run-bipeds.py` 的摆臂）只是照搬，不是原因。重新生成网格也没用，重定向还会这样放。
- **做法**：`prepare-game-models.py` 的 `open_arms` 把每个片段里 Clavicle / Upperarm 的旋转关键帧沿球面插值拉回静止姿态的一半（`ARMS_OPEN = 0.5`），手肘、手和摆动都保留 Tripo 的。小火龙的手臂由它自己的 `prepare-model.mjs` 重摆，不走这一步。判断时渲染静止姿态和每个片段几帧的正、侧视图，对比手是在肚子外面还是里面；手臂不会触地，`lift` 和 `runClipSpeed` 不用重量。

### 参考图画错身份特征时，重新生成而不是重涂

- **现象**：旧皮卡丘的眼睛和耳尖是饱和的蓝色；一版雷丘整个头是黄的（应为橙色）。
- **原因**：都出在 text_to_model 自己生成的参考图（`generated_image.jpeg`）上，贴图忠实地照着画。游戏的调色（`grade.ts`）没有偏色：Blender Workbench 渲染和游戏截图颜色一致。
- **做法**：只在颜色能按色相段干净地分开时才用 `recolour`（卡咪龟的紫肚子；它的粉色、桃色残留按「低饱和、高亮度」再加一段）。头和脸颊、耳朵内侧同色这种分不开的，重新生成，提示词把颜色写成单独一句（「整个头、手臂、背和腿是同一种深橙色；只有肚子和口鼻是奶油色」）。

### 细长尾巴和尾巴尖，文生模型很难一次做对：改参考图再图生模型

- **现象**：雷丘连续四轮文生模型（12 个候选），尾巴不是细成铁丝、断成几段、太短，就是闪电尖飘在肩膀旁边；同时头和耳朵对的候选尾巴不对。
- **做法**：挑头、身体、颜色都对的那个候选，拿它的 `generated_image.jpeg` 用图像模型（Magpie，Gemini 3 Pro Image；GPT Image 会因版权角色拒绝）只改尾巴，存成 `generation/reference.png`，再 `tripo make <图片>` 图生模型（每个 40 积分，`texture_alignment=original_image`）。三个候选的尾巴都连成一整条，颜色也和参考图一致。

### 正面看左右不对称：网格对称，是 Tripo 的 idle 和绑骨歪的

- **现象**：水箭龟、皮卡丘等在大厅台座（正面）上左半身和左手明显更大；3/4 视角看不出来。小火龙在大厅里几乎侧身站。
- **原因**：量正面剪影的左右镜像重合度（只取身体中心平面之前的一半，尾巴、壳不算）：Tripo 双足的网格在静止姿态里是对称的（0.97–0.99），一进 idle 就掉到 0.72–0.89。两层原因，换网格都会再出现：
  1. Tripo 的 `preset:idle` 本身歪：每个形态都一样，Spine02 平均向一侧倾约 2.5°，骨盆转 −6…+3°，一只手比另一只低约 0.04（身高 1），两只脚外撇的角度也不一样（小火龙右脚 −50°、左脚 +31…45°）。
  2. Tripo 双足绑骨两侧的关节放得不一样：旧水箭龟左右手关节相差身高的 18%，多视图杰尼龟一侧的手臂链整条往身体里偏了 0.1；相同的旋转绕着不同的关节，两侧变形就不一样。
     只有妙蛙一系、伊维萨、妙蛙花（以及旧喷火龙）的网格本身不对称。
- **做法**：`prepare-game-models.py` 的 `symmetrise(run_shift)`：挑四肢骨和它带动的顶点最贴合的一侧，把它的静止骨、蒙皮权重（按镜像位置附近 4 个顶点反距离混合，网格形状对称但顶点不成对）和两个片段的关键帧镜像到另一侧；中轴骨与自己的镜像平均，去掉侧倾和扭转；跑步按半个步态周期错开镜像（Tripo 跑步一圈两个周期 = 片段的 1/4，`run-bipeds.py` 的交替步 = 1/2，双脚蹦跳 = 0），步子仍然左右交替。判断用正面剪影的半身镜像重合度，idle 8 个相位都要 ≥ 0.95。

### Tripo 的关键帧落在帧之间，只在整数帧补关键帧会留下旧帧

- **现象**：重写过的 idle 第 0 帧一只手还抬着，其余帧都对称。
- **原因**：Tripo 片段导入 Blender 后关键帧在 0.8、1.6、2.4…；在整数帧插新关键帧，旧的仍夹在中间，片段开头（0 到 0.8 之间）由旧的第一帧决定。另外，`frame_set` 设到当前帧时不会重新求值刚换上的动作。
- **做法**：重写片段前先清掉对应 fcurve 的全部关键帧，从 `floor(frame_range[0])` 开始逐帧采样；采样前先 `frame_set` 到别的帧。

### 多视图表的背面和正面要一致：尾巴画在同一侧，Tripo 会做两条尾巴

- **现象**：多视图生成的小火龙和喷火龙两侧各有一团尾巴火焰；小火龙脸上没有眼睛。
- **原因**：banana 画的背面图里火焰和正面图在画面同一侧，实际应该左右相反；Tripo 两边都信，就做了两条。
- **做法**：拆分后对比正面和背面：一侧的特征（尾巴、火焰）在背面应该在画面另一侧，不对就把背面图水平翻转（身体本来左右对称，只有尾巴的位置会变）。生成后看正面渲染有没有眼睛，再决定是否绑骨。

### 多视图表的侧视图把只在一侧的尾巴画在近侧，Tripo 会在两侧各做一条

- **现象**：杰尼龟从背后看两侧壳下各有一条卷尾巴（玩家反馈「杰尼龟怎么有两条尾巴」）；左、右侧渲染各看到一条完整的尾巴。
- **原因**：网格本身就有两条，不是绑骨、动画或程序尾巴的问题，`symmetrise` 只镜像权重和关键帧，也不是它。尾巴只卷向身体一侧（官方立绘和正面图：杰尼龟的左侧），这张表却有两处把它画到了右侧：两张侧视图都把整条卷尾巴画在离观众近的一侧（右侧视图里应该被身体挡住），背面图也把它画在了与正面图相同的画面右侧（上一条）。Tripo 把每张图都当真，在右侧又做了一条。两处错误同时存在，分不出是哪一张图单独造成的，送 Tripo 前两处都要查。
- **做法**：送 Tripo 前逐张查一侧特征的位置：背面图在正面图的画面另一侧；侧视图里只在朝向那一侧的一张画在近侧，另一张里它在身体后面，只露出伸出身体的部分。已经生成的网格用 `prepare-game-models.py` 的 `drop_lobe` 删掉多出的那条并补洞（不花积分），删完对照 `formModels.<name>.tail` 的中心线，确认程序尾巴链抓的是留下的那条。

### Tripo 双足绑骨对一些网格完全认错，重绑结果一模一样

- **现象**：多视图卡咪龟的双足绑骨把头放在髋下面、脚放在膝盖上方，尾巴蒙在右前臂和脚上；花 25 积分重绑，骨骼位置一模一样。
- **做法**：绑完先量两侧关节的镜像误差（同名 L_/R_ 骨的头相对中轴镜像后的距离 ÷ 身高）和尾巴、耳朵的主导骨，再买动画。骨骼认错时不要重绑同一个网格，换另一张多视图表重新生成网格。

### 尾骨链的中心线：只看第一段方向，回卷的尾巴尖会被留在骨盆上

- **现象**：新雷丘的尾巴拱到背后再贴地绕到左脚旁，第一版尾巴规格下有 9 个闪电尖顶点不进尾骨链，另有 38 个离中心线超过半径；35 个三角形一头跟尾骨链摆、一头钉在骨盆上，尾巴一摆就拉伸。
- **原因**：`tail.ts` 先用「在根点、沿第一段方向的平面前面」筛顶点，再按半径找最近段。尾巴向前回卷时，尾巴尖落在这个平面后面；扁平的闪电尖又比尾巴本身宽。
- **做法**：登记新尾巴后，在 Blender 里按 `tail.ts` 的同一套规则（载体骨、根平面、半径）给顶点分组，数「尾骨链顶点和保持刚性的载体顶点共用的三角形」：应接近 0，且尾巴附近不应留下刚性的载体顶点。第一段往尾巴回卷的那一侧斜，半径盖住最宽的部分（雷丘 0.14、皮卡丘 0.18 后这两个数都是 0）。

### 拼候选图时按文件名排序，别按生成日志的顺序认 ID

- **现象**：选中的雷丘候选绑完骨、做完动画才发现是另一个（多花 45 积分）。
- **原因**：`montage cand-*.png` 按文件名（ID）排序拼图，生成日志按完成顺序打印 ID，两者顺序不同。
- **做法**：每行拼图带上 ID（或拼完立刻打印 glob 展开的顺序），绑骨前用渲染图再确认一次。

### 原地动画的速度要从脚上量，不要凭眼睛扫

- **现象**：皮卡丘的跑步动画快到看不清，和移动速度对不上；之前按「着地脚世界速度最低」目测扫出的值比实测高约 40%。
- **原因**：Tripo 的跑步片段 1.25 s 两个步幅；皮卡丘腿短，步幅只有身高的 17%，地面速度 0.63（杰尼龟 1.01、小火龙 1.05，单位/秒，timeScale 1）。要让脚贴地需要 6.4 倍速，腿会糊成一片。
- **做法**：用 Blender 跟踪鞋底顶点，取脚向后移动时速度的中位数作为 `formModels[*].runClipSpeed`（`assets/measure-run-clip.py`）；再用 `MAX_CADENCE` 限制步频，超过时让脚滑而不是让腿糊（见「步频上限按每秒周期数」）。

### `tripo make -o` 会再套一层 `tripo-out`

- **现象**：`-o assets/enemies/<名字>/generation/tripo-out` 的产物落在 `…/tripo-out/tripo-out/poketone-<名字>-<id>/`，`result.json` 里的路径也带两层。
- **做法**：`-o` 只给到 `generation/`（CLI 自己加 `tripo-out/`），或生成后把内层挪上来并改 `result.json`。`prepare-game-models.py` 的 `**/model.glb` 两种都能找到，但和旧素材的目录结构不一致。

### 盘成一团的模型从 +X / +Z 两张侧视图看不出头朝哪

- **现象**：阿柏蛇盘成 S 形，+Z 侧视里头几乎正对镜头，分不清朝向。
- **做法**：取侧视图里头部轮廓最清楚的那张，按相机的右方向换算（Blender 里从 +X 看，画面右方 = glTF −Z）；再在游戏里暂停后把 `faceX/faceZ` 设成 +X、+Z 各截一张确认。

### 四足绑骨认对了身体，走路动画照样不能用

- **现象**：妙蛙草的四足绑骨这次读对了（头链末端在头里、种子在脊椎上、四条腿各自成链），但 `preset:quadruped:walk` 把腿拉直、脚尖踮起、脚掌拉成尖刺。妙蛙花的绑骨又认错了：身体散在一堆无名骨（`bone_16`、`bone_23`…）上，只有一条带名字的腿链。
- **做法**：不要指望重买同一个网格的四足动画；妙蛙这条线三个形态都改成自己绑（`assets/characters/rig-quadrupeds.py`，见下条）。

### Tripo 的参考图配错颜色时，重新贴图修不好

- **现象**：卡咪龟、水箭龟的肚子是紫色（应为奶油色）。
- **原因**：text_to_model 先生成一张参考图（`generated_image.jpeg`），参考图本身就是紫肚子；`texture_model` 按原图对齐重贴，没有文字提示参数（CLI 文档里也没有），只会重现同样的颜色。
- **做法**：看一眼 `generated_image.jpeg` 再决定：参考图对、贴图坏了才重新贴图；参考图就错的颜色，在管线里按色相段重涂（`prepare-game-models.py` 的 `recolour`，保留每个像素相对亮度，0 积分）。注意浅色区域在 Workbench 渲染里偏灰，判断白色要对照 Tripo 的 `preview.png`。

### 尾巴蒙在大腿上、尾巴尖的火飘在空中

- **现象**：第一版喷火龙尾巴很短，权重落在左大腿上，跑步时尾巴甩到脚前；尾巴尖的火焰是一块不连着尾巴的碎片，也跟着大腿跳。
- **做法**：这种是几何问题（碎片、断尾），改权重也修不好，重新生成时在提示词里写「one long thick tail attached at its lower back … a flame burning right on the tip of the tail」，并去掉「tail separated from legs」。新的一版尾巴连着身体、权重在骨盆上。双足绑骨的翅膀挂在锁骨上，跑步时翅膀会跟着肩膀略微下垂，不撕裂。

### 量原地跑步速度只取脚骨的鞋底

- **现象**：火恐龙的长尾巴贴地、水箭龟的壳很低，「最低的几个百分比顶点」里混进了尾巴和壳，左右脚量出的速度差很多。
- **做法**：`assets/measure-run-clip.py` 只取主导骨是 Foot / Toe 的顶点里最低的 3%，**按骨分组**跟踪（不按左右分：四足小跑同侧前后脚反相，按侧取质心几乎不动，妙蛙种子量出 0.24，实际 1.57），按 1/10 帧采样，取向后速度的**中位数**（平均值会被每次换向前后的慢速步拉低：妙蛙种子平均 1.31，中位数 1.55，与脚本里设定的 1.57 一致；Tripo 各形态旧的平均值偏低 0–30%）。各骨相差较大是动画本身（脚掌和脚尖、左右步幅不对称），取平均。速度按模型高度线性缩放，改了 `height` 就按比例改 `runClipSpeed`。

### 四足自己绑：Tripo 网格上骨骼热量权重会失败

- **现象**：Blender 的自动权重（bone heat）在妙蛙种子上全部顶点都没有权重；先按距离合并顶点后妙蛙种子能绑，妙蛙花仍有 1253 个顶点没权重；体素重建出「封闭」副本再传权重也不行（重建出来是 200 多块碎片）。
- **原因**：Tripo 低面数网格沿 UV 缝拆开、不封闭、叶片和身体互相穿插，热量扩散解不出来。
- **做法**：`assets/characters/rig-quadrupeds.py` 按区域算权重：每条腿管住脚周围、关节以下的一段（脚掌全给 Foot，往上 Lower → Upper），其余身体沿 +X 在 Hip → Chest → Head 之间过渡，种子和叶子只会跟身体走；跨过中线的腹底面片只给身体（否则两边跟着反相的两条腿，被拉成尖刺）。骨架按最低顶点聚类找脚，Hip 的骨头放在脚的中心上方（画面层 `hipAnchor` 按它对齐碰撞圆）。每帧在腿的竖直面里解两骨 IK，着地脚匀速向后、贴地放平，抬起的脚走弧线，直接写 FK 关键帧，不留约束和目标骨。

### 短腿走不到步幅两端

- **现象**：着地脚在步幅两端离地悬空。
- **原因**：静止姿态的腿几乎是直的，没有余量；步幅 ±0.13、腿长 0.27 时，两端需要的长度比腿还长 9%。
- **做法**：静止姿态的膝盖往前屈一点（`knee`，也定下了弯曲方向），脚本在够不到时直接报错。腿粗的形态（大腿是一整个球）不要把大腿劈在两根骨上，整块给 Upper，只把脚掌给 Foot，否则会压扁、起褶。

### 步频上限按每秒周期数，不按 timeScale

- **现象**：`MAX_CLIP_SCALE = 2.2` 对 1.25 s 的 Tripo 片段和 0.67 s 的妙蛙片段意义不同，Tripo 形态顶到上限后明显滑步。
- **做法**：`createRunView.ts` 用 `MAX_CADENCE`（3.4 周期/秒）× 片段时长 ÷ `formModels[*].runCycles` 得出各自的 timeScale 上限，超过时让脚滑而不是让腿糊。

### Tripo 跑步片段一圈是两个步态周期

- **现象**：小火龙跑起来腿快得发慌，和移动速度对不上；按上一条的上限它根本没被限住。
- **原因**：上限按「片段时长 = 一个周期」算，但 Tripo 的 1.25 s 跑步片段里每只脚前后换向 4 次，是两个周期（妙蛙一系的 0.67 s 片段是一个）。Tripo 形态实际的上限是 6.8 周期/秒：小火龙满速 5.05 周期/秒（每秒 10 步），皮卡丘 6.8，雷丘 6.5，卡咪龟 5.1；妙蛙种子是 3.3。之前「4.25 倍的皮卡丘每周期约 17 帧」其实只有约 9 帧。`runClipSpeed` 本身没错（逐脚重测与登记值一致）。
- **做法**：`measure-run-clip.py` 同时输出每圈周期数，填进 `formModels[*].runCycles`，上限按真实周期算。代价是短腿片段满速时脚只走地面速度的一部分（小火龙、卡咪龟 67%，杰尼龟 75%，雷丘 52%，皮卡丘 40%）；要脚贴地又不慌，得像妙蛙一系那样自己做步幅更大的跑步片段（见「短腿双足的跑步自己做」）。

### Tripo 双足绑骨没有尾骨

- **现象**：小火龙一系、杰尼龟、卡咪龟、皮卡丘、雷丘的尾巴永远朝一个方向，转身、停下都不动。
- **原因**：78 骨的 Tripo 双足骨架没有尾骨，尾巴整块蒙在 Pelvis / Waist 上（皮卡丘的尾巴片在左上臂上）。
- **做法**：载入时在 `view/tail.ts` 里沿 `formModels[*].tail` 的中心线加一串尾骨，只改主导骨属于 `carriers` 的顶点，第一段前半程渐变回原权重；每帧在 mixer 之后用弹簧摆尾（不改 GLB）。中心线按静止姿态的顶点散点图定，改完先把每节尾骨强行转 ±0.5 rad 截图看有没有撕裂。水箭龟的尾巴藏在壳下，没加。

### Tripo 原地片段的脚陷进地里

- **现象**：游戏把静止姿态的最低点放在地面上，Tripo 双足的 idle / run 里鞋底整段都在地面以下：皮卡丘跑步 0.13–0.19，喷火龙 0.16–0.26，水箭龟 0.25–0.35（世界单位）。
- **原因**：重定向的原地动画压低了髋部，脚没有钉在地上。
- **做法**：`measure-run-clip.py` 同时输出 run / idle 各自需要的抬升量（片段里最低点回到地面），填进 `formModels[*].lift`，画面层按两个片段的权重混合抬高。不要在运行时采样蒙皮算：每次挂模型要 80–160 ms，进化时会卡一下。

### 短腿双足的跑步自己做

- **现象**：步频封顶后，小火龙、杰尼龟、卡咪龟、雷丘、皮卡丘满速时着地脚只走地面速度的 67%、75%、67%、52%、40%，脚一直往前滑。
- **原因**：Tripo 的原地跑步步幅只有身高的十几个百分点，腿再快也追不上这些形态 3.35–4.2 的移动速度。
- **做法**：`assets/characters/run-bipeds.py` 保留 Tripo 的骨架、蒙皮和 `idle`，只重做 `run`：每帧给 Hip 下蹲、起伏、前倾、侧摆，两条腿在 Thigh / Calf 上解两骨 IK，着地脚匀速向后，后段绕脚尖翘起脚跟，抬起的脚走弧线。步幅 ÷ 着地占比 ≥ 形态速度（模型单位/秒）÷ 3.1，满速约 2.5–3.0 周期/秒，离 3.4 的上限还留 12–35% 给加速道具。调参先看每帧腿伸展比（≤ 0.95）和大腿摆角（Tripo 自己约 −45°…+55°），再渲染侧视图：地面网格按片段的着地速度后移，着地脚应钉在网格上。浏览器里实测着地脚 / 地面 0.97–1.00。皮卡丘、雷丘腿太短，跑不成交替步，做成双脚蹦跳：着地只占 19–22%，身体在着地时随脚后移、腾空时追回（`surge`），否则大腿要摆到 −80° 以上，把蒙在大腿上的肚子和屁股折出尖角。

### 绕脚趾关节翘脚跟，爪子会扎进地里

- **现象**：小火龙蹬地时最低点比地面低 0.03；皮卡丘蹬地时膝盖翻到上面，下半身折成一团。
- **原因**：Tripo 把脚趾前端的爪子蒙在 Foot 上，绕 ToeBase 关节转脚跟时，关节前面的顶点往下转。皮卡丘的脚（0.21）是腿（0.105）的两倍长，脚跟一翘，脚踝就比髋还高；膝盖方向取「向前在腿平面里的投影」时，腿往后平伸那一刻投影为零，膝盖翻上去。
- **做法**：整只脚绕脚尖（脚底最前面的顶点，放在地面上）刚性转动，关节后面的点只会抬高；脚长腿短的形态把 `roll` 压小（皮卡丘 0.1）。膝盖取髋—踝连线在侧视平面里转 90°，始终在腿的前面，不会翻。

### 带脚跟翘起的片段，脚底中位数测速偏低

- **现象**：`measure-run-clip.py` 量 `run-bipeds.py` 的片段只有脚本着地速度的 88–98%（雷丘最低），照它登记，游戏把片段播快，脚反过来向后滑。
- **原因**：脚跟翘起时脚底顶点绕脚尖转，向后的速度比脚尖慢，而翘脚跟占着地后段的 60–65%，中位数落在这一段里。只取脚底贴地时的样本能对上（误差 1–4%），但会把 Tripo 片段（脚陷进地里、着地时上下浮动）的值改掉一大截（火恐龙 1.89 → 2.90），所以通用脚本不改。
- **做法**：这些片段的 `runClipSpeed` 登记脚本打印的 `plantedSpeed` × 高度（脚尖是钉住的，这就是真值）；`runCycles`、`lift` 照常用测量脚本。

### 龟壳形态的胸口不能反拧

- **现象**：卡咪龟跑步时肚甲中间裂开一条黑缝，杰尼龟肚甲上出现折痕。
- **原因**：肚甲上半蒙在 Spine 上、下半蒙在 Waist / 大腿上；胸口反拧抵消髋部扭动时，两半错开。
- **做法**：有壳的形态 `chest = 0`，胸口跟着髋一起转；剩下的细缝来自蒙在大腿上的肚甲下沿，和静止姿态的接缝相当。

### 按顶点序号修权重，换了导出器就失效

- **现象**：小火龙改用 Blender 导出的源模型后，`prepare-model.mjs` 里「把尾巴火焰的权重抄成 1764 号顶点的」修复对不上了。
- **原因**：Blender 重新导出会重排顶点，写死的序号指向别的顶点；Tripo 把 221 个火焰顶点整块蒙在右前臂上。
- **做法**：在 `run-bipeds.py` 里按「主导骨是 R_Forearm、位置在身体后面」选出火焰顶点，整块改给 Waist（`rehome`），尾骨链载入时再把它们接过去。修权重按几何条件选顶点，不按序号。

### 四足的参考图要从侧面看到四条腿

- **现象**：第一版妙蛙花的最低点只聚成两团：身体中段两侧各一个大腿球压在爪子上，后面一条尾巴，只能左右踏步。
- **原因**：text_to_model 的参考图（`generated_image.jpeg`）是正面偏斜的视角，后腿被身体挡住，网格就照着只长了两条；改绑骨修不好。
- **做法**：主体描述写「side three-quarter view showing all four legs … two front legs under its chest and two hind legs under its rump, all four feet flat on the ground and clearly apart」并写明「no tail」。别写「palm-tree trunk」：会长出一棵高高的棕榈树把花顶上天；写「sitting low directly on its back … only a short stubby brown trunk」。生成后先用 k-means 看最低顶点是不是四团，再看形体。侧视参考图出来的网格可能不朝 +X（这版妙蛙花朝 glTF +Z），在 `rig-quadrupeds.py` 的 `yaw` 里转正；四脚前后错开时，找脚的初始中心要以脚的质心为准，不能以包围盒原点为准。

### Blender 的 `pose_bone.matrix_basis.identity()` 什么也不做

- **现象**：想先回到静止姿态再量，结果读到的是上一帧的姿势。
- **原因**：`matrix_basis` 返回副本，就地 `identity()` 改的是副本。
- **做法**：赋值 `bone.matrix_basis = Matrix.Identity(4)`。

### 改动招式栏的指令要等排队的卡

- **现象（审查发现）**：走进引梦貘人的同一 tick 吃到进化升级的糖果：卡已按当前招式抽好、正在等进化演完，站点窗口又打开并冻结全场；忘掉一招后再选那张卡，「升级已忘掉的招式」抛错，全是这种卡时还会卡死。
- **原因**：站点在 `updatePlayer` 里检查「有没有待选卡」，而升级和抽卡发生在同一 tick 稍后的 `updatePickups`。
- **做法**：会改招式 / 道具的东西（站点）放在本 tick 所有抽卡之后检查；`forget` / `fuse` 指令在有待选卡时一律丢弃（指令是网络边界，不能只靠界面不显示）。

## 平衡与测试

### 机器人「打不过」不等于游戏太难

- **现象**：加入地形后机器人大量早死，看起来像难度暴涨。
- **原因**：一部分是机器人不认地形，一直顶着爬不上的崖面；一部分才是真问题（毒孢子比玩家还快、中毒过强）。
- **做法**：先给死亡做诊断（伤害来源、最后几秒位移、所在坡度），再决定改游戏还是改机器人；机器人用真实的 `moveWithSlope` 探路。

### 地形坡度落在通行阈值附近

- **现象**：坡面上出现断断续续的「能上 / 不能上」小块，玩家在这种地方移动艰难。
- **原因**：坡度在攀爬上限附近抖动，逐格判定就会碎成斑点。
- **做法**：地形生成让坡度两极分化（缓坡明显低于上限、陡崖明显高于），通行掩码再清掉零碎小块；见 `docs/NAVIGATION.md`。

### 8 个种子的机器人结果看不出单只伙伴的变化

- **现象**：调数值后妙蛙种子从 5/8 到守卫掉到 2/8，再给它加伤害反而存活更短。
- **原因**：任何改动都会打乱整局随机序列，每局结果近似重新抽样；8 局的标准差约 ±1.4 局。换成 32 个种子，调整前后是 13/32 和 11/32，没有差别。
- **做法**：数值判断先看解析模型（`bun run balance:model`）；要用机器人判断某一只伙伴，至少 32 个种子（`ONLY=<starter> bun run balance 0 32`），并和改动前的同样 32 个种子对比。

### 自由召唤的守卫被固定等待模型漏测

- **现象**：首关成型后，后图早召守卫比路上头目更容易，原模型仍给出较长的守卫战。
- **原因**：怪群生命有后图成长下限，守卫却按重置后的局部时间生成；模型固定等到8:30召唤，把参考校准时刻当成了玩家必经路径。条件增伤还漏掉守卫及其持续伤害来源。
- **做法**：将固定挑战基准与实际召唤时刻分开，保留现有增援压力微调；至少比较早召和参考时点的连续构筑，核对模型与正式伤害函数。等级是成长结果，不是默认召唤门槛。

### 别的 agent 同时在改数值时，前后对比要自己冻结基线

- **现象**：加新敌人期间，另一个 agent 改了招式范围、伙伴招式表和 `output.ts`；工作区的 `pnpm balance:model` 一度直接报错，前后两次结果混进了别人的改动。
- **做法**：动手前把 `src/`、`scripts/` 复制到草稿目录当基线，跑模型和 32 种子机器人；「改后」也在基线副本上只叠加自己的改动再跑。报告写明对比用的是哪棵树。

### 机器人只躲危险物的中心点

- **现象**：加了阿柏蛇酸液后，机器人受到的伤害里酸液溅射占 8–17%、中毒（含独角虫、孢子、毒水洼）占 10–19%，8 种子归因。
- **原因**：`balance-bot.ts` 按危险物的 `x/z` 打分；酸液飞行中这个点是弹体，不是落点圈；冲刺线、光束的点是起点，不是整条线。
- **做法**：给死亡按伤害来源做归因（在副本里给 `damagePlayer` 打标签），再决定是改数值还是改机器人。机器人对「落点 / 线段」类预警是偏差的下限，不要直接拿它定这些招式的强度。

### 无头 Chrome 截图有几百毫秒延迟，HMR 不一定换掉画面模块

- **现象**：按定时截俯冲的命中帧，截到的还是起手；改了 `vfx/enemySkills.ts` 后画面没变。
- **做法**：轮询 `__poketoneWorld` 直到目标状态（如 `phase === "dash"`），设 `world.paused = true` 再截；改了画面代码就整页刷新、重新开局。

### 多人同时改数值时，「改前」基线会漂移

- **现象**：给每只伙伴加两招时，杰尼龟 novice 普通档到守卫：一开始记的「改前」是 71%，同样的旧招式组过一会儿再跑是 47%，再过 20 分钟又是 71%。
- **原因**：别的代理同时在改敌人、招式大小和导航，早些时候记下的「改前」已经不是同一份数据。
- **做法**：改前 / 改后在**同一时刻、同一份数据**上连着跑，只改自己那一处：例如临时脚本把 `starters[*].kit` 截回旧招式，再 `import` `scripts/balance-model.ts`，和正常跑的结果并排看。

### 草地上的绿色回复粒子看不见

- **现象**：终极吸取命中后飞回玩家的绿色光点，截图里几乎找不到。
- **原因**：亮绿色、0.07 m 的叠加光点叠在同样是绿色的草地上，色相和明度都没有对比。
- **做法**：回复类反馈用偏白的浅色（`grass.sun` → `grass.lime`）和一条从命中点拉回玩家的细光带（`Ribbon.streak`），而不是更多绿点；新特效都要在真实草地背景上截图看，不能只看代码里的颜色。

### 吸血比例先按参照点算回复量再定

- **现象**：终极吸取一开始按本家「回复伤害的 50%」取了 25%，模型参照点（4 次升级、5:00 怪群）上约 12 HP/s，比因为太强被削的贝壳之铃（5–7 HP/s）还高；存活率却几乎没变，提示里也不会报。
- **原因**：预算只比清怪和守卫输出，不比回复；而模型里的死亡主要来自被困连挨打，回复多少都看不出来。
- **做法**：新的回复来源先算「参照点清怪量 × 比例」，和剩饭、光合作用、贝壳之铃放在一起比，再定比例（现在 10%，约 4.9 HP/s）。

### 招式门槛先对照招式栏数

- **现象**：按「招牌招式 2 / 4 / 6 级」接入进化后，模型里进化招式只有 0–3% 的局学到。
- **原因**：默认只有 3 个招式栏，开局 1 招 + 两个高权重招牌招式在 4–6 级就占满；8 级进化时已经没有空栏，「有空栏才出现」的进化招式永远排不上。
- **做法**：定出现门槛前先数栏位：每个想让玩家看到的选择点都要有一个空栏。现在是 2 / 6 / 10 级（6 级第 3 栏在第 3 个招牌招式和进化招式之间二选一；门槛跟着第一次进化走，等级曲线变了要一起重定），看模型的 `learned` 占比确认。

### 地面上的东西要按地面高度判视线

- **现象**：终极技的燃烧地面落到了崖上的台地，烧到了火环本身够不到的敌人。
- **原因**：判「施放点看得见这块地」时瞄的是落点地面 + 胸口高度（0.7），这条线从崖边上方擦过（GRAZE 0.15 以内）。
- **做法**：贴地的落点（燃烧地面、水洼一类）按落点地面 + 0.3 判视线；只有判「看得见敌人身体」时才用身体高度。

### 跨时间段的友方输出要跟敌人的曲线走

- **现象**：同伴的伤害一开始固定在捕获那一刻（头目的接触伤害），模型里 2:30 收的同伴到 8:00 每秒只剩十几点，对任何水平都没用；改成也打守卫后，守卫 TTK 缩短 18–29%，涨的主要是本来就能通关的 average。
- **原因**：敌人 HP 是平方曲线，伤害只是线性，固定数值会迅速掉队；守卫自己的 HP 却是线性曲线，跟平方曲线长的东西打守卫又会过强。
- **做法**：会在一局里存在很久的友方输出按敌人 HP 的时间曲线缩放，并明确它打谁（同伴只打敌群）；调之前用模型对比「打守卫 / 不打」两种去向。

### 「嘲讽」不等于「解围」：先量后面的敌群会不会补上

- **现象**：第一版护主让同伴把碰到主人的敌人（再试 3 米、4 米内的全部）引走 2.5 秒；模型里 novice 到守卫 +15–25，机器人实测（同一组种子开 / 关）死亡 74 → 73–75，几乎没变。
- **原因**：被引走的敌人确实不再碰主人，但敌群密度下 2.5 秒内后面的敌人立刻补上，主人照样挨 2 下；模型把「护住一次被困」当成截断整串连挨打，高估了好几倍。
- **做法**：新的防御机制先用机器人量「触发后几秒内挨了几下、来自谁」（临时脚本给伤害源打标签），再决定模型怎么写；能截断被困的是对主人本身生效的东西（护主改成 1 秒无敌：74 → 60）。

### 站点的身体挡住导航，寻路要找区域边上

- **现象**：机器人在融合两招满级后迟迟走不到正辉的机器，一半的局一直绕圈。
- **原因**：站点身体是导航里的圆形障碍，`findPath` 到站点中心永远失败，机器人只剩随机游走偶尔撞进区域。
- **做法**：寻路目标取「站点身体 + 玩家身体 + 半个 `STATION_REACH`」那圈上朝向玩家的点（`balance-bot.ts` 的 `pathToStation`）；以后给任何实心物件寻路都一样。

### 文字不居中先查字体度量，不在组件里补偏移

- **现象**：kbd「1」、等级、标签、按钮里的字一律偏下约 0.07 em（26px 字偏 2px）。
- **原因**：Noto Sans SC 的 hhea 升部 1160 / 降部 288，行框中心在基线上 0.436 em，而数字、大写（cap 733）和汉字墨迹（−80..795）中心在约 0.36 em；flex 居中居的是行框，不是墨迹。
- **做法**：在字体文件里把升部 / 降部改成 1086 / 362（行框总高不变，中心落到 0.362 em），`scripts/fonts/centre-metrics.py`，重新子集化后必须重跑。不在单个组件里用 padding / translate 补偏移。验证用截图量墨迹中心对盒中心（改后 ≤0.2px）。

### 方向约定写成纯函数并测「语义」

- **现象**：Q / E 和触屏左右旋转按钮方向反了。
- **原因**：`yaw += turn` 的符号没按「相机前方 = (−sin yaw, −cos yaw)」推，增大 yaw 实际是向左转。
- **做法**：`src/run/cameraYaw.ts` 统一前方 / 右方 / 转向，`scripts/camera.test.mjs` 断言「向右转后前方朝原来的屏幕右侧」。输入、罗盘、小地图都用同一组函数，不各自写 sin/cos。

### `bun run format <文件>` 会格式化整个仓库

- **现象**：只想格式化一个文件，结果整个仓库（含其他 agent 正在改的文件、`CLAUDE.md` 表格）都被重排。
- **做法**：单文件用 `bunx oxfmt <文件>`，不要用 `bun run format <文件>`（脚本本身就是全仓库）。

### 回放脚本的输入节奏要比被测参数细

- **现象**：golden 回放每 8 秒按一次冲刺，冲刺冷却 2.4 → 2.41 改了也测不出来（每次按时冷却早就好了）。
- **做法**：会被调的计时参数（冷却、持续）要用比它更密的输入去打（冲刺改为每次冷却好就按）；新加守护脚本后先做「改一个常数必须失败」的自检。

### 守卫的脑子绕过了状态规则

- **现象**：被麻痹的飞天螳螂照样冲刺、照样放空气斩；群怪被麻痹就不出招。
- **原因**：「麻痹不能起手攻击」（`blocksAttacks`）只在群怪共用的 `skills/telegraph.ts`（和孢子）里查；守卫有自己的 `bosses/scyther.ts`，`enemies.ts` 只替它处理了睡眠（`interrupted`）。
- **做法**：任何新的出招入口（新守卫、新技能模块）在起手处查 `attacksBlocked`，在前摇 / 冲刺里查 `interrupted`，和 `telegraph.ts` 一致；加一条「带状态时不起手」的测试（`combat.test.mjs`）。

### 32 种子看不出单只伙伴 ±5 个百分点的差别

- **现象**：皮卡丘机器人 32 种子 6 / 32（19%），比妙蛙种子、杰尼龟的 8 / 32 低；同一棵树 128 种子是 27 / 128（21%），和它们的 27、30 / 128 没有差别。九个候选改动 32 种子在 4–12 之间跳；跑了 128 种子的八个里七个在 29–33（基线 31），只有四招麻痹 × 1.5 是 20。
- **原因**：通关率约 25% 时，32 局的标准差约 ± 2.5 局（8 个百分点），128 局约 ± 4.9 局（4 个百分点）。
- **做法**：32 种子只用来发现大差距；要判断 ±5 个百分点的改动，跑 128 种子（`ONLY=<伙伴> bun run balance 0 128`，单只约 5 分钟），前 32 个种子仍和 `bun run balance 0 32` 的结果对得上。

### 沙漠日落区所有敌人变成同一种红

- **现象**：沙漠第 2 区（日落）里敌人、玩家和地面几乎同色，分不清物种。
- **原因**：照搬森林黄昏的思路，用了偏红的主光（`#ff6c3a`）和暖粉天空；沙地本身就是橙色，红光再乘一次，所有颜色都被压到同一个色相。森林黄昏能用，是因为草地的绿和红光互补。
- **做法**：沙地上的日落用琥珀色主光（`#ffb47e`）、偏中性的天空和稍高的环境光（`zoneThemes.ts` `sunset`），靠长影子和低角度表现时间。新地图的氛围按该地图的地面颜色单独调，并在浏览器里看一群敌人的颜色还分不分得开。

### 海里的预警看不见

- **现象**：海岸第 2 区暴鲤龙在海里放水炮，红色预警带只从岸边开始出现，海面上的一段看不见；玛瑙水母在深水里的毒雾圈也只剩几缕烟。
- **原因**：预警和地面图章（`vfx/decals.ts`）按地形高度贴地，在海里贴在海床上；海面是一张不透明的液面，把它盖住了。粒子的落点（`fx.ground.heightAt`）同样取海床。
- **做法**：地形 uniform 带一个 `uLiquidTop`（最高液面的绘制高度，没有液面时远低于地图），图章取 `max(地形, 液面)`，`Vfx` 的 `heightAt` 同样取两者较高的。森林和沙漠没有液面，不受影响。新增水面上的单位或技能时，在浏览器里看一次海上的预警。

## 音频

### 同一提示词的几条 take，电平差到 46 dB，还有近乎无声的

- **现象**：同一个 `hit` 提示词出 4 条，峰值分别是 −49 / −26 / −16 / −3 dBFS；`hit`、`hurt`、`ui-denied` 里各有一条低于 −40 dBFS，几乎没声音。
- **原因**：模型不控制输出电平，也不保证每条都有内容。
- **做法**：原始文件不直接进游戏。先 `bun run audio:master --report <id>` 看峰值、起音、衰减和亮度，剔除 `SILENT`，再由母带按层级统一 RMS（[AUDIO.md](AUDIO.md)）。高频声音一条只要几个 credit，多生成几条再挑。

### 请求的时长不等于得到的声音

- **现象**：请求 1.5 秒的起跑音，得到约 100 ms 的爆音，之后全是 −60 dB 以下的静音；音乐请求 8 秒得到 9 秒、6 秒得到 7.5 秒。
- **原因**：`duration_seconds` 只是上限和提示，提示词没写出“持续”的结构时，模型会给一个很短的声音。
- **做法**：提示词写出时间结构（`rising ... for about one second and ending in ..., sustained from start to finish`）。拿到后看 50 ms 的包络确认，别信文件长度；母带按实际活动区间裁剪。

### 手机扬声器放不出 300 Hz 以下

- **现象**：`hurt`、`elite-kill` 前几条的频谱质心只有 100–270 Hz，在手机外放上几乎听不到。
- **原因**：提示词写了 `deep thump / low rumble`，能量全落在低频。
- **做法**：关键反馈加 `mid-range knock/crack ... audible on a small speaker`。重新生成后质心升到 565 Hz（`hurt`）、907 Hz（`elite-kill`）；`--report` 里质心低于约 300 Hz 的当作风险。

### 音乐循环：按名义速度的小节线直接切会错拍

- **现象**：三首循环曲按标称 BPM 算出小节线直接切，首尾拍型的相关度是 0.04 / −0.08 / 0.03，等于无关。
- **原因**：生成曲子的实际速度和标称值有偏差（没有精测），小节线位置累计后不再落在拍点上。AI 曲子还常带前奏（头目曲前 8 小节很稀疏）和结尾淡出（菜单曲最后几秒渐弱到静音），直接首尾相接会在接缝处突然变安静。
- **做法**：`audio-master.mjs` 在名义终点 ±1 拍里找拍型最吻合的终点，再把 1 拍长的尾巴交叉淡入开头（相关度 0.90 / 0.63 / 0.56）；前奏用 `startSec` 裁掉，`loopBars` 选在结尾淡出之前。

### ffmpeg `alimiter` 默认会自动拉高电平并延迟输出

- **现象**：音乐母带目标 −20 / −18 LUFS，实测 −18.5 / −16.5；循环文件头部多一小段延迟。
- **原因**：`alimiter` 的 `level` 默认开启（把输出重新归一），`latency` 默认关闭（输出被延迟，尾部丢掉前瞻缓冲）。
- **做法**：写 `alimiter=…:level=false:latency=true`，母带后用 `ebur128` 复测，不要只信参数。

### 一次提交几十条生成会被并发上限拒绝

- **现象**：同时跑两批共约 70 条，后一批里每个节点的最后一条返回 429 `rate_limit_exceeded`（被拒的不扣费）；个别单条显示 pending，提示 “Encountered a concurrency limit”，随后自动重试完成。
- **原因**：账号有同时排队的生成数上限。
- **做法**：分批，一批跑完再跑下一批，每批不超过约 30 条；只补被拒的那几条，不要整批重来。

### 音乐提示词写了“循环音型 + 恒定能量”，得到的就是不停重复的“叮咚叮咚”

- **现象**：试听第一批 BGM，`music-run-forest-1.mp3` 像一个拨奏音型在不停重复，没有旋律发展；试听者的原话是“叮咚叮咚不停重复”，并认为所有音乐都不好。
- **原因**：提示词里写了 `ostinato`、`steady constant energy`、`no dramatic swells`、`no big build`，乐器全是马林巴 / 卡林巴 / 拨奏弦乐，等于明确要一个单调的敲击循环；我又把“5 秒 RMS 波动只有 2.9 dB”当成好循环的证据，而它恰恰是单调的症状。没法试听时，指标只能抓缺陷，不能证明好听。
- **做法**：按 ElevenLabs 官方指南把编排按时间顺序讲出来（`start with just … then bring in … at about 0:08 a lead plays …`），用有旋律的乐器（吉他、小提琴 / 长笛、真鼓组、弦乐），马林巴一类留给音效；先出两种风格的 60 秒草稿让人听，再出全套。详见 [AUDIO.md](AUDIO.md)「音乐」。

### 音效提示词里的“亮、尖、闪”会得到 4 kHz 以上的嘶声

- **现象**：试听 `sfx-cast-electric-1.mp3`，又大又尖。量下来它 52% 的能量在 4 kHz 以上，原始峰值还超过 0 dBFS；`crit` 76–94%，`revive` 100%。
- **原因**：提示词写了 `bright / sharp / sparkle / metallic / zap / shimmer`，模型就给嘶嘶的宽带高频。
- **做法**：改写成 `muted, rounded, warm, dull, soft` 加 `no high-pitched squeal`（4 kHz 以上降到 0–21%）；母带对所有音效限制 4 kHz 以上的能量占比并加高频搁架，按事件大小设峰值上限。几乎全在高频的声音（旧 `revive`）压 12 dB 仍有 98%，EQ 救不了，只能重新生成。

### 居中问题反复出现：每屏手写标签 + 没有自动检查

- **现象**：字体度量修好后，新屏的「特性 / 终极技」标签又偏上 1–3px；之前是按钮、kbd、等级各自偏。
- **原因**：每个屏幕各写一套 chip / badge / tag（`display:block` 被父级 grid 拉高、行框比盒子矮 → 文字贴顶），而检查只靠人看截图，新组件一出就回归。
- **做法**：盒中标签统一用 `src/ui` 的共享 Tag 组件（`inline-grid` + `place-items:center` + 固定高度 token）；`bun run check:centering`（`scripts/ui-centering.mjs`）逐屏把每个盒中短标签按 4× 截图量墨迹中心 vs 盒中心，>0.5px 即失败。新屏 / 新弹窗要加进脚本的 `SCREENS`。

### 优化了“风格标签”，而不是用户描述的“感觉”

- **现象**：局内 BGM 连续被否：民谣 / 轻快乐队“不像肉鸽局内”；合成器摇滚 / taiko 管弦 / 街机摇滚“缺少宝可梦的感觉，太战斗爽”。
- **原因**：每次我都在换风格名（folk、band、synth-rock、orchestral…），把“不紧迫但不放松”理解成“有驱动感的战斗乐”；而用户要的是一种具体的感觉（宝可梦野外 / 道路主题：好奇、乐观、有记忆点的勾子、带一点悬念）。我又没法听，只能量速度和能量曲线，它们抓不住这一点。
- **做法**：在提示词里直接写感觉（`curious, adventurous and optimistic with a thread of gentle suspense, lively but not intense, not a battle track`），并明确排除“冲锋”元素（失真吉他、taiko、摇滚鼓组）；每轮出几个乐器世界不同、感觉一致的短草稿，让人选；把每次被否的原因写进 [AUDIO.md](AUDIO.md)，下一轮避开。

### 音效按真实时间播放，特效按模拟时间推进：命中停顿会让两者错开

- **现象**：同一个事件，声音已经响了，画面却还停着（命中停顿 0.12–0.35 s，特效速度降到 5%–15%），或者声音带前奏而画面的爆发点在停顿结束之后。
- **原因**：`drain(events)` 在事件当帧就按真实时间触发音效；特效用 `simDt` 推进，命中停顿时 `simDt = dt × 比例`（`createRun.ts` 的 `loop`）。
- **做法**：不要靠把每个音效的重音都裁到 0 ms 来对齐。母带写 `master/timing.json`（`hitMs` 等），接入时 `startAt = 事件时刻 + 画面关键帧 − hitMs`，负数用 `source.start(0, 偏移)` 跳过前奏；逐个音效对照画面关键帧的表在 [AUDIO.md](AUDIO.md)「声画同步」。同一帧叠加多个大音（守卫倒下时 `elite-kill` 加胜利音）要错开；同一批事件里已经有自己声音的大时刻，不要再叠通用提示音（`boss` 横幅、`level`），见 [AUDIO.md](AUDIO.md)「声画同步」。

### 战斗提示音写成“铃 / 报警”，响得再少也是叮叮叮

- **现象**：局内“叮叮叮”太突出，会心（`crit`）和预警（`tell`）“很差”，危险横幅（`danger`）“最奇怪”。每秒 0.5–1 次、最多 5–7 次，次数并不夸张。
- **原因**：提示词写的就是铃和报警：`small clean bell ping`、`clean tone`、`two quick urgent alarm beeps`。成品是 1–2.5 kHz 的纯音（一个窄带里 88–100% 的能量），`danger` 还有 700 ms 以上、放在最响一层。响度、4 kHz 占比、冷却都合格，查不出来。
- **做法**：战斗反馈（会心、预警、危险）的提示词写撞击 / 轻敲 / 气声（`knock`、`thump`、`tick`、`slap`、`swish`）加 `no ring, no bell, no pitched tone`；危险横幅用压低的铜管短音，不用报警声。母带报告新增 `tonal` 列和 `TONAL` 标记。糖果拾取的纯音钟声被确认没问题（奖励反馈可以是钟声），所以这只是建议，不是门禁。
- **顺带**：提示词里写 `mid-range audible on a small speaker` 对鼓类不起作用，两批鼓类的候选全是 100–300 Hz 的低音（手机放不出）；要中频就换本身是中频的乐器（铜管、木质轻敲），先看报告的 `centroid` 和 `LOW` 标记再选。

### 每个快照都重复“想要的音乐”，一个坏文件变成每 100 ms 重新下载一次

- **现象**：音乐文件 404 或损坏时，网络面板里同一个文件每 0.1 s 请求一次，报错也报一遍。
- **原因**：`createRun` 每个 HUD 快照（10 Hz）都调 `music.play(轨道)`；失败的解码被移出缓存以便重试，下一次调用就又取了一遍。
- **做法**：`play(轨道)` 与当前想要的轨道相同就直接返回，失败只在想要的轨道变化时才重试一次；调用方可以放心重复表达“想要什么”。

### 淡出 `cancelScheduledValues` 会取消同一参数上正在进行的淡入曲线

- **现象**：曲子刚起来不到 0.9 s 就切换，音量先跳到满再淡出。
- **原因**：淡入和淡出排在同一个 `GainNode.gain` 上；`cancelScheduledValues(t)` 会把包含 `t` 的 `setValueCurveAtTime` 一并删掉，曲线之前的值（满音量）立刻生效。
- **做法**：淡入、淡出各用一个增益节点串联，淡出只排自己的曲线，不取消任何东西。

### 开发服务器里动态 `import()` 引擎模块，拿到的是第二个实例

- **现象**：浏览器核对脚本里 `await import("/src/audio/engine.ts")` 之后，`window.__poketoneAudio` 指向另一个没有解码任何音效的实例，状态全是空的。
- **原因**：Vite 给模块 URL 带了版本参数（HMR 时间戳），带参数和不带参数是两个模块实例；每个实例各建一套 AudioContext 和监听。
- **做法**：浏览器核对只通过界面操作和开发句柄观察，不要再 `import()` 游戏模块；引擎文件自己用 `import.meta.hot.accept(() => location.reload())`，热更新后整页重载，不留下旧实例的音乐。

### 用实例颜色给身体闪色：乘不出模型本来没有的颜色

- **现象**：敌人出红色预警时身体闪色，绿色的飞天螳螂闪成了黄色，不是红色；蓝色闪在红褐色的烈雀上几乎看不出来。
- **原因**：实例颜色是**乘**在模型自身颜色上的。绿色模型的红通道很低，(4.6, 1.3, 1.0) 乘上去，绿通道仍然占优，结果偏黄；纯色调的乘数只会把缺这个颜色的身体压暗。
- **做法**：闪色用「整体提亮 + 一个通道过驱、另外两个压低」（红 (5.0, 0.75, 0.6)，蓝 (1.4, 2.1, 4.6)），并在红、绿、棕三种身体上截图确认；颜色的可靠载体是闪光精灵本身，身体闪色只是辅助（`vfx/tells.ts`）。

### 模块初始化时读另一个模块的常量，拆文件会造出循环引用

- **现象（设计阶段发现）**：重构步骤 1 想把 `castMove` 的每个分支挪进 `archetypes/<名字>.ts`。挪完以后，`homing` / `lob` / `wave` 三个模块要从 `attacks.ts` 引入 `nearest`、`aim` 等辅助函数，而 `attacks.ts` 本来就引用它们。
- **原因**：`attacks.ts` 的 `cast` 表在模块初始化时就读 `HOMING` / `LOB` / `WAVE` 这几个 `const`。只要第一个被载入的是 `archetypes/lob`（画面层 `vfx/lob.ts` 会直接引入它），它就会先去执行 `attacks.ts`，这时 `LOB` 还在暂时性死区里，直接抛 `ReferenceError`。只有函数声明的循环引用是安全的，因为函数在模块实例化时就已经可用。
- **做法**：拆文件之前，先查拆出来的模块是否在顶层读对方的 `const` / `let` / 类。有的话，先把这类聚合表改成在各自模块里定义（重构计划 3E 的 `ArchetypeDef`），再挪代码；别指望「入口总是先载入 `attacks.ts`」这种隐含顺序。
- **3E 的落地**：常量各回各的模块（`VORTEX`、`BEAM`、`LOB`…），共用辅助放在叶子模块 `archetypes/kit.ts`；形态模块和 kit 都不在运行时引入 `attacks.ts` 或 `archetypes/index.ts`，依赖只有「attacks → index → 各形态 → kit」一个方向。注意间接路径也算：`partners.ts` 原先从 `attacks.ts` 引 `nearest`，而 kit → combat → partners，所以它也改从 kit 引。`scripts/archetypes.test.mjs` 让每个形态模块在独立进程里第一个被载入；在 kit 里加一行 `import "../attacks"` 就会以同样的 `ReferenceError` 失败。
- **4L 又踩了一次**：敌人招式拆成 `sim/skills/<招式>.ts` 后，`partners.ts` 要读 `skills` 注册表，而酸液、念力、径向三个模块从 `combat.ts` 引 `damagePlayer`，于是「招式模块 → combat → partners → `skills/index` → 招式模块」成环，单独先载入 `skills/acid` 就抛 `Cannot access 'acid' before initialization`（画面层 `vfx/enemySkills.ts` 直接引入这些模块）。做法同上：把 `damagePlayer` / `PLAYER_IFRAMES` 挪进叶子模块 `sim/hurt.ts`。改完用 `for f in src/run/sim/**/*.ts; do bun -e "await import('./$f')"; done` 逐个先载入确认。

### 状态的「这一 tick 是否生效」分两种时点，统一成列表时不能拉平

- **现象（重构 2A 设计阶段发现）**：把敌人的 `burn` / `paralysis` / `sleep` / `wet` 和玩家的 `poison` / `slow` 换成一个 `statuses` 列表时，若每个状态都「先递减、再看还剩没剩」，剩余时间不足一 tick 的灼伤和睡眠会少算一 tick，golden 就会变。
- **原因**：旧代码里时点不一致。灼伤伤害、玩家中毒掉血、睡眠定身读的是这一 tick **开始时**的状态（先判断 `> 0`，再递减）；麻痹顿挫、湿润减速、玩家减速读的是**递减之后**剩下的。另外速度系数相乘的顺序（先麻痹后湿润）也会影响浮点结果的末位。
- **做法**：`sim/status.ts` 让调用方先读 `dotRate` / `drainRate` / `stopped`，再 `decay`，最后用 `slowed` 算速度；`slowed` 按注册表顺序相乘，所以 `content/statuses.ts` 的键顺序就是生效顺序，不能随意调整。玩家在 `updatePlayer` 开头递减，但中毒掉血仍然放在回血之后结算。

### 同一种子在 Node、Chrome、Safari 里跑出三个结局

- **现象**：golden 的同一用例，在 Node、Chrome、Playwright WebKit 里胜负 tick 不同，甚至一边胜利一边没打完；每个引擎自己重跑完全一致。
- **原因**：`Math.sin` / `cos` / `tan` / `atan2` / `acos` / `exp` / `hypot` / `cbrt` 不要求正确舍入，各家实现差 1–4 ULP：WebKit 用 Apple libm，Node 与 Chrome 是不同的 V8 构建，三角函数也不一样。JSC 的整数次幂 `x ** n`（n ≥ 3）是反复平方。1 ULP 进入距离比较、选目标，几十秒后就放大成不同的击杀和掉落。
- **做法**：sim / mapgen / `lab.ts` 只用四则运算、`Math.sqrt`、`round` / `floor` 等精确运算和 `src/run/sim/math.ts`（fdlibm 移植的 `sin` / `cos` / `atan` / `atan2` / `exp`，`hypot = sqrt(x²+z²)`，`powInt`）；`**` 只允许字面量 2，小数指数改查表或 `exp`。lint（`.oxlintrc.json` 的 `no-restricted-properties`）禁 `Math.sin` 等，`scripts/sim-math.test.mjs` 禁其余的 `**`。golden 的输入驱动也用 `sim/math.ts`。验证用 `scripts/determinism/run.mjs`，详见 `docs/research/DETERMINISM.md` §6。
- **移植 fdlibm 的坑**：`__ieee754_rem_pio2` 的第 2、3 轮规约只能在大幅抵消时进入（那时上一轮的减法是精确的）。图省事每次都跑满三轮，会丢掉第 2 轮的舍入误差，sin/cos 误差从 0.75 ULP 涨到 1.35 ULP，三引擎照样一致，所以只有拿高精度参考值对比才看得出来。

### context 恢复后再开一局，控制台刷满「delete: object does not belong to this context」

- **现象**：world canvas 经历 `webglcontextlost` → `webglcontextrestored` 后继续玩，放弃 / 结算后再开一局，控制台瞬间刷出大量 `WebGL: INVALID_OPERATION: delete: object does not belong to this context`，直到 Chrome 报 `too many errors` 后不再报告任何 WebGL 错误；画面仍正常。
- **原因**：three 的 `onContextRestore` 只是重新 `initGLContext()`，新建一套 textures / geometries / programs 管理器。恢复前上传过的资源仍挂着旧管理器的 `dispose` 监听，`dispose()` 时旧监听拿着失效的句柄在**已恢复的**同一个 context 上 `delete*`。
- **做法**：宿主在 `webglcontextlost` 回调里（three 已经 `preventDefault`）对所有已上传的资源调用 three 正式的 `dispose()`。丢失状态下 `delete*` 都是静默空操作，旧监听随之移除；CPU 对象保留，恢复后由新管理器重新上传（DataTexture 与 ImageBitmap 都实测可重传，`info.memory` 不重复计数）。场景树用 `src/rendering/releaseUploads.ts` 的 `releaseUploads(root)`：几何体、材质（含其属性里的贴图、`ShaderMaterial` uniforms 里的贴图）、`InstancedMesh`、`SkinnedMesh.skeleton`、灯光的 `shadow`；不摘节点、不关图片。树外的和只在 `onBeforeCompile` 闭包里的上传由拥有者的 `releaseUploads()` 负责：`RunView`（场景 + 地形高度图、地面图层、岸线这三张闭包贴图）、`RunAssets`（四张地面贴图、实例源几何体、全部已载入模型）、`LoadedModel`（与 `dispose()` 同一批资源，但不关 ImageBitmap）；未挂载的进化形态由 createRun 逐个 `form.model.releaseUploads()`。漏掉任何一个拥有者，之后 dispose 时就会重新报错（实测：不放形态 9 条、不放资源 14 条、只放场景 2 条）。uikit 的字体页可以从公开的 `Text.fontSignal.value?.pages` 拿到，但 uikit 整个应用期间缓存字体、从不释放，所以不卸载字体就不需要处理。另一种已验证的做法是对局结束前先 `forceContextLoss()` 再释放、下一局换新 renderer，但它会换掉 canvas，对常驻的 UI renderer 也不适用。

### GPU UI 的文字、Esc 徽标「消失」，窗口退场留下残影

- **现象**：选卡横幅的「升级 Lv N」和所有 Esc 徽标只有底板没有字；暂停 / 站点关闭时文字先淡完，面板底色、纹章和精灵球在原位停留到 240ms。
- **原因**：uikit 的 `zIndex` 和 `opacity` 都是普通继承，不是 CSS 的层叠上下文和组透明度。元素自己写了 `zIndex: 1`，它的 majorIndex 就是全局的 1，排在 `zIndex: 30` 的关闭键底板之下（`order.js`）。元素自己写了 `opacity: 0.28`，窗口淡出时它仍是 0.28。树外的 shader 网格（精灵球、焦点描边）也读不到窗口的透明度。
- **做法**：GPU UI 只通过 `src/ui/gpu/layer.ts` 设置层级和透明度。`stack(c, n)` 取父级层级再加 n，`fade(c, a)` 取父级的实际透明度再乘 a，树外网格用 `inheritedOpacity(锚点控件)`。`src/ui/gpu` 里不再直接写 `zIndex` 或 `opacity`。小地图和罗盘是有意用绝对 `baseOrder` 的独立子系统，暂不改。

### uikit 滚动容器出现 1px 的假滚动条

- **现象**：暂停正文和设置正文右侧常驻一条细滚动条，内容其实放得下。
- **原因**：按钮的厚底板是向外伸出 3–5px 的绝对定位子元素。uikit 计算 `maxScrollPosition` 时会把所有子元素（包括绝对定位的）的范围算进去，然后再加 padding，所以加多少 padding 都消不掉这块溢出。原版用的是 CSS `box-shadow`，它不产生可滚动溢出。实测：暂停和设置的 `maxScrollPosition.y = 1`。
- **做法**：投影和底板用 `src/ui/gpu/box-shadow.ts` 的 `BoxShadow`：布局盒等于父元素，由顶点着色器向外画，只画在边框之外，并照常被滚动容器裁剪。不要再用向外伸的绝对定位子元素模拟阴影。

### GPU 窗口每次打开都重新编译着色器

- **现象**：暂停窗口第二次打开时仍要编译 12 个着色器程序，开窗那一帧明显卡顿；保留程序之后，程序数量每开一次还会再多一个。
- **原因**：three 在最后一个使用某程序的材质被释放时删除该程序，而窗口每次打开都重建、每次关闭都释放。`ShaderMaterial` 的程序键由着色器源码缓存 id 组成，这个缓存条目也随材质一起释放，所以相同源码下次会拿到新 id，算出新的程序键。
- **做法**：UI renderer 在整个应用期间保留它编译过的程序（`app-host.ts` 中的 `retainPrograms`，UI 程序是固定的一小组）。手写着色器用 `src/ui/gpu/ui-shader.ts` 的 `UiShaderMaterial`，它按名字生成稳定的程序键。新建的窗口先用 `UiStage.compileAsync` 编译，编译完成前冻结它的时钟、暂不绘制。

### 世界暂停时 UI 画布仍以 10Hz 重画

- **现象**：打开暂停窗口、或者开发时手动暂停模拟，HUD 上没有任何变化，UI 画布却每秒重画约 10 次，JS 时间也居高不下。
- **原因**：`createRun` 每 0.1 秒都发布一个新的快照对象，即使内容和上次相同。React 随之重跑 `hud.update`，大量 `setProperties` 让舞台变脏。
- **做法**：快照内容不变时不再发布（序列化后比较）。罗盘的输入（tick、插值、镜头朝向）不变时也不重画。

### 网页字体抢走 GPU 首屏的带宽

- **现象**：在 10Mbps 网络下，GPU 主菜单的文字要到第 9–11 秒才出现。
- **原因**：`index.html` 用最高优先级预载了 DOM 界面用的 2MB woff2。即使改成 prefetch，或者页面上没有可见的 DOM 文字，CSS `@font-face` 也会在 DOM 排版时触发下载。UI 字体图集原先还是串行下载、全部到齐才开始绘制。
- **做法**：图集按字重懒加载（uikit 支持函数形式的字体源），每个字重的 JSON 和 PNG 并行下载，首屏需要的到齐后再预取其余图集。DOM 字体由 `src/domFont.ts` 在首屏完成之后（或 GPU 启动失败时）用 `FontFace` 注册。

### 选卡焦点描边上沿被裁掉

- **现象**：GPU 选卡的第一张卡获得焦点后上浮 6px，黄色描边的上沿被切掉；悬停、发牌和手机布局里也会被切。
- **原因**：卡片被放进一个只留 2px 内边距的滚动正文里，描边按这个滚动盒裁剪。原版选卡是铺满屏幕的 dialog，卡片外面没有任何裁剪盒，描边、上浮、发光和飞向槽位都在屏幕范围内自由绘制。
- **做法**：选卡的根节点本身就是铺满视口的唯一滚动盒（`run-choice-content.ts`），裁剪边界就是屏幕。卡片的描边、放逐虚线和投影画在卡片自己的着色器里（四边向外扩出的四边形），随卡片一起变换、淡出和分层。

### uikit 的数字 `lineHeight` 是字号的倍数

- **现象**：选卡里每段文字的盒子高达几百像素，卡片被撑满整屏，字也看不见。
- **原因**：按 CSS 的 `line-height: normal` 算出像素值（12px 字 → 17px）直接写成 `lineHeight: 17`。uikit 把数字当成字号倍数，17 × 12 = 204px。
- **做法**：像素行高写成 `px / fontSize` 的倍数（`run-choice-content.ts` 的 `lineHeight()`）。字符串百分比同样相对字号。

### 重抽后选卡横幅没有重新盖章

- **现象**：原版重抽时横幅会重新盖章（它以卡片 id 为 key）。GPU 版重抽时横幅不动。
- **原因**：模拟在原对象上重抽（`pending.id = nextId++; pending.options = …`），快照里的 `pending` 和上一次是同一个对象。拿 `before.pending.id` 和新状态比较，两边已经是同一个新 id。
- **做法**：需要比较前后状态时，在构建时把关键值存成原始值（横幅存 `"${id}:${source}"`），不要依赖上一次状态对象里的字段。`dealKey` 这类在 React 侧现算的字符串没有这个问题。

### uikit 子节点在同一次布局里移出再加回，面板消失

- **现象**：每次选卡状态更新（例如切换放逐模式）后，横幅上「升级」标签只剩文字，金色底和描边不见了。
- **原因**：布局函数每次都把标签 `removeFromParent()` 再 `add()` 回同一个父节点。uikit 的实例化面板在这一过程中没有重新登记。
- **做法**：只在布局形态真的改变时（桌面 ↔ 矮横屏、竖排 ↔ 侧栏）才重新挂载节点，其他时候只改属性。

### 原版 CSS 的覆盖规则不一定生效

- **现象**：照 `run-screen.css` 实现的选卡类型标签是药丸形、外加 2px 描边，「升级」标签外圈多一层深色描边，稀有度标签描边是金色，和原版截图都不一样。
- **原因**：`ui.css`（`.game-tag`）在 `run-screen.css` 之后加载，同等优先级的 `.run-card__kind`、`.run-card__tag`、`.choice-banner__kicker` 中的 `border-radius`、`box-shadow`、`--tag-ring` 都被覆盖。只有更具体的 `.run-card[data-kind="item"] .run-card__kind` 生效。另外 `::before` 不受全局 `* { box-sizing: border-box }` 影响，宝石是 7px 加 1.5px 边框，共 10px。
- **做法**：保真迁移以原版实际渲染的截图为准，CSS 只用来查数值。拿不准时放大原版截图核对。

### context 丢失时漏掉 shader 自己采样的纹理

- **现象**：（预防）卡面背景图只放在自定义 uniform 里时，`releaseUploads` 看不到这些纹理，context 恢复后会使用失效的 GPU 句柄。
- **原因**：`releaseUploads` 只遍历场景树、材质字段和 `ShaderMaterial.uniforms`，`onBeforeCompile` 闭包里的 uniform 不在其中。
- **做法**：卡面纹理放进材质自己的 `map` 槽位，着色器直接采样 `map`，这样共享的释放逻辑就能看到它。

### 手机上 GPU 提示一旦出现就点不掉

- **现象**：手机上点过一个有提示的控件之后，提示一直显示。点空白处不消失，只有点另一个可以操作的控件才会换掉。
- **原因**：GPU 窗口把「提示」挂在「当前焦点」上。触摸按下时 `MenuInput.down` 会把焦点移到被按的控件，而点在空白处没有命中任何控件，焦点就一直不变，提示也就不消失。原版的 Tooltip 是另一套规则：鼠标悬停时显示，键盘焦点可见时显示，触摸则是长按 450ms 显示、点禁用控件切换显示；点别处、滚动、Esc 或窗口尺寸变化都会关闭。
- **做法**：所有 GPU 窗口共用 `tooltip.ts` 的 `GpuTooltip`，状态统一由 `run-overlays.ts` 管理。控件只提供 `tip` 文案，禁用但可聚焦的控件用 `locked`（对应原版的 aria-disabled）。显示哪一个提示的优先级是：触摸打开的、鼠标悬停的、键盘焦点所在的。触摸只在焦点可见时才会显示提示。宿主在按下、移动、抬起时通知窗口；长按打开提示时，这次按压不会再激活控件。

### 预编译的窗口和真正打开的窗口用了不同的 shader 程序

- **现象**：载入页上已经把暂停窗口预编译过一遍，第一次打开暂停时仍然编译了一个 `poketone-outer-shadow` 程序。两个程序的缓存键只差裁剪平面数（预编译时 0，真实窗口 4）。
- **原因**：uikit 的 `Content` 给子网格设置 `clippingPlanes`、渲染顺序，是在子节点变化后用 `setTimeout(0)` 延迟执行的 `notifyAncestorsChanged()` 里完成的。窗口在同一帧里建好并立刻 `compileAsync`，这时材质还没有裁剪平面，编译出的程序和下一帧真正绘制用的不是同一个。
- **做法**：自定义 `Content` 表面在加入网格后立即调用 `this.content.notifyAncestorsChanged()`（`box-shadow.ts` 的 `OuterPaint`，其他表面本来就这样做）。验证方法：对比打开窗口前后 `renderer.info.programs` 的 `cacheKey`。

### uikit 文字在根节点设置字体之前创建会报字体不存在

- **现象**：控制台出现 `unknown font family "Poketone UI"`。每创建一个 `GpuRunOverlays` 实例报一次，预编译副本多了以后会报很多次。
- **原因**：类字段初始化先于构造函数体执行。`tooltip = new GpuTooltip(this.stage)` 在字段里就把文字挂到了根节点上，而根节点的 `fontFamilies` 要到构造函数里才设置，文字第一次解析字体时只能找到默认字体。
- **做法**：会挂到 stage 根节点上的文字组件，在根节点设置好 `fontFamilies` 之后再在构造函数里创建。

### 自绘 MSDF 文字：距离场之外是饱和值，不是「刚好在描边上」

- **现象**：GPU 伤害飘字每个数字外面都有一个深色方块，或者沿字形框有一圈淡淡的细线。
- **原因**：UI 图集是 48px/em、距离范围 4 个 texel，只记录边缘两侧各 2 个 texel 的距离；17px 字号下不到 1px。再往外，采样值饱和在 0 附近，算出来的距离约为 −0.7px，正好落在 0.5px 描边加抗锯齿的过渡区里，于是整个字形框都被画上了描边。字形框最外一圈 texel 经过双线性过滤、缩小后取到的 mip 层级，都会混入图集里相邻字形的数据。
- **做法**：中值低于 0.1 的采样当作「远在外面」；距离字形框边缘不到 1 个 texel 的位置不采样；固定用 `textureLod(…, 0.)` 采样。光晕不再依赖距离场，改为在两圈采样点上取已描边字形的覆盖率平均。

### 动画里复用同一个 Color 对象，UIKit 不会更新

- **现象**：HUD 受伤时 HP 边框变红后，再也不回到深蓝；金币数字变白后不回到金色。
- **原因**：每帧都对同一个 `Color` 调用 `.set().lerp()`，再把这个对象传给 `setProperties`。UIKit 的属性信号按引用比较，引用没变就认为值没变：第一次传入时生效，之后的修改全被忽略。
- **做法**：传给 `setProperties` 的颜色每次都用新对象（`new Color(...)` 或新的 `[r, g, b, a]` 数组）。可复用的 `Color` 只能用作中间计算。

### 并排三栏用 flex 平分，中栏不居中

- **现象**：HUD 顶部的计时和指南针整体偏左约 50px（1280 宽时中心在 590，应为 640），罗盘画在中栏之外并偏右 80px。
- **原因**：原版是 `grid-template-columns: minmax(0, 1fr) auto minmax(0, 1fr)`，两侧永远等宽，中栏宽度跟随指南针。GPU 版改用左右两栏 `flexGrow: 1, flexBasis: 0`，但 Yoga 会被左栏里 `width: 100%` 的子元素影响，两侧并不相等。中栏又写死为 260px，比 `min(420px, 46vw)` 的指南针窄，指南针溢出到右侧。
- **做法**：要求绝对居中的行，在 `resize` 里直接算出两侧宽度（行宽减中栏减两个间距，再除以 2）；中栏宽度取实际内容的宽度。`bun run check:centering` 现在会测量 HUD 顶部的计时、说明行和指南针，误差超过 0.5px 即报告。

### 装饰性循环动画把整个画面带着重画

- **现象**：暂停或打开属性窗口、什么都没动时，UI 画布仍然 60 帧/秒重画，每帧约 82 次 draw call。
- **原因**：一块画布只能整体重画。HUD 的待机动画（纹章呼吸、终极技就绪光环、低血量脉动）每帧都 invalidate，盖在上面的窗口也跟着一起重画。另外，原来的测量脚本等待的是名为 `anon` 的画布，没有等到实际开局，结果「暂停」其实是在死亡结算之后、世界仍在运行时采到的。
- **做法**：HUD 的待机循环共用同一个 15Hz 时钟，保证在同一帧推进，不会互相错开、叠出 30 次/秒；有窗口盖在 HUD 上时，这些循环暂停。实测：暂停和属性窗口打开后空闲时为 0 帧 / 0 次 draw call（修复前为 181 帧 / 14842 次）。测量脚本要先确认确实进入了要测的状态（截图核对）。

### 描边文字的副本被父容器拉伸后错位

- **现象**：研究所顶栏的金币数字，深蓝描边整体比金色数字高约 4px，看上去像一团阴影。
- **原因**：uikit 容器默认 `flexDirection: row`、`alignItems: stretch`。数字外框高 26px 时，`OutlinedText` 的 fill 被拉成 26px 高，文字在框内垂直居中；描边副本是绝对定位，只有自身的 18px 高，贴在顶部。另一个原因：`lineHeight: "100%"` 在 uikit 中按父容器高度解析，而不是按字号。
- **做法**：描边副本使用与 fill 相同的盒子（`width/height: 100%`），文字默认不换行（`whiteSpace: pre`）；行高写成无单位的 `1`，不用 `"100%"`。

### 1× DPR 下 UI 边框发虚：布局不落像素网格，面板抗锯齿 2px 宽

- **现象**：1× DPR 的桌面上，2px 边框显示成 1px 实色加 1px 约 50% 的半透明；研究所看板 1px 的黄色内线只剩约 60%（`#dbc77d`，应为 `#ffd45b`）；存档窗口的 textarea 落在 323.515625 这样的半像素上。
- **原因**：两处都在 uikit 1.0.78 里。① 全部节点共用一份模块级 Yoga 配置，`setPointScaleFactor(100)`，布局只取整到 1/100 单位，等于不取整。居中、百分比、三栏均分、文字宽度都会留下小数边，浏览器在绘制时会把边吸附到像素上，Yoga 只能靠 pointScaleFactor 做到。② 面板片元着色器用 `smoothstep(-fwidth, fwidth, d)` 做边缘抗锯齿，过渡带有 2 个像素宽；即使边正好落在像素边界上，像素中心距边 0.5px 时覆盖率也只有 smoothstep(-1, 1, 0.5) ≈ 84%（实测 `#324d6a` 正是 84% 的 `#142f50`）。
- **做法**：`patches/@pmndrs__uikit@1.0.78.patch`（`package.json` 的 `patchedDependencies`）只改两处：`dist/flex/yoga.js` 导出 `setLayoutPointScale(factor)`，设置那份共享配置（后来改为 uikit 自己吸附边，见「取整模型」）；`dist/panel/material/shader.js` 把过渡带减半为 `±fwidth * .5`。`UiStage.update()` 在自己的 `root.update()` 之前设置本层的网格（UI 缩放 × 渲染器像素比，`setUiPixelRatio` 由宿主传入）；只有像素比变化（拖到另一块屏幕）时，翻转根节点上一个不影响布局的样式，强制 Yoga 重新取整。实测：板框三像素都是 `#0d233f`，黄线 `#ffd45b`，格子边框两像素都是 `#142f50`。要放到行中心的栏，宽度按设备像素取整并保持奇偶（HUD 中栏）。我们自己的着色器（描边环、硬底投影、内阴影、卡面、Toast、站点等）原本也用 `smoothstep(-fwidth, fwidth, d)`，同样是 2 像素宽的过渡带，一并改成 `.5 * fwidth`；只有装饰性的球纹、颗粒和 HUD 有意加宽的那一处保持原样。
- **线宽也要取整**：80% / 150% 下，位置落在网格上之后，1.6、1.5 这种设备宽度的边框仍会有一个混色像素。`UiStage` 在布局前把本层所有 uikit 边框宽度取整为 `max(1, round(w × 网格)) / 网格`（与浏览器一致），记下原始值，之后再被设置时重新取整；着色器里的线宽（描边环宽度和间距、硬底投影、内阴影、井面上沿、放逐虚线框、HUD 槽框）用 GLSL `crispLine(w, fwidth)` 取整，跟随任意层的缩放和像素比。实测 80% / 150% × 1× / 2×：板框、格子边框、黄线都是整像素的纯色。
- **升级 uikit 时**：补丁按 `名字@版本` 登记，版本号不再匹配时 bun 照常安装、**不打补丁也不报错**（pnpm 会拒绝）；漏打后 `bun run typecheck` 会因 `src/ui/gpu` 引用的补丁导出（`setImageLoader`、`setLayoutGrid`）缺失而失败，但不能只靠它。逐项检查补丁里的改动：① Yoga 不取整（`createDefaultConfig` 里 `setPointScaleFactor(0)`），`yoga.js` 导出 `layoutGrid` / `setLayoutGrid`；② `FlexNode.updateMeasurements` 把每条边（盒子、边框、内边距）各自吸附到网格，尺寸、相对位置和内边距都由吸附后的边相减得到（`snapToGrid`）；③ `FlexNode.layoutInner` 记下吸附前的内容区尺寸，`text/layout/index.js` 按它换行；④ 文字测量的向上取整不越过约束（`roundMeasurement`）；⑤ 面板抗锯齿过渡带（`±fwidth * .5`）；⑥ 多页字体（见「一个字体多张图集页」）：`Font.pages / pageSizes / pageReady / setPageImage`、`FontInfo.pageTextures / pageSizes`、`glyphInfoMap` 公开为只读，`cache.js` 的 `pageTextures` 分支，字形组按页分组（键含页、`patchIndex = page`、页未就绪不画），`InstancedGlyph` 换页时先离开旧组再进新组，`createInstancedText` 在自己的 effect 里读深度和渲染顺序，以及这些改动在 `.d.ts` 里的声明。上游已经有的就从补丁里删掉，没有的就在新版本上重做，然后运行 `scripts/ui-edge-snap.test.mjs` 和 `scripts/ui-text-measure.test.mjs`；⑥ 还要按那一条的做法在浏览器里把一半字形临时挪到第二页复查。`updateMeasurements` 的上游实现变了的话，要重新确认它仍是唯一读取 Yoga 布局结果的地方。

### 文字末尾一列淡竖线：MSAA 在四边形外取样，图集字形紧挨着

- **现象**：1× DPR 下，「HP」「+40」「2/2」这类文字节点的最后一个字后面有一列约 10% 墨色的竖线，高度正好等于字高；2× 下看不到。
- **原因**：UI 渲染器开着 MSAA。四边形边缘的像素只要有采样点被覆盖，片元着色器就会在像素中心执行，而像素中心在四边形之外，UV 被外推到字形框以外。图集是 `msdf-atlas-gen` 无间距排列的，字形框外一个 texel 就是下一个字形的格子：本字形外侧的 `(0,0,255)` 和邻格的 `(0,255,0)` 各自的中值都是 0，双线性插值后变成 `(0,127,127)`，中值 0.5，正好算作「在边上」。最初以为原因是 mipmap，关掉 mipmap 后竖线仍在，单独把各向异性过滤设为 1 也没有变化。
- **做法**：`scripts/fonts/build-ui.py` 加 `-outerpxpadding 2`，每个字形框外再生成 2px 本字形的距离场（不计入字形框），越界取样读到的是本字形外侧的值。页面尺寸改为固定 2048×1280，不再用 `-potr`（否则会跳到 2048×2048，显存翻倍）。MSDF 页面另外关掉 mipmap、使用线性过滤：对距离通道求平均没有意义。
- **规律**：要判断一列颜色属于哪个节点，就把那个节点临时改成纯红再截图，比推理快。

### 文字节点的盒子比父容器宽 1px

- **现象**：开启像素网格后，`check:centering` 报 HUD 计时偏右 1.00px，而计时的根容器正好在 640。
- **原因**：Yoga 取整时，带测量函数的节点（文字）在宽度有小数时右边向上取整，普通容器四舍五入，所以文字盒可以比自己的容器宽出最多 1 个设备像素。文字左对齐，墨迹不受影响，偏的只是盒子中心。
- **做法**：居中检查量的是拥有这段文字的容器的盒子（`OutlinedText.root`），不量文字节点自己的盒子。

### 按数量判断要不要保留程序，会漏掉同一帧里被替换的程序

- **现象**：研究所第二次打开时又编译了 1 个着色器程序（灰度图标的材质），而前一轮测试这里是 0。
- **原因**：宿主在 `retainPrograms` 里给每个新程序加一次引用，让窗口关闭后程序仍然保留。它先比较 `renderer.info.programs.length` 和上次的数量，相同就直接返回。如果某一帧刚好释放了一个程序、又新建了一个，数量不变，新程序就没被保留，窗口关闭时随材质一起删掉了。
- **做法**：每次都按对象身份检查整张列表（`WeakSet`），不用数量做捷径。列表只有几十项，开销可以忽略。

### 最小布局尺寸要和安全区比，不能和整个视口比

- **现象**：手机横屏（左右刘海各 47px）下，研究所效果文字被截断成「伤害 …」，图鉴的关闭键压住了「状态」页签，可这些界面都已经声明了最小布局尺寸。
- **原因**：`screenScale` 用整个视口的宽高除以 `minLayout`，而界面实际是在扣掉安全区之后的区域里排版的，左右安全区会把可用宽度再吃掉 94px。另外，研究所的 640、图鉴的 667 这两个值是估出来的，不是界面内容真正需要的尺寸。
- **做法**：宿主用扣掉安全区后的宽高去和 `minLayout` 比较；每个 `minLayout` 都取实测「内容放得下」的尺寸（研究所 760、图鉴 750、整局 667×375）。HUD、对局窗口和地图叠层共用同一个比例，不再各自使用用户缩放。

### uikit 在创建 Text 时就请求字体图集，不等到布局

- **现象**：主菜单根本没有 700 字重的文字，首屏却要等三张图集（约 5.1MB）一起下完。
- **原因**：Toast 在宿主启动时就已经创建，它的 Text 用的是 700 字重，uikit 的信号效果在 Text 一创建就去取图集，与是否显示、是否布局都无关。三张图集同时下载，平分带宽。只是不对隐藏的 Toast 做布局，并不能阻止这个请求。
- **做法**：`fonts.ts` 在宿主说明首屏需要哪些图集（从菜单层的 Text 推出来，`atlasesOf`）之前，一张图集都不去取；首屏需要的先下，其余等它们到齐再开始。10Mbps 下首屏从 5.5 秒降到 4.0 秒，再加 4 倍 CPU 降速时从 6.5 秒降到 4.25 秒，图集质量不变。

### 手机窗口里莫名出现 3px 滚动条：文字盒子比父容器宽一两个设备像素

- **现象**：手机上的结算窗口出现横向滚动条（实测溢出 1.1px），暂停窗口溢出 0.5px，有的窗口出现纵向滚动条；内容本身明明放得下。
- **原因**：两处取整叠加在一起。① uikit 的文字测量函数把结果向上取整到 1/100，却不管 Yoga 给的约束宽度：在 467.5 宽度内排出的一行，返回的是 467.51；Yoga 对文字节点的右边缘再向上取整到下一个设备像素，盒子就超出父容器一两个像素，父容器于是可以滚动。② 由「放得下」算出来的缩放比例（例如 0.8592…）乘以像素比之后，得到 1.7181… 这种二进制无法精确表示的网格，Yoga 用 float32 保存布局，一个刚好 804 像素的宽度会被当成小数，再被向上取整推出去一个像素。
- **做法**：① 在补丁里加入 `roundMeasurement`：约束模式下，向上取整的结果不超过 `max(原始测量值, 约束)`。这样只去掉取整造成的超出；放不下的长词仍然保留真实宽度，溢出照样可见。`scripts/ui-text-measure.test.mjs` 覆盖了 467.5 这个例子。② `fitScale` 把算出来的比例向下取到 1/64 的整数倍（最多小 1.6%），用户自己选的比例保持原值。
- **排查方法**：开发版用 `__poketoneOverlays` 遍历带 `maxScrollPosition` 的容器，逐个列出子节点相对父容器内边的超出量，比看截图快得多。

### 状态切换时被抬起的按钮会让方向键判断错行

- **现象**：结算窗口里，焦点在「换宝可梦」时按 ↓，焦点跳到了「再来一局」。
- **原因**：方向键导航读的是 `globalMatrix`，里面包含了变换；获得焦点的按钮被悬停姿态抬高约 1px，旁边的按钮就被当成在它「下面」。
- **做法**：`grid-nav.ts` 改用静止的布局位置：从当前节点沿父节点链把 `relativeCenter` 累加起来，不包含变换和滚动。

### HUD 顶行被压扁，守卫血条盖住横幅

- **现象**：同时出现三条横幅时，守卫血条盖住第一条横幅上沿约 5px。
- **原因**：HUD 根节点是一列：顶行、横幅、底行。空间不够时，Yoga 会压缩所有可以收缩的子节点，而 flex-shrink 默认是 1，顶行也被压扁了，中栏（包含血条）就伸到了顶行下边之外。
- **做法**：顶行和底行设为 `flexShrink: 0`，空间不够时只压缩横幅区，横幅可以向下溢出，但不会被推到血条下面。

### 亚像素滚动条的另外两个来源：Yoga 对文字盒子向外取整、内边距不在设备像素上

- **现象**：上一条修完之后，手机上的结算和属性窗口仍然可以滚动 0.5 到 1.1 个单位；即使缩放正好是 0.8 也会出现。
- **原因**：
  - **文字盒子向外取整。** Yoga 的 `setMeasureFunc` 会自动把节点标记为 Text 类型；在取整到像素网格时，Text 节点的左边缘向下取整，宽度有小数时右边缘向上取整。拉伸开的文字宽度来自父节点还没取整的可用宽度，几乎总带小数，所以文字盒子会比父容器宽出最多两个设备像素，而它画出来的内容其实只有一半宽（例如 228 宽的一行，放在 467.5 宽的栏里，盒子却有 468.75）。uikit 按子节点的盒子计算滚动范围，父容器于是可以滚动。yoga-layout 的 JS 接口没有 `setNodeType`，没办法关掉这种取整。
  - **内边距和间距不在设备像素上。** 8 个单位的内边距在 0.8 × 2 DPR 下是 12.8 个设备像素。Yoga 单独对子节点的相对位置取整（12.8 → 13），而父容器的内容区是按精确的 12.8 算的，所以子节点会超出父容器内容区一点，兄弟节点之间也会重叠一个像素。
- **做法**：
  - （以下两条做法已被「取整模型」取代并删除。）补丁里新增 `contentExtent`：文字节点在 `updateMeasurements` 里按最终的内部宽度重新测量一次（AtMost 模式，也就是它实际换行的方式），滚动范围用测量结果，不用它的盒子。真正放不下的长词仍然按原宽度计入。曾经试过用「最后一次测量调用」的结果，这是错的：Yoga 会用不同模式调用多次，包括不受约束的 max-content，所以段落会报出整行的宽度。
  - `UiStage` 在布局前把内边距和间距与边框宽度一起取整到设备网格（`crispSpacing`，0 仍然是 0，不设最小值）。
- **顺带暴露的真溢出**：结算窗口的提示「冒险记录无法读取（…）」画出来有 512 宽，盒子只有 443.75。uikit 默认的换行只在空格处断开，中文句子从来没换过行，只是被滚动区裁掉了。现在用 `text-fit.ts` 的 `wrapLines` 按盒子宽度预先断行（line-break.ts，与提示框同一套规则：在中文字符之间断开，不拆开拉丁词和数字），文字本身用 keep-all + pre-line 绘制。不用 `break-all`，因为它会把「Lv.12」「+24%」这类词从中间拆开。
- **排查方法**：探针脚本在 zsh 里调用时要写成 `node probe.mjs ${=c}`。直接写 `$c` 不会按空格拆分，整串会成为一个参数，结果所有配置量的其实都是同一个默认配置。每次都要在输出里打印实际的缩放和网格，确认量的是对的配置。

### 亚像素滚动条的又几个来源：固定高度低于最小高度、外边距不在设备像素上、照抄的间距常量

- **现象**：前两条修完之后，设置窗口仍然可以滚动 5 个单位，暂停窗口在 0.8 下可以滚动 0.625，研究所在拟合缩放（如 0.984375）下可以横向滚动 0.5 到 0.9。
- **原因**：
  - **固定高度低于最小高度。** 「存档」按钮写的是 `height: 50`，触控规则又给了 `minHeight: 55`。Yoga 按 55 摆放按钮，但父容器算自身高度时用的是 50，于是父容器短了 5。用纯 Yoga 最小复现（一列里一个 `height: 50, minHeight: 55` 的子节点）可以稳定复现，和 WebFlexBasis 开关、`overflow: scroll` 都无关。
  - **外边距不在设备像素上。** 「放弃冒险」的 `marginTop: 8` 和上一条的内边距是同一个问题。在页面里把它改成 8.125（取整后的值）或 0，溢出就消失了。
  - **研究所的列宽是用常量算的。** 三列宽度按「内边距 12、间距 12」计算，但舞台已经把这两个值取整到了设备网格（0.984375 缩放下 12 会变成 12.19），三列加起来就比内容区宽了一点。
- **做法**：控件的触控尺寸只写最小值（`minWidth`/`minHeight`），不写固定的 `width`/`height`。外边距取整和研究所按取整间距算列宽是当时的做法，已被下一条的取整模型取代：研究所现在按 `layoutInner`（吸附前的内容区宽度）算列宽。

### 取整模型：Yoga 不取整，uikit 把每条边吸附到设备像素

- **现象**：把内边距、间距、外边距都取整到网格之后，设置窗口在 667×375（拟合缩放 0.953）下仍可滚动 1 个设备像素；再把尺寸也取整，暂停和结算窗口反而在另外 4 个配置下多出 1 个像素的横向或纵向溢出。HUD 的时钟、信息行和指南针在 844×390 @150% 下偏离行中心 0.5 到 1.5px。
- **原因**：Yoga 自己取整时，节点的**相对位置**单独取整，**尺寸**却由取整后的绝对边相减得到。只有每个祖先未取整的绝对位置都正好在网格上时，两者才一致。居中、百分比宽度、flex 均分都会让祖先落在半个像素上。纯 Yoga 最小复现：所有长度都在网格上，一行里两个 `width: 48%`、`flexGrow: 1` 的子节点，父节点偏离网格 0 或 ¼ 像素时从不溢出，偏离 ½ 像素时 300 个宽度里有 149 个溢出 1 个设备像素。只把作者写的长度取整到网格永远覆盖不了这种情况。
- **做法**：补丁让 Yoga 不取整（point scale 0），`FlexNode.updateMeasurements` 自上而下带着父节点未取整和已吸附的绝对边，把每个节点的盒子边、边框边、内边距边各自四舍五入到网格（`snapToGrid`），尺寸、相对位置、边框和内边距都由吸附后的边相减得到。这和浏览器绘制时的吸附方式一样：子节点在父节点内容区里，吸附后仍在里面。随之删除的：Yoga 对文字节点的向外取整和用来抵消它的 `contentExtent`，以及内边距、间距、外边距的 `crispSpacing`（探针确认已不需要）。保留的，每项都有实测的失败情况：① 边框宽度仍在布局前取整为 `max(1, round(w × 网格)) / 网格`。只吸附边的话，同一个 2 单位边框在 0.8 × 2 DPR 下会画成 3/3/3/4 像素（设置窗口 9 个带边框的盒子里有 6 个四边不等）。② 文字按吸附前的内容区宽度换行（`layoutInner`），否则吸附可能让宽度少半个像素，放得下的一行会被折断。③ `roundMeasurement`：Yoga 用 float32 存尺寸，测量结果不向上取一点，文字会因为差一点点而折行；向上取整也不能越过约束宽度。
- **测试**：`scripts/ui-edge-snap.test.mjs` 在真正的 `UiStage` 上覆盖 300 个宽度 × 父节点偏离 0、¼、½、¾ 像素，断言没有任何子节点超出内容区。把补丁换回 Yoga 取整后，这个测试会失败。

### 放慢升级后只降敌人 HP 救不回来

- **现象**：经验曲线放慢（8:00 从约 22 级到 18 级）后，机器人通关从 21–33% 掉到 3–12%；把敌人 HP 增长降 30–40%，机器人 4:00 的击倒数几乎不涨，通关也几乎不变。
- **原因**：前期一发弹丸本来就能打死一只，清怪受「每秒能打几个目标」（数量、冷却、范围）限制，不受伤害限制；少升级削掉的正是目标数。模型的经验收入也不是和强度无关：清不过来时怪堆起来，击倒、经验一起掉，形成恶性循环。死亡来自被围，单下伤害降 20% 也没用。
- **做法**：改节奏时一起动「数量」（刷怪倍率）、伤害和 HP 曲线，再按少掉的击倒重拟经验步长；用机器人（至少 32 种子筛、128 种子定）判断，不要只看模型 novice。见 BALANCE「节奏、招式离群值与韧性」。

### 开发服务器热更新把 GPU UI 卡死在失败状态

- **现象**：多个线程共用工作区时，另一个线程在开发页里试玩，UI 突然不再响应点击和按键（2026-11-06 04:00–04:19 UTC）；当时 UI 线程正在一次脚本里连续改写 `motion.ts`、`hover-pattern.ts` 等六个文件。之后的代码树完整走一遍（鼠标、键盘、触屏）没有任何异常。
- **原因**：Vite 热更新只替换改动的模块。GPU UI、对局和渲染模块持有长期存在的对象（各个 stage、world、WebGL context），替换一个模块就会让新代码去操作旧模块建出来的对象。多文件修改写到一半时，新版 `motion.ts` 已经去掉 `UiMotion.ticked`，旧版 `hover-pattern.ts` 还在调用它，帧循环抛异常，宿主进入 `fail()`：设置 `failed`、取消输入、所有按键和指针处理都直接返回。热更新不会重载页面，所以后面的文件写完也恢复不了。
- **做法**：`vite.config.ts` 的 `poketone-reload-stateful` 插件让 `src/ui/gpu`、`src/run`、`src/rendering` 下的改动整页重载，不做热替换（音频引擎原本就这样处理）。连续保存时每次都重载，最后一次总落在一致的状态上。宿主的 `fail()` 保持原样：真实的帧异常应当明确失败，而不是被吞掉。

### 物品名显示成「■■■爪」：UI 字体图集是一套没有对齐的文件

- **现象**：道具卡标题「先制之爪」显示成三个实心方块加一个正确的「爪」。当时磁盘上的 `public/fonts/gpu/` 是混合状态：ui-500 是 13:18 一次失败构建写出的新版（949 字），ui-700、ui-800 和 manifest 还是 11:55 的旧版（916 字）。
- **已确认的**：实心方块是 UIKit 的 `MISSING_GLYPH`（`renderSolid`），即浏览器里那份字体的字形表没有这几个字。json 与 webp 来自不同构建时（两种方向都复现过），画出来的是错位的别的字形，不是方块。磁盘上和 git 记录里的每一版 ui-800.json 都有先、制、之。
- **推断（未复现）**：那个浏览器载入的是一个从未完整保留的中间状态，很可能是上面那次中断构建留下的混合集合。它当时读到的具体文件已无法找回。
- **结构漏洞**（与推断无关，都已关闭）：① `build-ui.py` 逐个字重直接覆盖固定文件名，中途失败就留下混合的一套；② 文件名固定，生产环境 `/fonts/` 缓存 7 天，部署后可能旧 json 配新页；③ 载入器不核对 json、页面和清单是否同一次构建；④ UIKit 遇到缺字只记日志后画方块。
- **做法**（可靠性由测试保证，不靠上面的推断）：
  - 原子发布：全部页面先在临时目录烘焙，全部成功才发布；文件按内容 SHA-256 命名并在清单 / json 里记完整摘要，先装到旧文件旁边，再一次 rename 替换清单。发布锁放在集合目录外，覆盖整个安装 + 换清单 + 清理过程，第二个构建等待而不是交错。发布不立即删文件：保留最近 3 次发布引用的文件，这只保护本地和并发构建（开着的开发页跨重建）；仓库和部署镜像只带当前一版（提交前修剪到 1 版），部署后已打开的旧会话按需取旧页会 404 并明确报错，刷新即恢复。测试：`scripts/ui-fonts-build.test.mjs`（失败构建逐字节不变、保留窗口、发布中途启动的第二个构建等待；去掉锁时该测试会失败）。
  - 载入器只认清单：清单 `no-cache`，哈希文件 `immutable`；按摘要核对 json 和每页内容（同尺寸的别的页面也会被拒）、字数、页数和解码尺寸，不一致报「UI 字体图集与清单不一致」，宿主进入失败页。测试：`scripts/ui-fonts-paged.test.mjs`。
  - 缺字：UIKit 补丁记 `console.error`（带码位），但仍会画方块；开发构建里 `fonts.ts` 的 `logMissingGlyphs` 再记一次字体名和码位。运行时缺字只画方块、不阻断（用户 2026-11-06：方块可以接受，整页不可用不行；曾经把它升级成失败页，结果一个缺字就让玩家无法继续）。测试：`scripts/ui-fonts.test.mjs`。`scripts/ui-glyph-sweep.test.mjs` 在每个字重核对运行时生成的全部文字。
  - 字符集与分页：见 `docs/fonts-paging-design.md`（游戏文字的 core 集提交入库；名字字符的 base 集由构建生成）。

### 焦点环左、上被裁：裁剪容器的内边距小于焦点环的伸出量

- **现象**：主菜单「开始冒险」聚焦时，外圈的深蓝焦点环左边和上边被截平，右边和下边完整。
- **原因**：焦点环画在控件外面，偏移 3、宽 3，名义上伸出 6；绘制时偏移和宽度各自取整到整设备像素，再加半像素抗锯齿，裁剪边也取整到设备网格，最多还要多出两个设备像素。菜单指令列表会裁剪（`overflow: scroll`），内边距只有 4（右侧 10），第一个按钮的上边、每个按钮的左边、最后一个按钮的下边都被截掉。另外几个滚入视野的实现各自写了边距（图鉴 4、研究所 8，菜单、对局窗口、设置是 0），聚焦到列表边缘的一行时环也会被截。
- **做法**：`box-shadow.ts` 导出 `RING_ROOM = 8`（环的伸出量加最多两个设备像素的取整，网格至少为 1）。会裁剪的容器在装有可聚焦控件的各边留出这么多内边距（菜单指令列表）。所有「把聚焦控件滚入视野」都改用 `scroll-reveal.ts` 的 `revealInScroller`，它留出 `RING_ROOM`（图鉴、研究所、对局窗口、设置；菜单的两层滚动同样留出）。`OutlineRing` 把偏移和宽度记在 `content.userData.ring`，一次性的环探针（未进仓库）按实际绘制的伸出量，在每个界面、手机和桌面配置下核对每个可见控件的环都在所有裁剪祖先的可见框内；滚动容器还能继续滚的那一侧不算（聚焦时会滚入），另外对图鉴列表做键盘焦点逐行检查。修复后 4 组配置、约 100–190 个环，被裁 0 个。

### 焦点环竖边锯齿、逐帧抖动：设备像素取整落在 .5 上

- **现象**：1440×900、界面缩放 1.5、DPR 1 时，主菜单聚焦按钮的焦点环左右两条竖边参差不齐，每帧形状都不同，画面静止下来也一样；1280×800 缩放 1 时是干净的。
- **原因**：`crisp-line.ts` 的 `crispLine` 用 `floor(w/px+.5)` 把线宽取整到设备像素，`px` 来自片元的 `fwidth`。3 单位的线在缩放 1.5、DPR 1 下正好是 4.5 像素，`fwidth` 的浮点误差每个片元、每一帧都不同，于是逐行在 4 和 5 像素之间跳。所有用 `crispLine` 的地方都有这个问题（焦点环、按钮底边、HUD 外框、阴影偏移）。
- **做法**：取整时 .5 向上，并留一点余量：`floor(w/px+.501)`，和 CPU 侧 `crispWidth` 的 `Math.round` 一致。只有 DPR 1 加小数界面缩放（1.5 等，线宽 × 缩放正好是 x.5 像素）会触发；改动描边、线宽或取整时要在这个配置下复查。

### 一个字体多张图集页：uikit 只认单页，换页、就绪、顺序都要自己定

- **现象**：字体分页（`docs/fonts-paging-design.md`）后，uikit 1.0.78 直接拒绝：`cache.js` 遇到 `pages.length !== 1` 就抛错，字形组只按字体分，材质只绑定 `font.page`，UV 用整个字体唯一的 `scaleW/scaleH` 归一化。
- **原因**：uikit 的文字一字体一组一材质一贴图。分页后同一个 Text 的字形可能落在几页，同一字形换字后也可能换页；页的图片按需载入、可被释放、context 丢失后要重传；同一 major/minor 的几个页组在 `order.js` 的 `compareOrderInfo` 里比较结果相等，绘制先后只取决于网格在父节点里的位置，而组扩容会把网格摘下再加到末尾，顺序会随之翻转。
- **做法**（`patches/@pmndrs__uikit@1.0.78.patch`）：
  - 一个字重一个排版 `Font`，`pages` 是整个字体生命周期里固定不变的 `Texture`（材质只绑定一次，不随载入换贴图），`pageSizes` 按页给尺寸，UV 和着色器里的 `pageSize`（抗锯齿）都用字形所在页的尺寸。`Font` 自己给每页设 `flipY = false`、不生成 mipmap、`LinearFilter`：MSDF 页大约以 1/3 的格子大小绘制，mipmap 会把紧挨着的下一个字形一起平均，UIKit 的 alpha gamma 把这点渗色放大成词后的一列淡线，平均后的距离通道也不再表示边。屏幕空间抗锯齿负责缩小。
  - 驻留由字体层决定，通过 `font.setPageImage(page, image | null)` 告诉 uikit：放图片时 `needsUpdate`，下一次绘制上传；传 null 时释放上传和图片。`pageReady[page]` 是信号，页组订阅它：释放时立刻隐藏网格（`UiStage.render()` 不更新字形组，下一次 `onFrame` 之前的渲染也不能拿空页去画），到达时请求一帧，在下一次 `onFrame` 显示。
  - 字形组的键在原来的 (major, minor, depthTest, depthWrite, renderOrder) 后面加页，组的 `patchIndex = page`：同一层里页组的顺序固定，后一页画在前一页之上，不再取决于哪个网格最后扩容。程序不变：页号不进 defines，也不进 `customProgramCacheKey`，每页只多一次贴图上传。
  - 换页的字形先从旧组 `delete`，再换归属、写新字形，最后在新组 `requestActivate`（激活时写全部属性）。深度和渲染顺序在 `createInstancedText` 自己的 effect 里读，换字体、顺序、深度时整组重建；页组在字形第一次用到这一页时才建。
  - 缺字的 `MISSING_GLYPH` 是第 0 页的 `renderSolid`。伤害数字自己采样第 0 页，遇到不在第 0 页的字形直接抛错。`UiStage.releaseUploads` 释放每个字体的全部页。
- **约定：重叠的文字必须用明确的层。** 同一个字体、major/minor、renderOrder 的文字共用一组字形组，组内顺序按实例槽位（单页时也不是创建顺序：实测同页重叠时先建的那段画在上面），组之间按页号，只是同一层里的兜底顺序。所以互相重叠、颜色不同的文字（文字投影、描边、压在文字上的角标）都用不同的 `zIndex`（`stack()`）或 renderOrder 分层，不靠创建顺序或页号。核查（2026-11-06，QA 全部界面走查 × 桌面 1280×800 / 手机 844×390，每个界面找可见、包围盒重叠、颜色不同且字体和 major/minor/renderOrder 都相同的文字对）：0 处；所有投影标题、描边文字、HUD 角标、Esc 角标都已经用 `stack()` 分层，伤害数字是自己的网格（renderOrder −10，只用第 0 页）。唯一的命中是手机 HUD 计时器的描边副本与下面一行守卫信息的行盒相接不到 1 单位，墨迹不重叠。结算界面那次没走到（走查在「放弃 → 结算」处超时，与本改动无关），没有核查。
- 空的页组保留网格和缓冲（不可见，不产生 draw call），随舞台销毁才释放。
- **留给驻留/就绪设计**（未处理）：只被保留的空字形组或树外拥有者引用的字体，`UiStage.releaseUploads` 遍历不到，它们的页由驻留拥有者负责释放。伤害数字不订阅 `pageReady`，所以第 0 页必须一直驻留。
- **验证**（开发构建里把每个 UI 字重一半的 CJK 字形临时挪到第二页，第二页用同一张图片，结果应与单页逐像素一致）：桌面 1280×800 的研究所、返回后的主菜单、context 丢失后恢复的研究所都与单页 0 像素差异（手机 844×390 只差背景花纹动画）。打开研究所的编译次数相同（4 对 4），context 恢复的编译次数也相同（34 对 34）。第二页未就绪时只隐藏它的字形，到达后（包括在研究所进场途中到达）补齐；释放后在同一个任务里（任何帧更新之前）它的组就不可见，下一次渲染只少了第二页的字，没有警告。字形组从 10 个变成 15 个，缓冲从 68 KB 变成 76 KB，一次重画的 draw call 从 350 次变成 365 次。

### 单画布：跨 await 持有的 render target 在下一帧被应用循环换掉

- **现象**：`scripts/ui-settings-render.browser.mjs` 在接入唯一的 `AppRenderer` 后读不到设置窗口标题的白色像素；同样的代码用独立的 `WebGLRenderer` 时通过。
- **原因**：脚本开头 `setRenderTarget(target)` 一次，之后每帧 `await requestAnimationFrame`。单画布后同一个 renderer 有应用帧循环，它在两次 await 之间把目标绑回画布（`setRenderTarget(null)` 再清屏），脚本后面的绘制就画进了画布。
- **做法**：framebuffer 状态不跨 await 持有：每次绘制前绑定自己的目标，用完恢复（`codex-model.ts` 的 `renderInto` 即此做法）。应用里的世界、UI 与辅助目标都在同一帧回调内设置并恢复各自状态（`grade.ts` 的 `inWorldPass`、`UiStage.render`）。

### 公网 HTTP 上首屏报「无法显示游戏界面」：`crypto.subtle` 只在安全上下文存在

- **现象**：部署到 HTTP 源站（非 localhost）后首屏直接进失败页，错误 `Cannot read properties of undefined (reading 'digest')`；本地 `localhost` 和 HTTPS 都正常，curl 200 也看不出来。
- **原因**：字体加载用 `crypto.subtle.digest` 校验 json 和页面的摘要，而浏览器只在安全上下文（HTTPS、localhost）提供 `crypto.subtle`。另外 `.dev` 顶级域在 HSTS 预载列表里，浏览器总会把 `http://*.dev` 升级成 HTTPS，所以 `.dev` 域名只能走 HTTPS。
- **做法**：`sha256Hex` 在没有 `crypto.subtle` 时改用 `src/ui/gpu/sha256.ts` 的纯 JS SHA-256，摘要校验照旧（`scripts/ui-sha256.test.mjs` 对照 Node 的结果）。验证时用本机局域网 IP 起 `vite preview --host`，它是非安全上下文，能复现线上 HTTP 的环境。

### 敌人顶着台地边的土坡不动，旁边的怪却能走下去

- **现象**：绿毛虫等地面敌人贴在两级草地之间的土坡边上永远不动；同一道坡，从别的位置过来的怪能走下去。扫 16 个种子、贴墙出发的追击里约 16% 卡住，与速度无关。
- **原因**：流场和移动对同一步的判断不一致（`nav/movement.ts` `blocked`）。路线按格子判：迈进单向崖面格（往下）合法，站在墙格里时不升高的步子都合法。移动却①按落点四周 4 格里**最严**的那格判，单向崖段挨着陡崖段的那一排被当成陡崖；②要越过墙线 0.25 格才算站上崖面，刚迈上去的身体既不算贴墙也不算在崖面上，往前的每一小步都被拒。流场一直指着这一步，身体正对墙推没有滑开的那一侧，于是不动。能不能下取决于从哪一排碰上坡，所以看起来像按物种区别。
- **做法**：越过墙线（墙距离 < 0）就算站在崖面上；迈进的墙按路线同一套格子规则（迈进格的类别）判，只在楼梯角墙线切进可走格时用四格最严，保住平滑墙线。曾试过按所在格判「站在崖面上」，结果墙线切进可走格的凹角成了出不去的陷阱（独立审阅发现，`nav.test.mjs` 的墙角用例）。擦到墙线不到 0.25 格的身体总能往外退。`scripts/nav.test.mjs` 用真实种子的两道坡对绿毛虫和尼多朗都验证能走下去。路线和移动的规则以后改一处必须对照另一处。

### 换区后重建场景报「模型材质应为 MeshStandardMaterial，实际是 MeshLambertMaterial」

- **现象**：第 1 区离开后，下一区的场景构建失败，弹出「无法开始冒险」，错误指向玩家模型的材质类型。
- **原因**：`mountRig` 把玩家模型蒙皮网格的材质原地换成 Lambert 副本（外加自阴影深度材质），`unmount` 只释放副本，没有把原材质放回去。模型实例属于整局（`loadRunAssets`），换区时新的 `createRunView` 再挂一次同一实例，`lambertCopy` 就读到了上一次留下的 Lambert。
- **做法**：`mountRig` 记下每个网格原来的 `material` / `customDepthMaterial`，`unmount` 时放回。凡是会被重复挂载的共享实例，挂载时改了什么，卸载时就要原样还回去。

### 换到 bun 后：`node:test` 文件直接跑报错、长测试 5 秒超时、`assets:game` 无视模型名

- **现象**：`bun scripts/x.test.mjs` 报 `Cannot use test outside of the test runner`；`bun test` 下跑整局的测试在 5 秒处失败；`bun run assets:game -- bulbasaur` 重建了全部模型。
- **原因**：bun 只在 `bun test` 里执行 `node:test` 的用例；`bun test` 默认每个用例限时 5000 ms（bun 1.4.4 上实测 `bunfig.toml` 的 `[test] timeout` 对这些 `node:test` 用例无效，命令行 `--timeout` 有效）；`bun run` 会吞掉参数里的 `--`，而 Blender 只把 `--` 之后的参数交给 Python。
- **做法**：测试一律 `bun test --timeout=0 ./scripts/<文件>`（`test:sim` / `test:ui` 已带 `--parallel --timeout=0`，`--parallel` 让每个文件各用一个进程，和 `node --test` 一样互不串状态）；`assets:game` 脚本自己以 `--` 结尾，名字直接跟在后面：`bun run assets:game bulbasaur`。

### 第 2 区守卫血条写着「飞天螳螂」，尼多王出招时往前栽倒

- **现象**：凯罗斯 / 尼多王出场时 HUD 守卫名仍是「飞天螳螂」；尼多王放地裂和践踏时身体前倾 0.35 弧度，像要摔倒。
- **原因**：只有一个守卫时写下的假设：`run-hud.ts` 把名字写成字面量；`createRunView.ts` 对任何守卫的 `dash` 阶段都前倾（飞天螳螂的冲刺），而尼多王的 `dash` 是站着让地裂生效。
- **做法**：名字随 HUD 快照的 `boss.name` 走（只在变化时改字，不每 0.1 秒重排）；姿态由 `view/enemyMotion.ts` 按当前守卫的 brain 决定。加新守卫时搜一遍按「守卫」写死的视图 / UI 行为，阶段名在不同 brain 里含义不同。

### 大厅弹出「ui-move released」提示，挡住底部法律声明

- **现象**：开发服务器上每次新开大厅，底部都弹一条英文提示「ui-move released」（1280×800 下正好盖住法律声明行）。
- **原因**：`useAppAudio` 挂载时持有全部 UI 音效，并把 `held.result` 的任何拒绝都转成提示。按等待句柄的约定（`src/prepare/handle.ts`），句柄在载入完成前被释放，会以 `AbortError`（`<名字> released`）拒绝。React StrictMode 在开发环境下会先卸载、再挂载一次 effect，第一次的持有在载入中就被自己的清理函数释放，这个取消就被当成了载入失败。
- **做法**：声音的载入失败只由引擎上报（`onError`，每次失败一次），持有者不再读 `held.result` 报错；声音持有在失败时也照常就绪（静音），因此也不再挡首屏或出发（见 `docs/AUDIO.md`「载入」）。别处读 `Handle.result` 并上报错误时，仍要把自己 `release()` 引起的 `AbortError` 排除掉（如 `app-host.ts` 的 `failure`）。

### Blender Python 抛错后仍返回退出码 0

- **现象**：P4 勇基拉本地修复抛出 `RuntimeError`，`bun run assets:game kadabra muk` 仍返回 0，旧 GLB 留在原位，后续渲染看起来像构建成功。
- **原因**：未设置 Python 异常退出码时，Blender 的正常退出不代表脚本成功；输出文件存在也可能只是旧产物。
- **做法**：直接运行 Blender 验收脚本时带 `--python-exit-code 1`。此次保留既有 bun 命令，另检查构建日志没有 `Traceback`、每个指定模型都有构建记录，并以最终 GLB 的哈希和实际三角面数登记 provenance。不要只凭进程退出码或文件存在判断构建成功。

### 减面后拳脚与触角碎开

- **现象**：火暴猴、巴大蝶等在预算内出现浮动碎片，源模型却完整。
- **原因**：glTF 导入沿 UV/法线拆顶点，直接 Decimate 把原本重合的接缝各自收缩。
- **做法**：仅对已检查的静态源连接重合开放边界，保留每角 UV，再同预算减面并逐图比对。蒙皮与近邻独立薄片不能机械套用。

### idle 最低帧接地，其他帧却浮空

- **现象**：水箭龟等固定 lift 正确，idle 仍离地约 0.06 世界单位；起跑混合又陷地。
- **原因**：源动画腿脚未约束，固定 lift 只处理最深一帧；四元数混合的轨迹也不保证接地。
- **做法**：在最终骨架烘焙双脚/髋部约束，用实际蒙皮表面量。运行时只给额外穿地正向补偿，不压低 run 腾空。CPU 蒙皮前必须刷新 SkinnedMesh 的 bindMatrixInverse，单用 updateWorldMatrix 不够。

### 换区后尾巴越挂越歪

- **现象**：复用模型重挂时把离场偏转当作新的 rest，静止后也不恢复。
- **原因**：卸载只停止 mixer，没有恢复程序尾骨。
- **做法**：TailSpring.dispose 恢复捕获的 rest；真实挂载/卸载跨三次复用测试保护此契约。

### 手机短横屏右侧出发栏滚动，名称卡被卷走

- **现象**：宽屏手机横置时，名称卡与出发按钮不能同时保持在右栏内；底部声明进一步挤占高度。
- **原因**：共享缩放虽同时读取宽高，页面申报的最小高度却小于实际堆叠内容；局部滚动掩盖了这个布局契约错误。只让 React 外壳使用 `100dvh` 也不能保证固定定位 canvas 跟随浏览器栏变化。
- **做法**：共享 `fitScale` 保留纵向工作区并维持 80% 可读下限和 44px 点击目标；声明移到品牌下方，属性 chip 并入名称卡，删除特性行与出发栏滚动。canvas 本身使用 `100%` / `100dvh`，隐藏准备阶段仍保留布局盒，尺寸统一从 canvas client size 读取。932×430、844×390、667×375、1280×800 已看；真实 iPhone 浏览器栏与安全区变化仍需实机验收。

## `bun test --parallel` 偶发卡死并满 CPU 空转

- 症状：`test:sim` 平时约 11 秒，偶尔一个 worker 永远不结束，CPU 100%，已无子进程；`--timeout` 不起作用。负载越高越容易出现。
- 原因：bun 1.4.4 在并行 worker 中用异步子进程（`execFile`）时，高负载下可能漏掉子进程退出事件，事件循环一直空转等待（采样栈停在 `kevent64`）。per-test 超时只能打断回到 JS 的代码，打断不了这种空转。
- 修复：测试里需要子进程时用 `spawnSync`（同步取退出状态，不经事件循环）；`test:sim` / `test:ui` 经 `scripts/test-deadline.mjs` 加总时限，卡死时失败并报出命令，而不是无限等待。

## Bun 开发服务的端口独占

症状：同一端口再次调用 `Bun.serve`，没有预期的 EADDRINUSE。
原因：本机 Bun 1.4.4 在 `development: false` 下允许端口复用。只固定 port 不足以保证唯一实例。
修正：Web 和 Harbor 明确设置 `reusePort: false`，冲突直接失败。`scripts/web.test.mjs` 实际绑定同一端口检查，并验证停止后能重新绑定。开发刷新版本同时带实例 ID 和页面加载的构建版本，以识别服务重启与构建错误后的恢复。

## 线上缓存

### 「音效 enemy-heal 不在 bank.json 里」：浏览器拿着旧清单

- **现象**：部署后线上报 `音效「enemy-heal」不在 bank.json 里`，整套音效都不响；服务器上的 `bank.json` 其实有这一项。
- **原因**：`/audio/bank.json` 文件名固定、内容会变，却和音频文件一起按 7 天缓存。浏览器（也可能是 CDN 边缘）拿着比代码旧的清单；引擎又在清单缺任何一项时让整个音频库失败，把一处不一致放大成全部无声。美术、音频、纹理也都是「固定名 + 长缓存」，只是坏得不那么明显（旧图、旧声音、卡点错位）。模型此前用 `?v=` 查询参数，依赖 CDN 把查询串纳入缓存键。
- **做法**：
  - 代码只用文件本名引用公共资源（`/audio/…`、`/art/…`、`/models/…`、`/textures/…`），统一经 `fetchAsset` / `assetUrl`（`src/prepare/asset-url.ts`）取。发布构建（`scripts/web-build.mjs` 的 `assetUrls`）为每个文件生成 `name.<内容哈希>.ext` 副本，内容一变网址就变。
  - nginx：哈希文件 `immutable` 一年；本名文件一律 `no-cache`（每次校验）。不要再给固定名、会变的文件设长缓存，也不要用查询串做版本。
  - 不要绕过 `assetUrl` 直接 `fetch` / `resources().read` 这些目录（`scripts/build.test.mjs` 会拦）。新增被抓取的资源目录时，加进 `HASHED_DIRS` 和 nginx 规则。
  - 清单类数据缺某一项只让那一项失败并报告，不让整体失败（音频 `filesOf`）。

## 合作：一人断线或打开地图，全队冻结

- 症状：任意成员断线、刷新、直连回退或打开地图/菜单，所有人一起卡住；恢复后偶尔还停在「等待队友」。
- 原因：网络层用全房间恢复代次和全员在线屏障，暂停用全队投票；任一席位的问题都变成全队状态，且本机菜单与网络暂停意图容易脱节。
- 修复：合作不暂停共享世界；断线只把该席位置离线、输入清零，重连按席位 hello → 地图/resumed → ready。新增全局屏障前先问：另外三个人为什么要等？

## 合作：怪多时客机看到的位置与房主不一致

- 症状：房主看到客机被大量敌人包围，客机画面周围却没有怪，同时掉血；越玩越明显。
- 原因：差分基准直接引用世界里的嵌套对象，世界变化后基准也跟着变，`entityDelta` 认为没有变化而漏发；拥塞跳帧时又按全局节奏推进了基准。
- 修复：`wireEntities` 深拷贝嵌套值；每名客机保存自己的基准，只有发送成功才前进。测试断言基准与客机实际持有的状态一致，而不只是“收到了帧”。

## 合作：房主看客机滑行，客机看敌人步态频繁跳动

- **现象**：客机位置在房主画面移动，但角色不跑步；客机的敌人跳动/伸缩频繁顿挫，长局更明显。
- **原因**：`presentHost` 为避免二次插值把客机 `px/pz` 设成展示位置，玩家动画仍用这组坐标差计算速度，得到零。敌人和同伴用「总 elapsed × 当前速度」算步态相位；30 Hz 模拟与 20 Hz 快照产生交替的一步/两步位移，重建速度发生波动，每次速度变化都被总时长放大成相位跳变。
- **修复**：网络呈现单独返回采样速度，经 `createRun` 传给角色动画，展示坐标仍保持固定并在模拟前恢复。敌人/同伴由视图按每帧 dt 累积步态相位，实体消失时清理；不把相位写入模拟，不改快照或随机数。检查位置平滑时同时检查动画速度与相位，覆盖长局、暂停和快照耗尽，不能仅断言 x 单调增加。
