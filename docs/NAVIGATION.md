# 导航与地形移动

`src/run/sim/nav/` 让单位按「机动类别」受地形约束。所有玩家和会走路的敌人共用**地面**类，波波等属于**飞行**类；海岸另有只在海里的**游泳**类（玛瑙水母、海刺龙、金鱼王）和水陆都能走的**两栖**类（暴鲤龙）。地面单位缓坡随便走、下坡比上坡宽松，真正的陡崖和实体道具（岩石、树、以后的建筑）要绕开；飞行单位越过地形和道具。被挡住时沿障碍滑开（move-and-slide），不会卡死。它是纯 TS 模拟层的一部分：不依赖 DOM / Three.js，不用 `Math.random`，遍历顺序固定，联机动作与共享结算复用相同移动规则；地图以房主下发的实际地图为准（见 [MULTIPLAYER](MULTIPLAYER.md)）。

## 方案选择

手写网格 + 流场，不引入依赖。评估过的成熟方案：

- **recast-navigation-js（Recast/Detour，WASM）**：一张导航网格只有一组 `walkableClimb` / `walkableSlopeAngle`，表达不了「上坡 0.92、下坡 1.05」这种按方向不对称的限制。Detour Crowd 是逐个体寻路和避让，280 只群怪的开销随数量增长，也不是为锁步确定性设计的。WASM 要异步加载，还会给无头 Node 测试增加一道初始化。
- **通用流场库**：npm 上没有找到同时支持有向（不对称）边、运行时阻挡和分时计算的成熟包；我们的网格就是地形采样网格，核心算法本身不到 200 行。

群怪用共享流场才划算（开销与敌人数量无关）；点到点查询在同一张网格上跑 A*，规则完全一致。

### 网格

- 格心正好落在地形采样点上：格宽 **0.5**（`1 / terrain.resolution`），覆盖可玩区 ±44，**177 × 177** 格，外围再包一圈不可通行的墙格（179 × 179），邻居下标永不越界。
- 每格存高度和**陡度**：用中心差分算的地形梯度模（沿下降最快方向每单位的落差）。任意位置的高度、陡度都按四个格心双线性插值。
- 阻挡不改地形掩码，只改三张计数数组：`hard`（格子阻挡，身体和路线都不能进）、`soft`（圆形阻挡外扩 0.5 的覆盖范围，路线绕开，身体用精确圆判定）、`near`（圆形阻挡外扩 2 的范围，只在这里做精确圆判定）。计数允许阻挡互相重叠、各自增删。进入被阻挡格只允许是终点（玩家贴着岩石站时仍可达）。

### 地形分类（`walkable.ts`，每个类别建层时算一次）

可走不可走按**格**决定一次，而不是每一步按坡度现判，所以坡面上不会出现「这一块能上、旁边一块又不能上」的碎斑：

1. 陡度超过 `climb` 的格是墙；
2. 小于 `MIN_REGION`（16 格 ≈ 4 m²，8 连通）的墙块改回可走——缓坡上偶尔冒出的陡点、小土包都在这一步消失；
3. 3×3 闭运算把相隔一格的墙接上，崖边连续（只加墙不减墙；场地外按空地算，崖尾不会被接到场地边缘、封住旁边的通道）；
4. 被墙围住、小于 16 格（4 连通）的可走小坑改成墙；
   4b. **不留对角相接**：两个墙格只在一个角上相接（2×2 里墙在一条对角线上）时，把另一条对角线上更陡的那个空格也填成墙，反复直到没有这种点状接口。否则移动和寻路对这个只有一个点宽的缝判断不一致，人会卡住或挤过去；开发者模式的遮罩上就是两个菱形只碰一个角。
5. 每个墙格看周围 ±3 格内崖面最陡处（崖心）：不超过 `drop` 记为**单向崖面**，否则**陡崖**；再在 ±4 格（4.5 m）窗口里按多数决定，同一段悬崖不会一格单向一格陡崖地来回跳。按崖心判断，所以从缓的崖沿踩上去也不能顺着陡崖心滑下去。

### 地形规则（`terrainStep`，路线和身体共用）

```
从墙格出发（被推到崖面上）：只要不升高就能走 → 永远不会卡住
可走格 → 可走格：           一律允许，不再看这一步的坡度
可走格 → 墙格：             只允许往下走进单向崖面；陡崖两个方向都不行
```

- 路线掩码在相邻格心之间套这条规则；对角线要求两条 L 形折线都可走，路线不会切角。
- 移动用每个类别的**带符号墙距离场**（`wallDistance`：两遍 chamfer 距离，墙外为正、墙内为负，单位格）做双线性插值：< 0 算墙，滑行法线是同一个场的梯度。判定和法线来自同一个场，滑开后的那一步沿着挡住它的同一条边走，不会撞上格子台阶的下一级；一两格宽的细墙带、45° 斜墙也一样平滑。
- **不留死坑**：只能下不能上的地方会形成「掉进去就出不来」的坑。建层时从场地中心（出生空地，`terrain.ts` 保证平坦）反向搜一遍，「能走回中心」的格子不许迈进「走不回中心」的格子；移动也遵守同一张表（`homeward`）。

清理效果（种子 7919 × 1…8）：

| 指标                                   | 只按陡度阈值 | 分类后                          |
| -------------------------------------- | ------------ | ------------------------------- |
| 墙块数                                 | 150          | 92                              |
| 小于 16 格的墙块（格数）               | 56（331）    | 0                               |
| 被墙围住、小于 16 格的可走小坑         | —            | 0                               |
| 崖心不到 climb + 0.08 的「临界」墙块   | —            | 1（16 格）                      |
| 墙格占可玩区                           | 2.15%        | 2.05%（单向 0.80%，陡崖 1.25%） |
| 可走地面中能从出生点走到的比例（平均） | 99.5%        | 99.5%（每个种子 98.7–100%）     |

地形本身已经足够双峰（缓坡区坡顶 p99 0.85、最大 0.95；崖面区 p5 0.96、中位 1.07），分类后缓坡区里的墙格为 0%，所以没有再改 `terrain.ts`。

### 机动类别

```ts
interface MobilityProfile {
  climb: number; // 能走上去的最陡一步，也是能站着往上走的最陡地面
  drop: number; // 能往下走上去的最陡地面；大于 climb，两者之间的崖面是单向的
  flying?: boolean; // 越过地形与实体道具，只受场地边界限制
  water?: "swim" | "both"; // 水的规则：缺省 = 深水是墙；swim = 只有水深 ≥ 0.3 m 处可走；both = 水不挡
}
```

数值只在 `content/mobility.ts` 的 `mobilityClasses` 里出现一次；敌人表（`content/enemies.ts`）的 `mobility` 引用其中一类，玩家固定用地面类。`nav/profiles.ts` 维护机动类别的比较和导航分层规则。

| 类别 | climb | drop | 单位                           | 效果                                                                                             |
| ---- | ----- | ---- | ------------------------------ | ------------------------------------------------------------------------------------------------ |
| 地面 | 0.92  | 1.05 | 4 名可选宝可梦、除波波外的敌人 | 所有缓坡上下都能走；崖心不超过 1.05 的崖面能走下去、爬不上来；更陡的崖面上下都过不去；道具要绕开 |
| 飞行 | ∞     | ∞    | 波波                           | 越过地形和岩石树木（决定：飞行单位也无视实体道具）                                               |
| 游泳 | ∞     | ∞    | 玛瑙水母、海刺龙、金鱼王       | 只在水深 ≥ 0.3 m（`SWIM_DEPTH`）的水里；水下坡度不挡；岸上的格没有任何一步，不上岸               |
| 两栖 | 0.92  | 1.05 | 暴鲤龙（海岸第 2 区守卫）      | 坡度同地面；水不挡，深水也能走                                                                   |

取值依据：地形生成器用一张慢变噪声决定每段梯田边缘是缓坡还是悬崖。按这张噪声把采样点分成「缓坡区」和「悬崖区」，统计每段坡上陡度的峰值（当前地形，种子 7919 × 1…8）：

| 区域   | 峰值分布                                |
| ------ | --------------------------------------- |
| 缓坡区 | p50 0.50，p90 0.71，p99 0.85，最大 0.95 |
| 悬崖区 | p1 0.85，p5 0.96，p10 1.00，p50 1.07    |

climb 取 0.92 落在两者之间；个别超过它的缓坡陡点都小于 16 格，会被分类清掉。drop 取 1.05，明显比 climb 宽松，崖心不超过它的崖面可以往下走。

### 地形遮罩（给渲染层的契约）

```ts
groundBlockedMask(nav): TerrainMask
// { data: Uint8Array, width: 177, height: 177, originX: -44, originZ: -44, cellSize: 0.5 }
```

- `data[j * width + i]` 对应格心 `(originX + i·cellSize, originZ + j·cellSize)`，行优先；采样时取最近格或在格心之间插值都可以。
- **0 = 可走；255 = 墙（爬不上去）。** 返回的就是上面清理后的地面类分类，移动和寻路用的是同一份格子，泥土画在哪里、哪里就走不上去。单向崖面（能往下走）也记为 255：它对玩家来说同样是「上不去的土坡」。
- 从 `nav/index` 或 `nav/profiles` 导入都可以。
- 只看地形：岩石、树和运行时阻挡都不在里面；地形建好后不变，取一次即可。

### 流场

- 每个**有敌人在用的**类别一张积分场（按实际地面、游泳、两栖等类别建立），从所有存活玩家所在格同时出发做多源 Dijkstra，沿边**反向**松弛（「谁能一步走到这里」），上下坡不对称因此是对的。
- 边权取整数：正交 5、对角 7（≈√2，误差 1%），队列用 Dial 桶队列：8 个桶，入队出队 O(1)，没有浮点舍入问题。
- 方向不单独存一张 177² 的方向场：敌人查询时看所在格 8 个邻居的积分值取最小，然后**朝那个邻居格心**走（而不是沿网格方向平移），偏到边上的身体会被拉回路线，不会贴着崖边磨。
- 双缓冲：读者只看已发布的 `cost`，新一轮积分写进 `work`，跑完才交换，读不到半成品。
- **刷新策略（分时）**：每 tick 由 `updateEnemies` 调用 `refreshFlowFields(nav, players, 4000)`，所有类别合计最多结算 4000 格。某张场在「目标换了格子」或「阻挡变了」且上一 tick 有人读过时才算过期；过期的场轮流计算，每轮跑完再换下一张，所以任意时刻最多只有一张场在算，队列全局共用。
- 敌人转向（`enemies.ts` `steerToward`）是常见的混合做法：
  - 离目标不到 **6** 单位、并且直线可走时，每 tick 直接朝目标**当前**位置走（近身精确追击，不受流场刷新延迟影响）；
  - 直线检测每只敌人每 **4** tick 才重算一次（按 id 错开），结果存在 `Enemy.sightline` 里，100 只敌人围在玩家身边也很便宜；离开 6 单位就清掉缓存，进入后最多 3 tick 后重新检测；
  - 其他情况按流场走；流场没有数据（无路可达）时直接朝目标走。
  - 每 tick 都会读一次流场，让它保持「在用」，近身直线断掉时流场是新的。
  - 没有做「玩家附近的流场优先刷新」：近身已经精确追击，流场延迟只影响远处的敌人，部分刷新需要第二种搜索模式，不够简单，所以没做。
- 出生：敌人只在流场显示能走到玩家的格子出生；随机点不可达时沿射线向玩家挪最多 6 单位，仍不行就不生成。守卫一定在可达处出生：射线都不行时取竞技场 2 m 网格上最不显眼的可达点，没有就抛错（`director.ts`）。

#### 实测开销（本机，Node 26）

| 项目                                    | 开销                                                                     |
| --------------------------------------- | ------------------------------------------------------------------------ |
| 一张完整地面流场（31k 格，Dial 桶队列） | ≈1.1 ms（改用桶队列前的二叉堆版本 ≈3.1 ms）                              |
| 每 tick 刷新预算 4000 格                | ≈0.15 ms；地面流场约 8 tick（≈0.27 秒）刷新一次                          |
| 建一层地面掩码（分类 + 剪死坑）         | 3–5 ms（冷启动首次 13–19 ms），开局一次                                  |
| `stepWorld` 每 tick（8 局，顺序运行）   | p50 0.15–0.19 ms，p99 0.21–0.44 ms，p99.9 0.37–0.77 ms，最坏 0.6–3.5 ms  |
| 250 只敌人围着绕圈的玩家（3 个种子）    | 每 tick 中位 0.28–0.29 ms（改成近身节流直线检测前 0.30–0.31 ms，约 −7%） |
| 32 局整局平均（含机器人自身开销）       | 接入后 ≈0.18 ms，接入前同口径 ≈0.07 ms                                   |

流场的新鲜度：玩家速度 3.25–4 u/s，一次刷新（≈0.27 秒）内移动约 1 单位；近处敌人走直线，不受流场延迟影响。玩家站着不动时目标格不变，流场不重算。

机器负载高时（同机其他任务，load average ≈8）同样的局会测出 p99 1–2 ms、个别 tick 10–25 ms；单独重跑就消失，跟踪 GC 时也没有超过 2 ms 的停顿，所以上表取的是空闲时顺序运行的数字。

### 运行时阻挡

```ts
const id = addCircleBlocker(nav, x, z, radius); // 圆形：岩石、树、图腾
const wall = addCellBlocker(nav, cells); // 格子集合（墙、建筑占地）：用 cellAt(nav.grid, x, z) 取格子编号
removeBlocker(nav, id); // 未知 id 直接抛错
```

增删只改受影响格子的计数（圆形按包围盒光栅化，删除时用同样的参数反向减），地形掩码不重建；所有流场标记为 `dirty`，在下一次刷新时重新积分（仍受每 tick 预算约束）。没有做增量 Dijkstra（D* Lite 之类）：玩家一直在移动，流场本来就每隔几 tick 整张重算，增量修补省不下什么。

地图唯一静态契约是 `World.map: GeneratedMap`：高度与墙读取 `world.map.terrain`，实体道具读取 `world.map.obstacles`，保留通道读取 `world.map.passages`。`World.nav` 独立保存可变导航状态；换区时 map/nav 整体替换，快照恢复从传入 map 的 terrain 与导航续算事实重建 nav。

地图生成（`mapgen/`，见 `MAPGEN.md`）在最终地形的导航上把每个 `solid` 道具注册成圆形阻挡，把这份导航交给世界（`createWorld` 不再另建一份），世界再加站点阻挡，然后在这份导航上做最终验收。生成时实体道具不放在陡度 > 0.5 的地方（以免堵住坡道），也不放在平整地块、水洼和布局保留的通道上。

塔楼模板的静态墙也走 `addCellBlocker`：唯一占地来自 `terrain.walls`，每个格心对应中心 ±0.25 m 的完整方形。`hard` 记录实际墙格；`soft` 为路线增加 0.5 m 常见身体余量，删除时对称减去，重叠阻挡仍按计数处理。`moveWithSlope` 与 `bodyFits` 共用 `cellWallOverlap` 的身体圆/墙格方形相交，身体不能半穿墙；若新阻挡盖住已有身体，仍允许它走出。飞行沿用原先跳过地面阻挡的规则。

地图选址导航先登记墙，平台、道具和必要通道都面对真实占地；最终那份 nav 仍交给世界。裸 `createNav` 不隐式登记静态墙，因此快照重放阻挡不会重复安装。`groundBlockedMask` 仍只表示地形分类，选址所用遮罩另合入已登记的墙格。弹道和墙体几何不再从模板自行推算：`sight.ts` 与 `view/walls.ts` 都直接消费同一 `terrain.walls` 的格子和高度。

### 可达集（`routeReach`）与站立判定（`bodyFits`）

```ts
routeReach(nav, profile, fromCells, toward); // Uint8Array（带边框下标）：toward=false 从这些格能走到哪，true 哪些格能走到这里
bodyFits(nav, profile, x, z, radius); // 身体下地形可走，完整身体圆不碰墙格方形或任何圆形阻挡
```

- 每一步都用 `routeStep(..., intoGoal = false)`：和流场、A\* 同一条规则（地形掩码、阻挡、不切角），被阻挡的格子从不进入。反向搜索按「谁能一步走到这里」松弛，上下坡不对称、单向崖面都自然处理。
- 只用自己新分配的缓冲区，不建层、不碰流场的 `cost`/`work`/队列/调度顺序，所以开局验收不会改变之后的流场结果。
- 没有阻挡时，从出生格的正向可达集就是「地形上能走到」的集合（去死坑保证它也都能走回来）；地图选址用的就是这个。最终保证只认装好全部阻挡之后的双向结果（`MAPGEN.md`「失败定位」）。

### A\* 与直线判定

```ts
findPath(nav, profile, fromX, fromZ, toX, toZ, out); // out = [x0, z0, x1, z1, …]，不含起点、以终点结尾
hasWalkableLine(nav, profile, ax, az, bx, bz);
```

- A\* 与流场同网格、同规则（上下坡不对称、绕开阻挡、不切角），octile 启发，带 decrease-key 的二叉堆；缓冲区第一次查询时分配，之后复用（`seen` 用递增戳代替清空）。
- 拉直：从每个锚点出发，贪心跳到仍可直线行走的最远路径点。
- 找不到路时会搜完起点所在的整个连通区（最坏约 31k 格，几毫秒）；高频调用方应先用 `canReach` 或限制频率。
- 目前还没有调用方（预留给游荡者、召唤者、首领换位）。

### 移动（move-and-slide）

```ts
moveWithSlope(nav, profile, body, dx, dz); // body: { x, z, radius? }
```

- 位移拆成每步不超过 **0.25** 单位的子步（比任何崖面、墙格、岩石加身体半径都窄），首领冲刺 14 u/s、玩家冲刺 3.4 倍速、击退、分离推挤都不会穿过去。
- 每个子步按顺序检查：场地边界 → 格子阻挡（斜穿两格之间的角也算）→ 圆形阻挡 → 地形规则与死坑表。被挡住时只去掉位移里**朝向障碍法线**的分量，保留切向分量再试，每个子步最多 3 次，凸角（崖边接岩石）不会卡住。
  - 地形的法线取落脚点的地形梯度方向；圆形的法线取身体**当前位置**指向外的方向，沿它的切线走一定是向外，绕石头不会停顿。
  - 撞上地形墙时先「走了再推出」（Unity / Godot 角色控制器的 recovery 做法）：照走这一步，落点若进了墙，就沿墙距离梯度按穿透深度推回墙外 0.02 格，推回后的位移不比原步长、且本身合法才采用。沿墙的分量完整保留，凹凸的墙边不会把每一步都吃掉。
  - **转角微调**：投影 3 次仍完全走不动（凸角、台阶边），就把输入向它本来要滑的那一侧转 22.5°、再试 45°（步长乘 cos），先通的那个生效。正对墙推没有「那一侧」，原地不动，不会被带着横移。
  - 越过墙线（墙距离 < 0）以后用哪条规则，越过墙线就算「站在崖面上」（只能往下或沿等高线走；墙线切进可走格的凹角也算，否则走进去就出不来），迈进哪种墙按**路线用的同一个格子**判：迈进的那一格是单向崖面就能往下走，不看旁边更严的格子。否则流场指的路移动不认：单向崖段和陡崖段交界处、刚迈上崖面的身体都会顶着崖边不动，步子大的怪偶尔一步跨过去，看起来像「有的怪能下、有的不能」。只有楼梯角上墙线切进了可走格时，才按落点四周最严的墙格判，保持平滑的墙线。
  - 越过墙线不到 0.25 格的身体只是「擦到」：往墙外退的步子总是允许的，走到一块单向崖沿上还能退回去。
  - 实测（4 个种子、6390 次以 30° / 45° / 60° 斜推墙）：完全卡住从 1.9% 降到 0.8%，滑得明显慢（< 60% 切向速度）从 8.4% 降到 3.6%；剩下的一半是真正的凹角（顺着墙推也走不动）。
  - 45° 撞上直崖时每 tick 保留 70.7% 的速度（正好是切向分量 √½）；45° 撞上岩石时首个接触 tick 保留 69.4%（法线取在接触前一点点），绕石期间平均 94.8%。
- 已经和圆形重叠的身体（出生、被推进去、阻挡加在它脚下）只会被拦住「往里走」的步子，移动结束后再按穿透深度推出来，推出位移也走同一套子步。站在崖面上的身体按地形规则总能往下或沿等高线走；站在墙格里的身体总能走出来。
- 飞行类别只做场地边界钳制。
- 玩家（`updatePlayer`）和敌人（`updateEnemies` 的步伐 + 击退 + 分离）都只通过这一个函数移动。首领只在能直线走到玩家时起冲，冲刺撞上陡崖或岩石就停下（并沿边滑开）。冲锋兽群的小拉达离开场地时不受约束（场外没有网格），冲锋途中被地形挡住就转为普通追击。
- 唯一绕过它的是 `attacks.ts` 里火焰旋涡的吸引（直接改坐标），可能把敌人拖过崖边或拖进坑里；需要改成调用 `moveWithSlope`。

### 玩家起步与停步

只有玩家有加速度（`player-movement.ts` 的移动推进）：速度以固定速率追向输入，0.07 秒到全速、0.05 秒停下（30 Hz 下各约 2 tick），转身也走同一速率。冲刺开始时速度立刻变成冲刺速度；冲刺结束时超出步行速度的部分立刻截掉；冰面例外由该模块处理。敌人没有加速度，直接用流场方向乘速度。

### 水

- `surface.ts` 的 `sampleSurface(terrain.surface, x, z)` 是地面规则的统一读取入口，返回 `kind / waterDepth / lavaDepth / speed`。静态海水和有限水洼共用 `terrain.surface.water`（与 `map.water.depth` 为同一个网格），熔岩有独立深度，不会被当成水。
- `grid.ts` 通过同一个采样读取水深；`walkable.ts` 在坡度形态清理后把 **水深 > 0.6 m** 的格设为 `SHEER`，不会因水域小于 16 格被当噪点擦掉。深水于是自然进入同一份 pass、homeward、墙距离、A\*、流场、直线判定与 move-and-slide；刷怪/最终验收仍读这些规则，没有第二条“能不能走”定义。
- 浅水本身不阻挡。`moveWithSlope` 在拆子步前读取该处的地表速度倍率，适用于玩家、地面敌人、同伴及地面位移；飞行提前返回，不读水或熔岩。森林/沙漠倍率为 1，保持原行为；海岸为 0.8。敌人原有 wet 的 0.85 倍另由状态系统处理，两者在海岸叠乘。
- 熔岩不额外设导航墙：地形坡度允许时可以踏入，并由既有伤害/状态管线惩罚；宽堤道是安全跨越的位置。冰川 `ice` 为可走干地，玩家冰面滑移由玩家移动模块处理。海岸首版静态水位，没有潮汐或每 tick 地形重建。

**游泳 / 两栖（海岸，2026-11-07）。** 仍是同一条水规则：`walkable.ts` 的 `waterBlocks(profile, depth)` 在坡度清理之后决定水是不是墙，地面类深水（> `WADE_DEPTH` 0.6 m）是墙，游泳类反过来浅于 `SWIM_DEPTH`（0.3 m，岸和涉水边缘都算）是墙，两栖类水不挡。其余全部沿用：pass、homeward、墙距离、A\*、流场、直线判定、move-and-slide、`bodyFits`、刷怪的 `canReach`。按类别补充的只有下面几处：

- **游泳类的 home 与上岸。** 场地中心在岸上，游泳类的 homeward 从它最大的 4 连通可走区（开阔海面）的第一格开始算（`createLayer` 的 `homeCell`；中心可走的类别仍用中心）。岸上的格对游泳类没有任何一步，所以没有路线、流场或刷怪点从岸上开始；移动的「坑」规则（homeward 内不进 homeward 外）让它们停在水线，冲刺也一样。流场以玩家附近最近的可站水格为种子，所以游泳敌人聚到离玩家最近的岸边。
- **水中速度与站立高度。** 游泳和两栖类在水里不吃 `shallowSpeed`，也不因水变湿润（水是它们的环境）。它们站在水面上：`sight.ts` 的 `standingHeight` 返回水面高度（地面类仍是地形高度），供瞄准高度、近战 / 接触的同层判定（`withinStep`）、毒雾圈和渲染共用。
- **被甩下的游泳敌人。** 游泳敌人跟不上岸，留在海里会一直占刷怪上限。`director.ts` 的 `releaseStrandedSwimmers`：离所有存活玩家都超过刷怪环外径（24）且不在任何人屏幕上的游泳敌人直接游走（移除，不算击杀，不掉落）。森林、沙漠没有游泳敌人，不受影响。
- `primeEnemyNav` 只为本地图各区实际出现的类别建层和预算流场，森林、沙漠仍只有地面一层。

## 新增机动类别

1. 在 `content/mobility.ts` 的 `mobilityClasses` 加一类，敌人表里让 `mobility` 引用它。数值相同的类别自动共用一层掩码和一张流场；新类别第一次使用时建层（≈1–2 ms：掩码 + 剪死坑）。敌人类别在 `primeEnemyNav` 里于开局预先算好流场。
2. **新飞行单位**：引用 `mobilityClasses.flying`，不建层，不占流场预算。渲染层的悬浮动画也读 `mobility.flying`。
3. **新的地形规则**：在 `MobilityProfile` 加字段，在 `classifyTerrain`（如游泳 / 两栖的 `waterBlocks`）或 `terrainStep` / `createLayer` 里按格子属性决定能不能走；如果需要新的格子属性，在 `grid.ts` 的 `NavGrid` 加一张按格数组。流场、A\*、直线判定只读掩码，移动只调 `terrainStep`。
4. **能越过道具但受地形限制的类别**：需要在 `routeStep` 和移动里按类别跳过 `soft`/`near` 判定，目前没有这个开关。

`bun run test:sim`（`node:test` 写法，`bun test` 运行；bun 直接解析无扩展名导入），全部用真实的地面 / 飞行类别：

- 0.85 的陡缓坡上下都能走，遮罩里没有标记

- 被推到崖面上的身体能往下走、能沿崖走，不能往上
- 只能下不能上的坑被剪掉：地面单位停在坑边，飞行单位能进

## 流场恢复

已发布场、正在搜索的场和玩家当前目标是三种不同事实。快照恢复先按发布描述完整重建可查询场，再按搜索种子与已处理前缀恢复进行中的工作；直接预热当前玩家位置会改变后续移动、可达性判断与随机消耗。

阻挡安装顺序和机动层语义也属于恢复前提。已发布场若基于旧拓扑，只保存当前阻挡与搜索前缀不足以恢复它；潮汐等动态拓扑方案必须先解决该问题。生命周期与字段位置只在 [模拟地图 I01–I05](state-machines/simulation.md#i01) 维护。
